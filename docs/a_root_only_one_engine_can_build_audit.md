## 1. 錯誤一：`@list.mine` 不是可定義的（推翻偵察 §4.1 末段）

偵察寫：「Q-032 解封的是使用者座標：使用者可定義 `@int.mine`、`@unit.mine`、
`@u8.mine`、`@list.mine` 甚至 `@zzz.mine`。」

〔量〕四個標準根座標**全部仍封著**，只有控制組通：

| 式 | 結果 |
| :--- | :--- |
| `@zzz.mine`（控制組） | `9` |
| `@int.mine` / `@unit.mine` / `@u8.mine` | `1` / `2` / `3` |
| `/add.mine` | `⊥ #missing_key` — Key 'mine' missing in closed Cocoon |
| `@list.mine` | `⊥ #missing_key` |
| `@option.mine` | `⊥ #missing_key` |
| `@result.mine` | `⊥ #missing_key` |

`@list` 那一格另有 E4 規則（`type_constraint.rs:45`，12 個保留名不可遮蔽）作為
既有解釋；**`/add` 沒有**——它不是型別名。所以這不是型別模型問題。

## 2. 缺陷：投影路徑的查找順序是反的（Q-032 回歸，偵察未見）

〔量〕同一個名字、同一份原始碼，三種用法拿到**兩個不同的值**：

```nlang
/add: { mine: 1 }
app: {
  bare_add: /add        ;; → { mine: 1 }        使用者的
  applied:  /add(1, 2)  ;; → ⊥ #conflict        使用者的(無 %builtin)
  proj:     /add.mine   ;; → ⊥ #missing_key     標準根的閉合繭
}
```

**裸解析與應用走使用者的根；只有投影掉進標準根。**

原因在兩處查找的順序相反，且**同出於 Q-032 交付 `a71a69b`**：

| 路徑 | 順序 | 位置 |
| :--- | :--- | :--- |
| 裸名 | scopes → `~%Config` → staged → **`ctx.root`** → **`ctx.standard_root`** | `lib.rs:3673` → `:3700` |
| 投影 | scopes → `~%Config` → staged → **`ctx.standard_root`** → **`ctx.root`** | `lib.rs:3813` → `:3840` |

裸名那處還帶著寫對的註解：「They are not hydrated into the user root, so a user
definition above wins.」**投影那處把同一句話做反了。**

工單 §2.1 對此有明文：「root 先、標準根後……**不得改變這個方向**。」

### 2.1 寫得進身分，讀不回來

〔量〕提交 `/add: { mine: 1 }` 後，根物件**確實含有**該欄位、確實進了雜湊：

```
{ /add: { mine: 1 }  @list: { mine: 2 }  @zzz: { mine: 9 }
  app: { v: 1 }      ~%__nlang_system_digest: "2da5b713…" }
```

而寫下它的那台引擎讀不回 `/add.mine`。**這是「持有但打不開」（Q-031）在座標粒度
上的同一個形狀**，只是這次不是拒絕，是靜默地回答了別人的值。

### 2.2 為什麼 P1 是綠的卻沒見證到

`the_half_that_was_never_written_probe_test.rs:174` 的 P1 只斷言 `evolve` 不含
`Error`。`evolve` **確實**成功——失敗發生在觀測。而 O58 要的「四個孤兒變成可遮蔽」
**是觀測性質**。

> **教訓（本次新增）：斷言「沒有報錯」的探針，只見證了沒有那個報錯。**
> 與本弧已記的兩則同族（P3 綠而無見證；斷言訊息子字串＝釘拼法）。
> 這是驗收方的漏，探針由我寫並校準。

## 3. 錯誤二：`~%Official` 不是待裁項，是已裁而未兌現（偵察 §5 誤判層級）

偵察把 `~%Official` 列進 D2「逐案處理，不得以『都先保留』代替裁定」。
但 SPEC_13 §135 **已經裁了**，並寫了理由：引擎本地合成的同名節點
「不是該物件的退化版本，而是**另一個東西冒用其名**」，且指定了正解——
本地觀測該路徑應得 `⊥ #missing_key`。

〔量〕現值不是那個：

| 式 | 結果 |
| :--- | :--- |
| `~%Official` | `{{ }}`，CAID `27c48162…` |
| `~%Official.anything` | `⊥ #missing_key` |
| `~%NoSuchModule`（控制組） | `_` |

路徑本身解析成一個**被合成出來的空物件**，不是 `⊥`。這是現行 MUST NOT 的違反，
不是待裁項。

**耦合（偵察未指出）**：這個空殼在標準根的 26 個模組裡 ⟹ **它在每一個根的身分裡**。
移除它會移動標準根 digest ⟹ v0.26.0 之後那是破壞性身分變更。
**因此它不能當獨立清理做，必須搭 D2 的 B 或 C 一起切，否則身分代價付兩次。**

## 4. 補強：規格唯一一張核心清單，引擎只兌現三分之一

偵察 §5 量的是一個方向（引擎有 14 個模組規格沒有規範清單）。反方向沒量。

〔量〕SPEC_09 §5.1「核心系統組件清單」是規格裡唯一一張規範性模組表，六列：

| 規格列 | 引擎 |
| :--- | :--- |
| `~%Logic` | **缺席（`_`）** |
| `~%List` | 存在 |
| `~%Str` | **缺席**（引擎叫 `~%String`；`~%Str` 全規格僅此 1 處，`~%String` 0 處） |
| `~%Option` | **缺席** |
| `~%Result` | **缺席** |
| `~%Cond` | 存在 |

`option`／`result` 只以**型別**存在於 types 軸，以及 `option.`／`result.` 的
builtin 前綴——**沒有同名模組**。

**這改變 D2 的代價表**：偵察說 A（凍結 v0.26.0 全量）「最便宜」。
但 A 會蓋章一個**連規格自己的核心清單都不滿足**的標準根 ⟹ A 必須同時重寫 §5.1，
否則不自洽。A 沒有偵察說的那麼便宜。

## 5. 補強：§6 的 round-trip 障礙是 3 個欄名，不是 printer

偵察結論「由引擎印一份 `.n` 放進規格目前不可用」成立，但範圍可以收得更緊。

〔量〕標準根共 **265 個相異欄名**，其中**不是合法識別字的恰好 3 個**：

```
system / Engine / rules / %differential.1
system / Engine / rules / %differential.2
system / Engine / rules / %differential.3
```

全部在 `~%Engine` 一個模組裡，形狀是 arity 多載（`.1`／`.2`／`.3`）。
**這是引擎內部多載編碼漏進使用者可見座標**，不是 printer 的結構性缺陷。

⟹ D3 不必然要設計一套 escaping：先裁那三個座標的正準拼法，
round-trip 的障礙就從「printer 不可用」縮成「一個模組的命名慣例」。

## 7. §4.1 比偵察說的更重：這是 §6.7 的第三例

偵察把雙身分呈現為 D1 的設計選項。〔量〕但它同時違反 SPEC_04 §156 的
「顯示、`=`／`<=`、CAID **四者同調**」：

| 式 | 結果 |
| :--- | :--- |
| `@list` 顯示 | `{{ %kind: #type, %name: "list" }}` |
| `(@list)` 顯示 | `{{ %kind: #type, %name: "list" }}` — **相同** |
| `@list <= (@list)` | `#true` |
| `(@list) <= @list` | `#true` — **雙向** |
| `@list.%id` | `c596dc99…` |
| `(@list).%id` | `2a43f297…` — **不同** |

**顯示相同、雙向 refine、CAID 不同。**四者裡兩者說同一個值、兩者說兩個值。

這正是 v0.26.0 剛關掉兩次的 §6.7 形狀（等值不等位元組）的**第三例**。
⟹ **D1 不是自由選擇**：現況兩種讀法都不自洽，無論怎麼裁都有既寫下的東西要改。
