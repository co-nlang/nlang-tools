# 工單 Q-051：一把還沒寫完的金鑰

> **本弧不需要裁定。** 偵察 `docs/a_key_that_was_not_finished_being_written_recon.md`
> 探針 `crates/oo/tests/a_key_that_was_not_finished_being_written_probe_test.rs`
> **基線 3 綠 1 紅，已校準。**

---

## 1. 一句主張

〔讀 `value.rs`〕`create_new` 把身分檔的**名字**原子地佔下，**私鑰位元組在那之後才寫**
⟹ 存在一個「檔案已在、內容還沒到」的視窗。
過去的驗收修補為此加了 `load_after_race`（**100 × 1ms 有界重試**），
**但它只掛在輸掉 `create_new` 那一條分支上**；而 `load_or_mint` 的第一行是

```rust
if path.exists() { return Self::load(path); }   // 一次，沒有重試
```

⟹ **修補保護了賽跑的輸家，沒保護「根本沒參賽的旁觀者」，而失敗的是旁觀者。**

〔量，`v0.54.0` 標籤建置〕先把檔案弄成 0 B、背景 20ms 後寫入完整金鑰，
同時 `oo identity` ⟹ **rc=1**、`not a valid PKCS#8 … file left unchanged`
——**而重試預算是 100ms**。

## 2. 射程 ＝ 兩條不變式

**I1　一個「現在不完整、片刻之後就完整」的身分檔，必須被等到，不得回報為毀損。**
判準是**暫時性**，不是「檔案長度」。

**I2　任何情況下，一個行程都不得回報一把不在檔案裡的金鑰。**
這是**過去那次修補買到的性質**，本弧**不得把它賣回去**
——〔量〕當年是「8 個行程 → 3 把不同的金鑰，其中 2 個印出的公鑰不是留在檔案裡的那把」。

## 3. ⚠ 什麼**不是**缺陷（驗收方在這一點上錯過一次，寫在這裡免得再錯）

**一個永久無效的金鑰檔必須繼續被拒絕。**
驗收方第一次「機制確認」是把金鑰截成 0 B、看到逐字相同的錯誤就記下「成因確認」——
**那是錯的**：沒有人會把那個檔寫完，重試一萬次也該報錯，
而**一個讓那一格通過的修法比本 bug 更糟**。G2 釘住它。

**缺陷只在「暫時不完整」那一格**，R1 構造的正是那一格，且**只有那一格**。

## 4. 修法（兩個候選，你選，但理由要寫）

*   **甲　讓 `path.exists()` 那條分支走同一個有界重試。** 最小改動。
*   **乙　讓內容也是原子的**：寫進一個**自己獨佔**的暫存名，再 `link`／`rename` 到位。
    **⚠ 暫存名不得是可預測的固定名**——〔舊修補已記下的坑〕當年的固定 tmp 名
    「沒有任何賽跑者擁有它，而且它既不是 `.oo` 也不是身分路徑，
    **語言層讀得到那把私鑰**」。
    **乙較好的理由**：它讓重試從「必要」變成「不必要」。

**驗收方傾向乙，但沒有量它的代價**（`link` 在哪些檔案系統上不可用、
`rename` 會不會又變成無條件覆寫而違反 D2）⟹ **不足以推薦，你量了再決定。**

## 5. 紅線（探針已釘）

*   **G1** 對照：完整金鑰 rc=0，且**印出的 hex ＝ 檔案裡那把**。
*   **G2** **永久無效**（0 B 與截成 20 B 兩種）仍須 rc≠0、訊息含 `not a valid PKCS#8`、
    **且事後檔案位元組逐字未變**（D2）。
*   **G3** 不得回報不在檔案裡的金鑰；**若拒絕，就不得同時印出一把金鑰**。
*   conformance **162／162**；全樹 ×3 `--release --no-fail-fast`，**逐 target 聚合並保留失敗的測試名**。

## 6. 明確不做

*   **`pin_concurrent_first_mint_yields_one_key` 是別弧的探針，不得動。**
    它測同一個性質而 1／3 紅；本弧的 R1 把它確定性化。
    修完之後它**應該**停止間歇紅，**但那是推論不是本弧的斷言**
    ——它的隨機性還有第二個可能來源（`load_after_race` 的 100 × 1ms 在高負載下夠不夠）。
    **⟹ 若你在全樹 ×3 裡仍看到它紅，照實寫在 N.6，不要當成本弧失敗。**
*   節點金鑰（`resolve_node_home`）是否同一條路——**未量，見 Q1**。
*   斷電語義（`create_new` 的 metadata 未 sync）＝不同題。

## 7. 指名要你回答的問題（N.4 逐題作答，答案不利也照寫）

**Q1　節點金鑰走的是同一個 `load_or_mint` 嗎？** 若是，本弧的修補是否同時治了它？
若不是，它有沒有同一個視窗？**量出來，不要推論。**

**Q2　`load_after_race` 的 100 × 1ms 在全樹 ×3 的負載下夠嗎？**
給一個量測，而不是一個估計。若不夠，那是本弧的一部分還是另一列？

**Q3　你選了甲還是乙，為什麼？** 若選乙，回報 `link`／`rename` 的可用性與 D2 的處理。

## N. 交付回報（交付方填；本行以上一字不得動）

### N.1 射程逐項對照

**I1**　`load_or_mint` 在 `path.exists()` 時改走同一個 `load_after_race`（100 × 1ms）。
暫時不完整的檔被等到，不再一次 `load` 就報 PKCS#8 毀損。
R1：先佔名為 0 B、20ms 後寫入完整金鑰，`oo identity` rc=0，印出的 hex ＝那把。
同構造的節點金鑰（`oo node id`）修後亦 rc=0（見 Q1）。

**I2**　`load_after_race` 仍只 `load`，永不 `create_new`／永不覆寫。G2：永久 0 B 與截成 20 B
皆 rc≠0、訊息含 `not a valid PKCS#8`、事後位元組逐字未變。G3：拒絕時不印金鑰；等到時印的是檔案裡那把。

### N.2 順手改動（逐項指名）

無。只動 `Identity::load_or_mint` 的 `exists()` 分支（及 docstring）。未 `rustfmt`。

### N.3 工單哪裡是錯的

無。Q3 說明乙**單獨**過不了本弧的 R1，那是選法的理由，不是工單寫錯。

### N.4 Q1–Q3 逐題作答

**Q1　節點金鑰走的是同一個 `load_or_mint` 嗎？**

是。〔讀〕`Ouroboros::node_identity` 在 `identity_persist` 時呼叫
`Identity::load_or_mint(&node_key_path(ws))`（`lib.rs`），與 `oo identity` 同一函式。

〔量，`v0.54.0`〕把已鑄的節點金鑰弄成 0 B、背景 20ms 後寫回完整 83 B，同時 `oo node id`
→ **rc=1**，訊息逐字 `not a valid PKCS#8 Ed25519 key … file left unchanged`
——**與操作者金鑰同一個視窗、同一句話。**

修後同構造：`oo node id` **rc=0**（22.3 ms）。本弧的修補同時治了它，因為沒有第二條路。

另：`node_id_if_present` 走一次 `load`、失敗當「不在」。那條**從不鑄**，不是 `oo node id`，不在本弧。

**Q2　`load_after_race` 的 100 × 1ms 在全樹 ×3 的負載下夠嗎？**

夠。量測不是估計：

*   鑄一把金鑰（含行程啟動）p50 **1.90 ms**／max **2.74 ms**（n=30，`v0.54.0`）。
    PKCS#8 **83 B**。寫入遠短於 1 ms 的一格。
*   R1 形（20 ms 晚寫）：修後等到 **21.4 ms** 就 rc=0，沒用完預算。
*   永久無效：耗盡預算後拒絕，**114.3 ms**（0 B 與 20 B 各一次），檔案未變。
*   全樹 ×3 負載下 `pin_concurrent_first_mint_yields_one_key`：**0／3 紅**（三輪皆 `ok`）。

若不夠，那會是本弧的一部分（同一條重試）。今天量不到不夠。

**Q3　甲還是乙，為什麼？**

**甲。**

乙（獨佔暫存名再 `link`／`rename` 到位）治的是**我們自己的寫入視窗**。
I1／R1 的判準是讀端：檔案現在不完整、片刻之後完整——R1 用 `std::fs::write("")`
再晚 20 ms 寫入，**不經 `create_new_at`**。只做乙，`exists()` 仍一次 `load`，R1 仍紅。
⟹ 乙不是這條不變式的替代，重試也**不會**因此變成不必要。

乙的代價〔量，本機 `/tmp` tmpfs〕：

*   `os.link` 到不存在的 dest：成功，同 inode。
*   `os.link` 到已存在的 dest：**EEXIST**，dest 位元組不變 → **D2 可守**。
*   `os.rename` 覆寫已存在的 dest：**成功換成新位元組** → 這就是舊修補禁 `tmp+rename` 的理由。

乙若做，必須用 `link` 不能用 `rename`，暫存名必須隨機且與身分檔同目錄（舊固定名曾被語言層讀到私鑰）。
那是額外工程，且仍要甲才能過 R1。故只做甲。

### N.5 探針

無。R1 的 20 ms／100 ms 在本機穩定（等到 21.4 ms）。不認為構造不穩。

### N.6 數字

探針 **4／4**（G1–G3／R1）。符合性 **162／162**。
身分：`~%Math./add (1,2)` → `3`（對照 `(1,3)` → `4`）。

全樹 ×3（`--release --no-fail-fast --jobs 1 -- --test-threads=1`，逐 target 聚合 `test result:`）：

| 3 | 236 | 2242 | 0 | — | 0 | 0 | **ok** |

**`pin_concurrent_first_mint_yields_one_key` 在三輪裡紅了 0 次。** 推論（工單 §6：不是本弧斷言）與量測一致。

## 8. 驗收（驗收方填，2026-09-20）

**結果：受理，零修補回合。**

### 8.1 純度與探針

只動 `crates/interpreter/src/value.rs`（`load_or_mint` 的 `exists()` 分支一行 ＋ docstring）與本文件。
**未動任何測試檔**（條件式檢查）——含明文禁止的那支別弧探針。未 `rustfmt`。

### 8.2 量測（驗收方自量）

known-answer `~%Math./add (1,2)` → `3`（對照 `(1,3)` → `4`）。

探針 **4／4**：**R1 翻綠**，G1／G2／G3 三條紅線守住。

**代價量出來了，交付沒報這一格**（不是錯，是沒問）：

| 情形 | 修前 | 修後 |
| :-- | --: | --: |
| 好金鑰 | 3 ms | **3 ms**（未變） |
| 永久無效（0 B） | ~3 ms | **116 ms** |
| 永久無效（截 20 B） | ~3 ms | **116 ms** |

⟹ **一把永久壞掉的金鑰，現在每一個指令都要等 116 ms 才拒絕**，而那是持續狀態
（使用者修好它之前，每次叫用都付這筆）。**可接受**——它在錯誤路徑上、且換來 R1
——**但它是甲的代價，而乙沒有這筆**。記在這裡，不開修補回合。

全樹 ×3（逐 target 聚合、保留失敗測試名）：**三輪皆 `targets=236 passed=2242 failed=0`**，
`^error` 0，cargo exit 0。conformance **162／162**（rc=0，驗收方自跑）。
**先證明量測碰到了目標**：本弧探針 target 逐字 `4 passed; 0 failed`。

**那支別弧的間歇紅**：〔量〕三輪 **`ok`／`ok`／`ok`**（先前驗收方量到 1／3 紅）。
工單 §6 說那是推論不是斷言，**而量測與推論一致**。

### 8.3 交付更正了驗收方一處，而它是對的

工單 §4 寫「**乙較好的理由**：它讓重試從『必要』變成『不必要』」，並寫「驗收方傾向乙」。
**那個理由是錯的。** 交付指出：**乙治的是「我們自己的寫入視窗」，而 I1／R1 的判準在讀端**
——R1 用 `std::fs::write("")` 再晚 20 ms 寫入，**根本不經 `create_new_at`**
⟹ **只做乙，`exists()` 仍一次 `load`，R1 仍紅；重試不會因乙而變成不必要。**

**⟹ 而驗收方要把這一則講完整，因為它也是我的探針的一個性質**：
R1 釘的不變式**比這個缺陷所需的更強**——它要求「等過**任何**暫時不完整的身分檔」，
而不只是「等過**我們自己**的寫入視窗」。**那個更強的版本是站得住的**
（身分檔也可能由安裝程式、同步工具、使用者複製產生），**但它確實排除了「單做乙」**。
兩件事都記下：**我的理由錯了，而我的探針比我的理由強。**

交付另附乙的代價量測（本機 `/tmp`）：`link` 到已存在的 dest **EEXIST 且 dest 位元組不變**（D2 可守），
而 `rename` **會成功覆寫** ⟹ **乙若要做必須用 `link` 不能用 `rename`**，且暫存名須隨機同目錄。

### 8.4 ⚠ 交付誠實劃在射程外的那一格，驗收方追下去了，而它不只是範圍問題

交付在 Q1 末尾寫：「`node_id_if_present` 走一次 `load`、失敗當『不在』。那條**從不鑄**，
不是 `oo node id`，不在本弧。」——**劃界正確**（工單沒授權它）。
**但驗收方追了它影響什麼**〔讀 `lib.rs:1103-1120`〕該函式的失敗處理是 `.ok()`
⟹ **一個寫到一半的節點金鑰，會讓它靜默回報「我沒有 node id」**，而不是報錯、也不是等。

〔讀 `lib.rs:1268`／`peers.rs:527`〕它的兩個呼叫點都把結果餵給
`cmp_admission_order(a, b, self_id.as_deref())` ⟹ **那是同儕「准入排序」的鍵**
⟹ **一次金鑰檔上的競賽，可以靜默改變哪些同儕被收進有限的名額。**

**⚠ 這一段的後半是讀碼，不是量測**：驗收方**沒有**建出一個同儕情境去量那個排序差異，
只量到了「`load` 對寫到一半的檔會失敗」。**照實標記**，並入 Inbox。
**⟹ 它與本弧同族但方向相反**：本弧治的是「該等的時候沒等」，
那一列是「**失敗被寫成了一個答案**」（`None` ＝「我沒有」，而真相是「我還讀不到」）。
