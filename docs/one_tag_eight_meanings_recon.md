# 偵察：一個標記，八種意思

> 起因：v0.52.0 收弧後 Ready 首位＝「值編碼表寫完」（`REAL_03` §6.2 缺五個標記）。
> **開卡前先量這張卡是不是純規格弧。答案是不是。**
> 量測用 `v0.52.0` 標籤建置（`/home/gali/nlang-baselines/v0.52.0-verify`），
> known-answer `(1 = 1)` → `#true`／`(1 = 2)` → `#false`。

---

## 1. 這張卡原本以為的射程

`REAL_03` §6.2 的值編碼表列了 11 列，而引擎發出的標記不止 11 個。
Q-047 收弧時記下缺五個：`0x17` Thunk／`0x18` Range／`0xFD` `#blur`／`0xFE` `_|_`／`0xFF` `_`，
**而標準根自己就含三個 `0xFF`** ⟹ 今天公佈任何 CAID，第二個實作也算不出來。
v0.52.0 又加一列：`0x12` 的名字 `Int64`／`[i64_LEB128]` 是歷史拼法。

**原以為是純規格弧**（把引擎已有的行為寫進表）。

## 2. 讀 `bn_serial.rs` 得到的標記全集

| 位元組 | 意思 | §6.2 有沒有 |
| :-- | :-- | :-- |
| `0x01`／`0x02`／`0x03`／`0x04` | Combo／Cocoon／List／Tuple | 有（併成一列） |
| `0x10` | **Atom — 見 §3，它承載八種** | 有，寫作「Atom」 |
| `0x11` | Tag | 有 |
| `0x12` | 整數 | 有，名字是 `Int64`（歷史拼法） |
| `0x13` | Float（定點） | 有，**而它有損——O88** |
| `0x14` | Complex | 有 |
| `0x15` | Bool | 有 |
| `0x16` | Ref | 有 |
| `0x17` | Thunk | **缺** |
| `0x18` | Range | **缺** |
| `0xFD` | Blur | **缺**，且**無具名常數**，逐字 `buf.push(0xFD)` |
| `0xFE` | Bottom | **缺**，同上 |
| `0xFF` | Top | **缺**，同上 |
| **（無）** | **Union — `serialize_union` 一個標記都不推** | **缺，而且缺的不是一列** |

## 3. 主要發現：`0x10` 承載八種不同的值，而它們因此共用位址

`serialize_atom` 有八條臂都推 `TAG_ATOM` 然後寫一個字串：
`Str`／`MultilineStr`（內容）、`Code`（`format!("{:?}", expr)`）、`PathLit`、
`Unit`（字面 `"()"`）、`Regex`、`Uri`、`Time`、`Bytes`（`hex::encode`）。

**⟹ 凡文字相同者共用位址，而語言分得開它們。**

〔量，對照組 `"x"` `0b0872e1…` ≠ `"y"` `dc20d22d…`，量測碰得到目標〕

| 一組 | 共用位址 | `=` | meet |
| :-- | :-- | :-- | :-- |
| `"()"`／`()` | `5f6b36a7…` | `#false` | `("()" & ())` → **`"()"`** |
| `"ab"`／`r"ab"`／`p"ab"`／`u"ab"`／`t"ab"` | `2f5992b8…` | 四對皆 `#false` | 四式皆被吸收 |
| `"6162"`／`b"ab"` | `4414b39b…` | `#false` | `(b"ab" & "6162")` → **`b"[97, 98]"`** |

**六個值一個位址，再加一組兩個。** 這是 D69 的第三族，
**而它直接違反 v0.52.0 昨天才立的 `REAL_03` §6.7 第二條**（值不得共用位址）。

**⟹ 所以這張卡不是純規格弧。** 表不能誠實地寫成「`0x10` ＝ Atom」——
`0x10` 今天是八件事，而其中六件因此撞在一起。**修法與補表是同一件事**：
每一種給它自己的標記位元組，那些位元組就是表上要新增的列。

## 4. 不是違反的一格（留下，免得被當成第四族）

**所有 `⊥` 共用一個位址，而那是對的。**
〔量〕`(1 & 2)` 與 `("a" & "b")` 同址，**而 `=` 判它們 `#true`**
⟹ 值層認為只有一個 `⊥`，位址與值一致，§6.7 第二條不生效。
〔對照〕`((1 & 2) = _)` → `#false`，`⊥` 與 `⊤` 分得開。
（`Value::Bottom(_)` 把整個 `BottomDetail` 丟掉不入位址，與 D65 一致。）

## 5. 驗收方在本次偵察中作廢的一組讀數（留下，不刪）

**我一度讀出「union 與它的首元素同址」，那是我的量測工具的錯，不是引擎的。**
〔複驗〕`~%Discovery./identify_and_store ("a" | "b")` 回的是
**一個 CAID 的 union**（`cdf2d551…` | `3299762a…`，即逐元素分配），
而我的 helper 取 `head -1` 加第一個欄位 ⟹ 只看見第一個。
`(1 | 2)` 讀成 `2` 的位址、`("a"|"b"|"c")` 讀成 `"a"` 的位址，**同一個成因，三筆全部作廢**。

**⟹ 於是 `serialize_union` 不推標記這件事，今天只有「讀碼」沒有「量測」。**
它仍然可疑（無標記、無長度前綴 ⟹ 框界由相鄰位元組決定），
**但可疑不是證據**，工單必須要求交付方對它做一次真的量測，
**而且不得用會對 union 分配的入口去量**。

## 6. 開卡前還沒量的（逐項列出，不以沉默代替覆蓋）

*   `Code` 的身分是 `format!("{:?}", expr)` ＝ **Rust 專屬格式** ⟹ 第二個實作算不出來。
    Inbox 已有同族一列（「commit 的位址算法是 Rust 專屬的」）。**未量它是否與同文字的字串相撞。**
*   `Thunk`（`0x17`）與 `Blur`（`0xFD`）今天從表層語法碰不碰得到，未量。
    `Range`（`0x18`）**碰不到**：〔量〕`1...3` 是 parse error（Inbox 已有一列）。
*   `AtomKind::TagStart`／`TagEnd` 被編成名字為 `"_"`／`"_|_"` 的 tag，未量是否與真 tag 相撞。
*   **紀元範圍**：語料、標準根、引擎測試裡各有多少 `r"`／`p"`／`u"`／`t"`／`b"`／`()` 值。
    **這一項必須由交付方量出來寫，不得只說「應該很少」。**
*   標準根含三個 `0xFF` 是 Q-047 的讀數，**本次未複驗**。

## 7. 這張卡需不需要裁定

**不需要。** 「該不該修」已由 `REAL_03` §6.7 第二條回答（v0.52.0 立）；
「怎麼修」是給每一種一個標記位元組，**而那正是這張表要寫的東西**。
O88（n/ 的浮點數是什麼）**不堵本卡**：`0x13` 那一列照現況寫，
並標明它與 §6.7 第二條相衝、待 O88。

**⚠ 一個該先被看見的交集**：本卡要補的 `0xFD #blur` 與 O88 的候選己
（Unum Type I 的 ubit ＝ 把「這是區間不是點」寫進值）指向同一件事的兩層。
今天不衝突，**但若 O88 取己，浮點數那一列會再動一次。**
