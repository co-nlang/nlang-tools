## 0. 判準

*   **一個判不出來的比對不是匹配**（`SPEC_08` §3.2.2 第 1 款：值語境遇到 `#blur`，結果就是那個 `#blur` 原樣傳出）。表對每一支分支，拿引數與模式交會；交會的結果在**模式有要求的坐標**上是視界——模式本身是視界、交會時燃料或深度耗盡、或引數在模式要求的那個欄位上是視界——那一支就**判不出來**：它是不是匹配不知道，所以整張表的答案也不知道，**答那個視界**。它的本體不是答案，它也不是「不匹配」。
*   **引數是載體**（§3.2.2 第 2 款）：引數帶著的視界，落在模式**沒有要求**的坐標上（模式那裡沒有這個鍵，或寫的是 `_`）時，比對照樣判得出來。
*   **兩支模式誰比較細，是表自己的簿記，不花燃料**（`SPEC_04` §6.5：`%fuel` 只在 force 點消耗；D113 的先例：宇宙自己的合併是簿記不是觀測）。一張判得出來的表，答案不因為它有幾支重疊的模式而變成視界。
*   不須裁。

## 1. 缺陷

〔量，`v0.119.0` 標籤建置；空目錄；`acc/q119/surfaces.py`、`scale.py`〕

*   **判不出來的比對被當成匹配**：`dispatch_morphism` 對每一支求「引數 ∧ 模式」，**只要不是衝突就收進匹配**（D117：做出衝突的才不匹配）。視界不是衝突，所以一支模式是視界的分支一律被收下，它的本體被當成答案：
    *   `({ /f: (x -> x == 0 ? 0 : /f (x - 1)), r: { @{ /f 5000 }: 1, @{ 5 }: 2, _: 7 } 5 }).r` ⟹ **`1`**——模式 `/f 5000` 是 `#blur #max_depth_exceeded`；真正匹配的 `@{ 5 }: 2` 整支消失；答案裡沒有任何視界的痕跡。
    *   同形：只有那一支（`1`）、旁邊一支不匹配的（`1`）、兩張表交會、具名的規則表 `/g`、箭頭的參數模式 `x @{ … } -> 1`、聯集引數、記錄模式的一個欄位是視界、`@int & (/f 5000)`、引數的欄位是視界而模式要求它、從記錄裡導航到表——全部答 `1`。
*   **從根上讀大表**：提交過的 `t: { @{ 0 }: 0 * 2, …, @{ N-1 }: (N-1) * 2, _: 0 }`，讀一次要對每一列各交會一次，每列約 5 單位燃料，2000 列起燃料在分派途中耗盡；耗盡之後的比對全是視界，全被收進匹配：
    *   2000 列：`_.t 2000`（只有 `_: 0` 匹配）⟹ **`0 | 528 | 1656 | 2538 | 3434`**——沒有 `#blur`，四個不在表裡這一格的數；`_.t 5` ⟹ `0 | 10 | 528 | 1656 | 3434 | #blur …`。
    *   4000 列：`_.t 5` ⟹ **`602 | 4920 | 6964 | 7670 | #blur …`**——連真答案 `10` 都不在裡面。
    *   同一張表直接求值 `({ … }) 5` 答 `#blur`：同一個值兩條路兩個答案。1900 列以下兩條路都答對。
*   **偵察時一度以為是另一件事**（留給你知道為什麼本卡只動分派）：「從根上讀大記錄後面的欄位燃料耗盡」那一列是**提交**把字面欄位在一份共用的燃料下逐一強制、用完之後把 `#blur` 存進根（`project_for_commit`）——那是另一個不變式，**另開一卡**（§6）。表的根在本卡的參考上與 v0.119.0 逐位元組相同，錯的聯集是讀的時候才產生的。

## 5. 必答（請在交付報告裡回答，逐題）

*   **Q1 一處**：你在哪裡判「判不出來」；表的施用還有沒有不經過那一處的入口（`read_branch` 導航讀分支、`%bodies` 多本體、舊引擎的 `%morphism` 表、內建）——逐一說明為什麼不必或怎麼處理。
*   **Q2 模式看不看**：你怎麼決定一個坐標「模式有要求」——尤其是模式的欄位還沒強制（thunk）、寫的是 `_`、在 local／型別軸上的情況；為什麼引數帶來、模式不看的視界不讓比對判不出來。
*   **Q3 簿記**：「誰比較細」不花燃料之後，它最壞的成本是多少、為什麼不會跑不完；深度耗盡時你怎麼處理。
*   **Q4 大表**：2000 列的表現在從根上讀答 `#blur #fuel_exhausted`——每一列各花多少燃料、花在哪幾步；其中有沒有不是 force 點的（這一題只要量與說明，**不要改**，見 §6）。
