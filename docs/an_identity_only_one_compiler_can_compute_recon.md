# 偵察：一個只有一個編譯器算得出來的身分

> 起因：v0.53.0 收弧後，`Code` 是 `REAL_03` §6.2 表上唯一沒有規範性酬載的一列。
> 前置裁定 **D71**（2026-09-19，`Code` 的身分是內涵的）已落地。
> 量測用 `v0.53.0` 標籤建置（`/home/gali/nlang-baselines/v0.53.0-verify`）。
> known-answer `~%Math./add (1,2)` → `3`／對照 `(1,3)` → `4`。

---

## 1. 一句主張

〔讀 `bn_serial.rs:87`〕`Value::Code` 的身分編碼是

```rust
buf.push(TAG_ATOM);
encode_string(&format!("{:?}", expr.without_spans()), buf);
```

`Expr` 是 `#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]`
⟹ **位址取決於一個 derive 出來的 Rust 除錯格式**。
**Rust 明文不保證該格式跨版本穩定** ⟹ 不只第二個實作算不出來，
**同一份程式碼換一個編譯器就沒有保證**。

## 2. 而 `Code` 是可達的，已經在耐久位元組裡

〔量〕帶 body 的態射提交後，物件裡逐字是

```
%code: { ~%__nlang_code: #true  ~%__nlang_expr: ~%Math./add (x, x) }
```

⟹ **耐久位元組存的是 `to_nlang`（正準 n/ 源碼），而位址是 `Debug` 算的**
——**同一個值，兩種呈現**。
⟹ 第二個實作拿著那些位元組**重算不出位址**，違反 **§6.6（讀路徑位址驗證）**。

**⚠ 兩處驗收方先前寫錯、已更正（留下）**：
(a) 「`Code` 是 §6.8.2 的阻塞」**錯**——〔量〕標準根物件 16,029 B 裡
`~%__nlang_code`／`~%__nlang_expr`／`ExprKind` **各 0 次**，其 255 個態射
**全是 `%builtin: "名字"`（一個字串）** ⟹ **`Code` 不進標準根**。
驗收方從「`0x10` 之下還有 `Code`」直接推到「標準根算不出來」，**中間那一步從來沒量**。
(b) 「今天表層碰不到 `Code`」**不準**——`~%Code./quote` 確實 `#missing_key`、`'(1)` 確實 parse error，
**但態射的 body 就是 `Code`**，而它會進倉。

## 3. 修法不得只是改用 `to_nlang`

〔引擎註解逐字，L2-65 已量〕`to_nlang` 在深左結合鏈上遞迴，
**約 10³ 層就爆掉 64 MiB 的 CLI 棧**。

〔量〕conformance **L2-65**（`65-blur-merge-caid-verbatim.n`）逐字是
**3999 個 `+` 的左結合鏈、16,044 B**，其 `out` 正是 `(big & { b: 1 }).%caid == big.%caid`
⟹ **那條鏈的 `%caid` 今天算得出來**（rc=0、`#true`，離開碼未經管線）。
⟹ **`to_nlang` 版本會在語料裡現成的一個向量上爆掉。**

> **⚠ 2026-09-19 驗收方就地更正 I3 的理由（交付指正，而它是對的）。**
> 上面那句「〔引擎註解，L2-65 已量〕`to_nlang` 在約 10³ 層就爆掉 64 MiB 的 CLI 棧
> ⟹ **『改用 `to_nlang`』會在語料裡現成的一個向量上爆掉**」——**後半句是假的**，
> 而前半句是**驗收方把一句程式註解當成量測寫上去的**（「已量」二字不是驗收方量的）。
>
> 〔驗收方自量，`v0.53.0` 標籤建置，離開碼未經管線〕**3999 層（＝L2-65 的深度）三條路都沒爆**：
> `--observe f`（走 `to_nlang`）rc=**0**、輸出 16,108 B；
> `identify_and_store f`（走 `Debug`）rc=**0**；`oo fmt` rc=**0**。
> **⟹ 交付說它重現不出來，是對的。**
>
> **⟹ 而往深處量，真正的形狀是另一件事**：20,000 層與 80,000 層時**兩條路都 rc=1**，
> 而錯誤是 **`Parse Error … #stack_overflow`** ——**剖析器的具名邊界先擋下來**（v0.18.0 的前置界），
> 不是序列化器爆棧、也不是宿主崩潰。
> ⟹ **在今天經由剖析器可達的深度區間裡，`to_nlang` 從來輪不到爆。**
>
> **I3 這條不變式本身仍然成立，但理由要換成這一句**：
> **身分編碼不得從一個 pretty-printer 繼承深度上限**，而**剖析器的界不是對序列化器的保證**
> ——語法樹也可以從倉讀回來或由程式建起來，那兩條路上沒有那道界。
> 〔交付採顯式堆疊，因此本條無論理由對錯都已滿足。〕

## 4. ⚠ 本卡沒有紅探針可寫，而這一點必須寫在最前面

核心缺陷是**跨實作／跨編譯器的可重算性**，而**一個二進位無法表現它**：

*   〔量〕`Expr { kind, span }` 兩個欄位，`without_spans()` 清掉 span
    ⟹ **Debug 是純結構的，沒有 to_nlang 看不見的隱藏欄位**
    ⟹ 「存進去再讀回來位址會變」**量不出來**（〔量〕`plain`／`chain`／`parens`／`nested`
    四種 body 提交後 `status`／`log` 皆 rc=0）。
*   兩種書寫法在 body 裡**分得開且都 round-trip**（D71 的依據），故那裡也沒有紅。

**⟹ 基線會是全綠。** 而「全綠不等於被檢驗過」——**一張探針基線全綠的卡，正是空洞交付最容易藏身的形狀**。
**故本卡的驗收不能靠探針，補償要求寫在工單 §4／§5**：
交付必須產出**一張規範性的 Expr 節點編碼表**（`REAL_03` §6.2 的同形），
而 I1 的探針**在修補回合寫**——等編碼被規範下來之後，才寫得出黃金向量。
**這是兩階段，不是偷懶，且理由是可檢查的：今天沒有東西可以當黃金值。**

## 6. 開卡前沒量的（不以沉默代替覆蓋）

*   **α-等價**：〔量〕`x -> add(x,x)` `6b39a51b…` 與 `y -> add(y,y)` `e09b9542…` 不同址，
    而 `=` 亦判 `#false` ⟹ **兩邊一致，不是違反**。「α-等價的態射是不是同一個值」**未裁**，Inbox 另列。

    ⟹ 與 D68 同形，**Inbox 另列，不在本卡**。

    ⟹ **同一個問題的另一半可能在那裡，未量**。工單指名要交付方回答。
