## 0. 判準（規格原文）

*   **規格沒有 `~%Json`／`~%Toml`／`~%Csv` 這一章**（`SPEC_09` 只在 §5.1.1 的鍵序表列出模組；驗收方收尾補寫）。依據是以下幾條，加上一條裁定：
*   **`SYNTAX_06` §4 #11 全引擎唯一等值**：`=` 是值的性質，不是來源的性質（#14「span 與符號拼寫不得影響任何語義判定」）——兩個 `=` 的值，經同一支內建，答同一個答案。字面寫出的 `{ a: 1 }` 與 `~%Json./parse` 讀回來的記錄 `=`，就必須寫成同一段文字。
*   **`SYNTAX_06` §4 #6 值語境統一律（G6）**：內建讀成值的運算元與清單元素讀它的值——混血讀 `%val`、聯集逐支（Q-112）、還不是值答 `_`（D119、D121）。一筆記錄就是以鍵為名的元素；序列化內建把每一個欄位讀成值寫出去。
*   **`SPEC_08` §3.2.2 第 1 款（G3）**：值語境讀到 `#blur` 就是答案，不得改鑄、不得寫成 `null`。
*   **D124**（2026-10-30 用戶裁定，甲）：`~%Csv./stringify` 的列是記錄時，第一列記錄的鍵依序寫成首行，每一列依那個鍵序寫值——`~%Csv./parse_with_headers` 的反函數；某列缺的鍵寫空格，首行沒有的鍵答 ⊥ `#conflict`。
*   **本意可循處**：`crates/interpreter/tests/csv_p47_test.rs` 的 `test_csv_stringify_roundtrip`（`"a,b\n1,2"` 經 `csv.parse` 來回）——它直接把清單交給內建，所以是綠的；從語言裡呼叫時引數是打包的 `{ 0: rows }`。`json_p33_test`、`pin_probe`（`~%Json./stringify lst` 寫出合法 JSON）同理只測了清單與原子。

## 1. 缺陷

〔量，`v0.113.0` 標籤建置；空目錄；`acc/q113/recon.py`、`recon2.py`（字串以 `"""…"""` 寫——n/ 的單行字串沒有 `\"` 跳脫）〕

*   **字面記錄的每一個欄位寫成 `null`**：`~%Json./stringify ({ a: 1 })` ⟹ `"{\"a\":null}"`；`({ a: "x", b: [1, 2] })` 全 `null`；巢狀、清單裡的記錄、混血欄位同。而 `~%Json./stringify (~%Json./parse ("""{"a": 1}"""))` ⟹ `"{\"a\":1}"`——兩個 `=` 的值寫出不同的文字。〔讀〕`nlang_to_json` 只看已強制的值，字面記錄的欄位是還沒強制的 thunk。
*   **TOML 同一個洞**：`~%Toml./stringify ({ a: 1 })` ⟹ ⊥ `#conflict`；`~%Toml./stringify (~%Toml./parse ("""a = 1"""))` ⟹ `"a = 1\n"`。
*   **CSV 印出 Rust 的內部結構**：`~%Csv./stringify ([["a", "b"], ["1", "2"]])` ⟹ `"Combo(ComboVal { data: {\"0\": Atom(Str(\"a\"), …` ——不論列是清單還是記錄、來自字面還是 `parse`。〔讀〕沒有拆開打包引數的第 0 格，整份清單被當成一列，每個子清單以 `{:?}` 印出。
*   **欄位讀成值的那一半**：聯集欄位 `{ a: 1 | 2 }` ⟹ `{"a":null}`、清單元素 `[1 | 2]` ⟹ `"[null]"`（Q-112 的登錄表沒有掃到這一支的元素）；燃料耗盡的視界欄位 ⟹ `null`；`{ a: _ }`、`{ a: @int }` ⟹ `null`。
*   **自我參照**：`x: { a: 1, b: x }` 再寫 `~%Json./stringify (x)` ⟹ `{"a":null,"b":null}`。
*   〔量〕經過坐標存下來的記錄，欄位在演化時已經強制，所以 `x: { a: 1 }`、`r: ~%Json./stringify (x)` 今天答對——同一個值，寫在一行裡與寫在坐標裡答案不同。
