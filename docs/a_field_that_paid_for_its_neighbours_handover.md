# 一個替鄰居付帳的欄位（Q-120）

探針：`crates/oo/tests/a_field_that_paid_for_its_neighbours_probe_test.rs`（不得修改）。

## 0. 判準

*   **一格存什麼、讀什麼、收下或拒絕什麼，不隨同一筆寫入裡有多少別的東西而變**（`SPEC_10` §2.3.1 D113 款：「一個座標存成視界，只能因為它自己的定義求值撞上視界；它存什麼、讀到什麼，收下或拒絕哪一筆寫入……不隨宇宙裡有多少別的座標……而變」）。記錄的欄位、清單的元素也是格。
*   **宇宙為自己的簿記去強制一個值時，每一格各自一份預算**：投影一次提交、判一筆寫入撞不撞、判一個成員是不是已在 HEAD、判一個定義要存配方還是答案——這些是宇宙自己的事，不是誰的觀測；它走過的每一格，花多少只算在那一格上。
*   **一個定義被算出來，仍是一次觀測，一份燃料**（D113 同款：「交會途中被強制的定義照常計費」）。上面那一條只管「格與格之間不互相分帳」，不讓任何一個定義多出燃料。
*   **宇宙自己的交會不花燃料**（D113）：判撞不撞、判在不在 HEAD 的那次交會。
*   不須裁。

## 1. 缺陷

〔量，`v0.120.0` 標籤建置；`acc/q120/recon.py`、`recon2.py`、`evo.py`、`call.py`、`d110.py`、`alias.py`；插桩 `q120-prof-base`（`check_resources` 依呼叫位置計數，第一次耗盡印呼叫鏈）〕

*   **提交把一個值的所有格放在一份燃料下強制**（`project_for_commit` 的原子／函式分支與一般分支，`force_recursive` 共用整次提交的 `ctx.fuel`，預設 10000，每格約 3）：
    *   `h: { k0: 0, …, k3999: 3999 }` 提交，**667 格存成 `#blur #fuel_exhausted`**，`_.h.k3999` 答視界（直接求值答 `3999`）；8000 欄 4667 格。字串、帶隱藏面向、清單裝著它、呼叫造的、之後再加一欄的，同。
    *   兩個 2000 欄記錄同一次提交 667 格，分兩次提交 0 格——**一格存什麼取決於同一次提交裡還有誰**。
    *   `local` 欄位與讀它的資料欄位 2000 欄存 1334 格、4000 欄 4000 格；記錄的清單 4000 個 2571 格。
    *   最後一欄是 `z: 1 & 2`：前面 499 欄時提交回報 `#conflict at h.z`，**前面 3999 欄時不回報**（讀它仍是 ⊥）。
*   **判撞不撞的交會計燃料**（`meet_clash`，演化時拒絕一筆寫入用的四處）：在已提交的 4000 欄記錄上寫 `h: { k3999: 7 }`——v0.120.0 收下（被上一條的視界蓋住），**修了上一條之後收下並把 ⊥ 存進歷史**；10、2100 欄具名拒絕 `#conflict at h.k…`。一個讀它的配方 `r: c` 在 16000 欄同（實值記錄的檢查一次收它整個大小的費用 16001）。
*   **判在不在 HEAD 的交會計燃料**（不帶 ctx 的 `Ouroboros::unify`：`injection_has_committable_content`、`head_if_it_holds`、`session_would_be_listed`、`injection_positions_equal`）：同一個 N 行的檔提交兩次，1900 行答 `already in HEAD <hash>`，**2100 行起答 `Nothing to commit`**。
*   **判存法的強制只有一份燃料**（`made_in_a_call`、`answer_syntax`；`evolve_field` 判「讀了宇宙沒有」的兩處）：
    *   呼叫造的記錄、最後一欄是捕捉了參數的函式（R-4：存配方）：1000 欄存 `(x -> { … }) 1`，**4000 欄存答案**、帶 `%closure` 快照。
    *   呼叫造的記錄、最後一欄讀宇宙的名字 `n`（D110：存配方）：1000 欄存配方，4000 欄存答案（讀數碰巧仍對，`z` 還是惰性的）。
*   **判一個配方「印出來讀回去是不是它」只有一份燃料**（`syntax_of` 在同一個 ctx 上強制兩次；`meet_coordinate` 判 D110 的兩處）：一筆寫入落在一個讀宇宙的欄位旁邊，被拒成 `#conflict at h`——
    *   `n: 5`、`h: { r: (500 欄 & 500 欄).k499 + n }` 提交後寫 `h: { z: 1 }`：**被拒**；100 欄收下；讀 `_.h.r` 答 `504`（讀得出來，判的時候卻算了兩次而用完）。
    *   `h: { k0: 0, …, k3999: 3999, z: n }` 提交後寫 `h: { w: 1 }`：**被拒**；10 欄收下。
    *   視界印不回語法 ⟹ `cannot_keep` 回 ⊥ ⟹ 拒絕：判不出來被當成衝突（與 Q-119 同一個錯，換了一個地方）。
*   **這些都隨位置與總數長，而且看起來像「慢」或「像樣的數」**：v0.120.0 上 Q-118 的「每 4 倍欄位至多 5 倍時間」守衛是綠的，**因為燃料用完的格根本沒有做**。

## 2. 依據；位址

*   `SPEC_10` §2.3.1 D113 款（上引）；`SPEC_04` §6.5（燃料只在 force 點消耗）；D46（構造不是觀測）；D110、R-4（存配方的判準）。規格不必改字——收尾時 D113 款補一句「宇宙為自己的簿記強制一個值時，每一格各自一份預算」並以本卡的數字當判例，屬編輯性。
*   **位址：小的寫入不動**。g2 釘了五顆根（v0.120.0 量得）；全樹沒有任何一支既有測試因本卡變紅，**沒有預先修訂**。大的寫入的根會動（原本存了視界的格改存真值；原本存答案的改存配方）。
*   **讀數會動**：每一格 `#blur #fuel_exhausted` 改答真值；提交多回報 ⊥；演化多拒絕寫入；兩次提交同一個檔改答 `already in HEAD`——破壞性條目，收尾時記進 `CHANGELOG`。
*   **有一格讀數會變差，而那是對的**（§3 M5 旁、§6）：呼叫造的 4000 欄記錄、最後一欄是閉包，之後再寫 `h: { z: 1 }`——v0.120.0 讀 `_.h.f 2` 答 `3`、`_.h.z` 答 `1`；本卡之後兩者都答 `#blur #fuel_exhausted`。原因：R-4 的判斷在 v0.120.0 因燃料耗盡而翻成存答案，碰巧繞過了之後那次交會；修好以後它和 1000 欄一樣存配方，兩筆寫入成為 `A & B` 的語法，讀它就是讀 `((x -> { … }) 1 & { z: 1 })`——**同一個式子就地直接求值也答視界**（4000 欄的交會在預設燃料下做不完，交會的成本模型，§6）。同理：呼叫造的 4000 欄記錄、最後一欄讀 `n`，之後再寫 `h: { w: 1 }`——v0.120.0 讀 `_.h.z`／`_.h.w` 答 `5`／`1`（D110 的判斷燃料用完、翻成普通交會、存答案），本卡之後存兩筆寫入的語法、讀它答視界。**兩格都是「判斷錯了，碰巧繞過成本模型」**。

## 3. 射程＝不變式（不是機制）

*   **M1 每一格存它自己**（r1，10 格）：4000／8000 欄原子、4000 欄字串、帶隱藏面向、清單裝著、呼叫造的、8 個巢狀 1000 欄、同一次提交兩個 2000 欄、已提交的 4000 欄再加一欄；對照 10 欄。每一格：提交成功、根裡 **0 處** `#fuel_exhausted`、頭／中／尾的讀數是真值。
*   **M2 ⊥ 照報**（r2）：最後一欄 `z: 1 & 2`，前面 499／3999／15999 欄，提交都回報 `#conflict at h.z`。
*   **M3 撞的照拒**（r3）：已提交的 10／2100／4000／16000 欄記錄上寫最後一欄的衝突值，演化 rc=1、具名 `#conflict at h.k…`、之後讀它是原值；讀它的配方 `r: c` 上 10／16000 欄同。
*   **M4 在 HEAD 的照說**（r4）：同一個 10／1900／2500／16000 行的檔提交兩次，第二次 rc=1、`already in HEAD` 且說出現在的 HEAD。
*   **M5 存法不看大小**（r5）：呼叫造、最後一欄是閉包的 1000／4000 欄記錄，最後一欄讀 `n` 的 1000／4000／16000 欄記錄——都存 `(x -> {`；讀數照答。同一種記錄（10／4000 欄）之後再寫 `h: { w: 1 }`，兩筆寫入仍存語法 `(x -> {`（Q-092；讀數不釘，§6）。
*   **M6 鄰居再貴，無關的寫入照收**（r6）：`n: 5`、`h: { r: (N 欄 & N 欄).k… + n }`，N＝100／500／1000，寫 `h: { z: 1 }` 收下、提交成功、`_.h.z` 答 `1`、`_.h.r` 答 `N+4`；`h: { 10／4000 欄, z: n }` 寫 `h: { w: 1 }` 收下、提交成功。
*   **另一半——觀測仍是一份燃料**（g1，11 格）：使用者寫的交會 `(1000 欄 & 1000 欄).k999` 照答 `#blur #fuel_exhausted`（100 欄照答 `99`）；`((4000 | 5) & { k0: _ }).k3999` 照答視界；直接求值 4000 欄照答 `3999`；`/f 5000` 照答深度視界；**一個存下的配方讀起來等於就地重讀**（4000 欄別名寫一筆一致的值之後，`_.r.k3999` 與 `(_.c & { k3999: 3999 }).k3999` 同答視界）；**一個在宇宙的走訪裡被算出的定義仍只有一份燃料**：`z: (4000 欄 = 4000 欄) & #false` 提交不回報 ⊥、讀 `z` 答燃料視界。
*   **另一半——小的根不動**（g2，五顆）。
*   **上一張卡學到的，逐條過**：
    *   不變式要在所有路徑都經過的那一處判（Q-092）：「每一格各自一份預算」**不要在各個入口各補一次**，要在走訪本身；你的做法若不在一處，寫明你怎麼證明沒有漏掉的入口（8.4 Q1）。驗收方的反查方法在 §7，請照做一次並報告。
    *   從計費點往上反查，不從入口往下找（Q-094）：本卡的修補點大多是用插桩從 `check_resources` 的耗盡往上找到的（另兩處是對著不變式造格時量到的，§7 錯誤 (5)），r1～r6 覆蓋的只是其中的形狀。
    *   規模格比兩個大小，讀數比真值，不比「看起來像樣」（Q-119）；**一個守衛綠，要問它是不是因為工作沒做完才綠**（本卡：Q-118 的線性守衛）。

## 5. 必答（請在交付報告裡回答，逐題）

*   **Q1 一處**：你在哪裡讓「每一格各自一份預算」生效；宇宙為自己強制一個值的入口還有哪些（提交投影、演化的拒絕檢查、R-4、D110、`status`、`refine`、`squash`、gc、`oo test`……）——逐一說明經不經過那一處、不經過的為什麼不必。附上你的反查（§7 的方法或你自己的）的結果。
*   **Q2 定義的邊界**：走訪中遇到一個還沒算出的定義時，你怎麼讓它只有一份燃料；為什麼 g1 的 `z: (4000 欄 = 4000 欄) & #false` 仍答視界。
*   **Q3 免費的交會**：哪些交會改成不花燃料；你怎麼確定沒有連帶改到交會的規則（D118 有好幾條規則看「這是不是宇宙自己的寫入」）。
*   **Q4 判不出來的比對**：`meet_coordinate`／`syntax_of` 判不出來（燃料或深度用完）時你怎麼處理——為什麼不是衝突；你的做法下還有沒有「視界 ⟹ `cannot_keep` ⟹ ⊥」這條路。
*   **Q5 成本**：每一格一份預算之後，一次提交最壞花多少；以 4000、16000 欄量提交與演化的時間，並與 v0.120.0 比（v0.120.0 的數字是做到一半就停的數字，比的時候寫明）。

## 6. 明文不在射程內

*   **交會的成本模型**：使用者寫的 `&` 每合一欄扣 5，兩個 1000 欄記錄的交會直接求值就答視界；存下的 `A & B` 配方讀起來同。本卡不改（D110：存下的配方讀起來等於就地重讀）。§2 那一格變差的讀數屬於這裡，與「一次查表對每一列各付燃料」同列 Inbox。
*   **`r: /f 5000` 存成視界**（D110 說讀了宇宙的純衍生定義存配方）：〔量〕那是**演化**存的（`universe.rs` 的 `recipe_instead_of_pure_answer` 把 `Blur` 與 ⊥ 一起原樣留下），不在任何走訪裡、與格的多寡無關——另一個不變式，另開 Inbox。
*   **同一個式子的燃料因寫在哪裡而不同**：〔量，v0.120.0 與參考同〕`(1000 欄 & 1000 欄).k999` 在頂層答視界，寫成 `({ r: (…) }).r` 或 `({ m: … }).m.k999` 答 `999`。成本模型的另一面，另開 Inbox。
*   **寫在一個讀數是視界的配方上的值被無聲吸收**：〔量，兩版同〕`c: { 1000 欄 }`、`r: (c & { 1000 欄 }).k999` 之後寫 `r: 7`：演化收下、提交答 `already in HEAD`、`_.r` 仍是視界。視界吸收寫入是不是對的，另開 Inbox。
*   **`sub_context` 每次深拷貝 `ctx`**（`lib.rs` 的 F2 註解）：本卡只動會隨走訪長大的那一項（見 §7 參考）；其餘不動。
*   N 個頂層函式坐標演化 N²（既有 Inbox）。

## 7. 探針完整性（沒有 `#[ignore]`：紅就是紅）

*   紅探針 r1～r6 基線必須是紅的；**你可以讓它們變綠，不得改寫它們的宣稱。** `rustfmt` 不得掃探針檔。每個 `oo` 行程 3 GB 位址空間上限、90 秒即殺；子行程的輸出邊跑邊讀。
*   〔驗收方校準〕**兩極皆做**：
    基線 v0.120.0（dev `f3e1eaf` 加本探針）：**2 綠 6 紅**——r1 錯 16 處（大的形狀全錯；10 欄與 8×1000 巢狀對）、r2 錯 4000／16000、r3 錯 4000／16000／別名 16000（10、2100 對）、r4 錯 2500／16000、r5 錯 5 處（4000 欄閉包、讀 `n` 的 4000／16000、之後寫 `w` 的 4000 被拒且存答案）、r6 錯 500／1000 與 4000 欄寫 `w`（100、10 對）；g1、g2 綠。
    參考實作（`q120-ref`，相對 dev 動 `lib.rs`、`unify.rs`、`universe.rs`）：探針 **8／8**（49.2 秒）；全樹 **310 個目標（`Running` 行）、2928 通過、0 失敗**（v0.120.0 的 309／2920 加本探針一個目標八支）；conformance **213／213**（空目錄前後 0）；交叉編譯 0 error。Q-118 的四種形狀（讀外層、local、記錄的清單）4000 欄演化 0.90～1.53 秒、提交 2.35～4.20 秒，每 2 倍約 2 倍。
