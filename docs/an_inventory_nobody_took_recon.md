## 1. 標準根今天是什麼（實測，非讀碼）

以 `root_with_system()` 遞迴展開全部五軸（`fields()`：data／rules／types／meta／
system），共 **308 列**。頂層 **30 項**：

| 軸 | 數量 | 內容 |
| :--- | ---: | :--- |
| rules (`/`) | **1** | `/add` |
| types (`@`) | **3** | `@list`、`@option`、`@result` |
| system (`~%`) | **26** | Math, Cond, List, String, Time, Bytes, Regex, Json, Io, Env, Process, Path, Query, Diff, Set, Stat, Csv, Url, Toml, Discovery, Effect, Reflection, Complex, Engine, Official, Config |
| data | 0 | — |
| meta (`%`) | 0 | — |

態射葉節點 **256 個引用、251 個相異 builtin id**（與 O56 當時所量一致）。

**整根 digest：`hash:sha256:v1:65f52e2d…`**——與 REAL_03 §6.8 判例裡引擎 v0.21.0
所印的 `65f52e2d…` **逐字相同**。⟹ 標準根**自 v0.21.0 起四個 minor 版未動**。

### 1.1 承重量測：CAID 與插入順序無關

`bn_serial.rs:273` 的 `entries.sort_by`：先按軸優先序，再按 key 字典序。實測——

```
ORDER A (alpha,beta,gamma) : f5c2974abb16df16…
ORDER B (gamma,alpha,beta) : f5c2974abb16df16…
```

⟹ **一張表就足以決定 digest**。規格不必指定建構順序，也不必把某個實作吐出的
位元組奉為正典。這正面支撐 §6.8.2「不得是某個實作建構順序所留下的結果」——
**順序根本不在身分裡**。

### 1.2 引擎已經有一張逐模組 CAID 表

`crates/interpreter/src/genesis.rs`：**26 個 `SEED_*` 常數**，`genesis_test.rs`
的 `seed_caids_are_stable` 逐一比對、今日全綠，檔頭寫著 `DO NOT modify`。

覆蓋 30 個頂層項中的 **26** 個。**未覆蓋 4 個**：`/add`、`~%Effect`、`~%Engine`、
`~%Official`。

⟹ **規格要的東西，引擎已經算出來並鎖住了四個版本**；缺的是「誰說它是標準的」。

## 3. `/add` 孤兒（對 v0.24.0 重現）

```
/add: x -> x          → Error: Evolution Conflict: #missing_key at /add.%builtin
/sub: x -> x          → 成功
/myop: x -> x         → 成功
```

反向也一樣不對稱：

```
/add 1 2   → 3
/sub 5 2   → _        （開放缺席，靜默）
1 + 2      → 3
~%Math./add 1 2 → 3
```

⟹ **`/add` 是全語言唯一一個「裸呼叫得動、卻不能在自己的宇宙頂層定義」的名字。**
其他 47 個 `~%Math` 態射兩件事都做不到／都做得到（裸呼回 `_`，可自由定義）。

來源：`git log -S'fields.insert("/add"'` → **`71177b7` Genesis commit of "oo"**。
它是標準根裡最老的一行，比 `~%Math` 成為模組還早。**沒有任何註解說明為何它在頂層。**
O52 的明文債逐字要求「`/add` 孤兒與三個型別都須有人明說為何在裡面」。

## 4. 型別：SPEC_09 §2.1 與 §2.5 為何不一致（推翻前次記載）

§2.5 的既有註記寫「〔量〕其創世型別軸只兌現 `list`／`option`／`result` 三筆，其餘
`@name` 憑名字現造——`@zzz` 與 `@int` 印出的形逐字同構」。

**印出的形確實同構，行為完全不同。**〔量 v0.24.0〕

| 探針 | `@int` | `@zzz` |
| :--- | :--- | :--- |
| `5 & @T` | `5` | `5` |
| `"s" & @T` | `_\|_ #conflict "Value is not an integer"` | `"s"` |

`@int` **不在標準根裡，卻照樣執法**。執法者是 `type_constraint.rs:22`
`from_name()` 的一張**保留名表**，與標準根是兩套機制。

⟹ **兩表不一致的真正原因不是「有一表沒做完」，而是它們在回答兩個不同的問題，
而沒有人說過這件事**：

| 族群 | 成員 | 住哪 | 行為 |
| :--- | :--- | :--- | :--- |
| **標準根型別**（3） | `@list` `@option` `@result` | 標準根 types 軸 | 帶代數介面（`%fmap`／`%some`／`%ok`…），且執法 |
| **保留內建名**（12） | any, num, complex, float, int, str, bool, list, combo, morphism, option, result | `type_constraint.rs`，**不在標準根** | 執法（`@any` 全收） |
| **使用者名義標籤** | `@zzz`、`@MyType` | 哪裡都不住 | **惰性，不執法** |

§2.1 的樹 ≈ 第 2 族，§2.5 的表 ≈ 第 1 族 ∪ 第 2 族的一部分。**兩者從來就不該相同。**

### 4.1 順帶量到的缺陷：`@u8` 什麼都不擋

§2.1 把 `@u8..@u256, @i8..@i256` 寫成「固定寬度投影，**FFI 邊界**」。實測：

```
300 & @u8  → 300
-1  & @u8  → -1
"s" & @u8  → "s"
```

`from_name("u8")` 落到 `Unknown` ⟹ 惰性標籤。`super_parent()` 另有一條
`is_fixed_width_int_name` 分支把它掛到 `int` 底下，**但那只影響 `%super` 反映欄，
不影響執法**。同族還有 `@unit`／`@record`／`@type`／`@caid`——`super_parent` 認得，
`from_name` 不認得，故四者皆惰性（`"s" & @unit` → `"s"`）。

⟹ **規格宣告為 FFI 邊界的區間約束，今天一個都不擋。** 這不是本弧的射程；已記 Inbox。

## 5. 所以本弧要裁什麼

§6.8.2 第一條 MUST 要求「規格定義的具體值」。上面的量測把它拆成三個互相獨立的
裁定，**任一個都會移動或不移動 `65f52e2d…`**：

### R1 標準根的範圍：26 個模組裡哪些是標準的？

§6.8.2 第四條已裁「**實作不得自行擴充**（MUST NOT）」。而〔量〕引擎的標準根裡
有 14 個模組、181 個態射是規格從未提過的。**這兩件事今天不能同時為真。**

它是「引擎的鍋」還是「規格的鍋」——**兩者皆非**：這是一個從未被裁的問題，
在裁定之前，任何一方都還沒有做錯。

| | 主張 | digest | 代價 |
| :-- | :--- | :--- | :--- |
| **(a)** | 26 個全是標準；規格把已出貨者寫下來，MUST NOT 從此只約束**未來新增** | **不動** | 規格要新增約 181 個名字的條文；7 個模組今天連一句話都沒有 |
| **(b)** | 只有規格已描述者是標準，其餘搬出標準根 | **移動** | 「搬去哪」是一個尚不存在的機制；既有倉全靠 v0.23.0 的多重具備活著 |
| **(c)** | 分層：Level 2 必備核心 ＋ Level 3 全集，各公佈一個 digest | **兩個** | **與 O52 直接衝突**（「標準根是一個東西，一個 digest」），須先撤 O52 |

### R2 `/add` 孤兒

| | 主張 | digest |
| :-- | :--- | :--- |
| **(a)** | **移除**：rules 軸清空，`/add` 只住 `~%Math` | 移動 |
| **(b)** | 保留，並把 `~%Math` 全部 48 個都掛上頂層 | 移動（大） |
| **(c)** | 保留 `/add`，規格明說為何 | 不動 |

(b) 會把「使用者不能定義這個名字」的問題乘以 48。

### R3 型別的世界觀（§4 的三族群要不要入憲）

| | 主張 |
| :-- | :--- |
| **(a)** | 明文承認三族群：§2.1 ＝保留名（執法），§2.5 ＝標準根型別（帶介面），其餘名義開放 |
| **(b)** | 封閉清單：§2.1 樹裡的名字全部都要在標準根裡有具體值 |

(b) 會把 `@int`／`@bool`／固定寬度整數全部搬進標準根 ⟹ digest 大幅移動，且與
「標準根型別＝帶代數介面者」的現有形狀衝突。

### R4 公佈形式（建議，非提問）

**表在 SPEC_09（規範），CAID 由規格公佈。** 依 §1.1，BN/ 排序使表足以決定 digest；
採「repo 裡放一份正典位元組」則等於把規格的值交給某個實作的輸出去定義，正是
§6.8.2 第一條 MUST 所禁。表須固定三件事：**每個 key 落在哪個軸**、**每個態射的
耐久形**（`{ %morphism: #true, %builtin: "<id>" }`）、**每個 builtin id 的字串**。
