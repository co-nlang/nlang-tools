# 偵察：一個它自己還沒蓋完的 store

**日期**：2026-09-12（v0.49.0 切版之後，Ready 空）
**起因**：`an_authority_you_could_delete_probe_test::r4_two_concurrent_discharges_both_survive`
在全跑裡偶發變紅。驗收方於 v0.49.0 收弧時把它**改判為「疑似 Q-040 殘留缺陷」**。
**本次量測推翻該改判。** 見 §5。

---

## 1. 量測器與 known-answer

三支，全部在會話 scratchpad，不進倉：

* `r4probe`（`rustc -O`，只用 std）——逐字照抄探針 R4 的形狀，**但保留兩個
  `evolve` 的離開碼與 stderr**（探針把它們送進 `Stdio::null()`）。
* `race`（同上）——泛化成「在一個全新工作區裡並行跑任意兩個 `oo` 子命令」，
  按第一行輸出把非零離開分類計數。
* `r4_harness.sh`——最早的 bash 版，**已作廢**：它的 subshell fork 慢到把窗口關上
  （100/100 全過）。留在此處是因為它是本次「未重現 ≠ 不存在」的第一個實例。

**known-answer（每支都先過）**：
* `solo`：只 discharge `#io`，`commit --grant effect_override:io` → **rc=0**（5/5）。
* `seq`：循序 discharge `#io` 與 `#nondet`，同一個 grant 提交 → **rc=1**（20/20）。

⟹ 閘是活的，量測器碰得到它。

## 2. 首要發現：紅的不是 R4 的斷言，是它的 REACH 守衛

release 建置、隔離重跑 **30 次**（＝300 對並行）：**15 紅**。
**15/15 全部倒在同一行**，一次都不是那條性質斷言：

```
panicked at …an_authority_you_could_delete_probe_test.rs:234:9:
assertion `left == right` failed: round 0: REACH: both landed
  left: 1   right: 2
```

⟹ **探針從來沒走到它要測的性質。** 而 R4 把兩個 `evolve` 的輸出丟掉了，
所以「為什麼只落地一顆」這件事，在探針裡是看不見的。

## 3. 把丟掉的那一半撿回來

保留 stderr 之後，輸家每一次都逐字說了同一句話：

```
evolve[0] rc=0
evolve[1] rc=1
  Error: cannot determine this store's object encoding:
         `.oo/objects.format` is absent; refusing to open
```

**不是「共用格子掉了一個寫入者」**（那是 Q-040 的病，探針註解描述的也是那個）。
**是 `.oo` 的自動初始化不是原子的。**

### 3.1 機制（`crates/interpreter/src/storage.rs:298`–`319`）

```rust
let new_store = !oo.join("format").exists()      // ← (0) 判別
    && !oo.join("HEAD").exists()
    && !has_cas_objects(&oo.join("objects"));
if new_store {
    fs::create_dir_all(&oo)?;
    atomic_write(&oo.join("format"),         "layout=5\n")?;   // (1)
    atomic_write(&oo.join("objects.format"), "encoding=5\n")?; // (2)
} else {
    Self::ensure_format(base_dir)?;   // 讀「兩份」宣告，缺一即 bail
}
```

**每一格都是原子的（rename），兩格合起來不是。** 第二個行程在 (1) 與 (2) 之間
問 (0)：`format` 在了 ⟹ 判定「這是別人既有的 store」⟹ 走 else ⟹
`ensure_format` 讀得到 `format`、讀不到 `objects.format` ⟹ 拒絕開啟。

**一句話**：**判別「這是不是別人的 store」的那個問題，讀的是它自己等一下要寫的
第一個檔案。**

### 3.2 這是 v0.43.0 引進的，而且只有一行

〔量，真標籤二進位，`status ‖ status`，各 100 回合，皆在 tmpfs〕

| 版本 | 非零離開 | `.oo/objects.format` |
| :-- | --: | :-- |
| v0.40.0 | **0** | 有 |
| v0.41.0 | **0** | 有 |
| v0.42.0 | **0** | 有 |
| v0.43.0 | **4** | 有 |
| v0.44.0 | **8** | 有 |
| v0.46.0 | **7** | 有 |
| v0.48.0 | **3** | 有 |
| v0.49.0 | **6** | 有 |

⟹ **拆成兩份宣告本身不是成因**（v0.40–42 也有兩份而 0/300）。
〔讀，比對 v0.42.0 與 v0.43.0 的 `init` 原始碼〕**差一行**：v0.43.0 在
`new_store` 前面加上 `!oo.join("format").exists() &&`。v0.42.0 的判別式只看
`HEAD` 與 CAS 物件——**兩者在初始化窗口裡誰都沒寫**，所以兩個行程一致判定
「新 store」、各自冪等地寫下同樣的兩行，無害。

**⚠ 那一行不是寫錯的，它有正當理由**，就在它自己上面的註解：先前的引擎可能
staged 過 injections 而從未寫下 HEAD 或 CAS 物件；把那種倉當成新的，會**只因為
打開它就偷偷推進 layout**，繞過明示的遷移閘。⟹ **修法不得只是把那一行拿掉。**

## 4. 射程有多大

〔量，v0.49.0 標籤二進位，全新工作區，各 100 回合，tmpfs〕

| 並行的兩個命令 | 非零離開 |
| :-- | --: |
| `evolve ‖ evolve` | 5 |
| `evolve ‖ status` | 5 |
| `status ‖ status` | 6 |
| `log ‖ log` | 8 |
| `status ‖ log` | 11 |
| 〔對照〕先跑一次 `status` 建好 store，再 `evolve ‖ evolve` | **0** |
| 〔對照〕先建好 store，再 `status ‖ status` | **0** |

三件事：

1. **與 `evolve` 無關，與寫入無關。** 兩個**唯讀**命令並行，其中一個會 rc=1 死掉，
   而它們兩個都沒有要寫任何東西。
2. **對照組把成因釘死在初始化窗口**：store 已存在時 0/200。
3. **使用者沒有辦法先把它蓋好**——`oo` 沒有 `init` 子命令（`--help` 全列已查），
   store 一律自動建立。⟹ **這個窗口是不可迴避的。**
   ⟹ 直接抬高既有 Inbox 那一列（唯讀命令仍偷偷 init）的份量：
   它不再只是「形狀不乾淨」，它是這個競態的唯一入口。

### 4.1 為什麼一直沒被看見：檔案系統

〔量，同一支量測器、同一個二進位，只換根目錄〕

| 根目錄 | 檔案系統 | 回合 | 失敗 |
| :-- | :-- | --: | --: |
| `/tmp` | **tmpfs** | 100 | 7 |
| `/tmp` | tmpfs | 100 | 6 |
| 會話 scratchpad（`/`） | **ext4** | 200 | 0 |
| 會話 scratchpad | ext4 | 200 | 0 |
| 會話 scratchpad | ext4 | 100 | 0 |

⟹ **ext4 上 500 回合零次，tmpfs 上約 6%。** 而 `ScratchDir` 逐字用
`std::env::temp_dir()`，本機 `/tmp` 是 tmpfs ⟹ **探針剛好落在唯一看得見它的
地方**。**在 ext4 上跑 CI 的人永遠不會看到這個缺陷。**

〔算式對得上〕每對約 6% ⟹ 一次執行 10 回合至少紅一次的機率
`1 − 0.94¹⁰ ≈ 46%`；實測 15/30 ＝ 50%。**與 §2 的分母一致。**

## 5. 更正：這不是 Q-040 的殘留缺陷

驗收 v0.49.0 時，驗收方把這支 flake 改判為「疑似 Q-040 殘留缺陷（性質已裁、
只是沒有在並行下被兌現）」。**該改判是錯的。**

〔量，合計三批：ext4 200 ＋ tmpfs 100 ＋ ext4 workspace 建置 100 ＝ 400 回合〕
其中 **393 回合兩顆都落地**，這 393 回合的
`commit --grant effect_override:io` **全部 rc=1**，逐字具名拒絕。
**零個反例。** ⟹ **Q-040 的修補（意圖與值同住不可變成員、提交取聯集）
在並行下站得住。**

那 7 個 rc=0 的回合，**引擎是對的**：只有一顆 injection 落地（`#io` 那顆），
而操作者持有的 grant 正好覆蓋它 ⟹ 提交本就該成功。**探針的 REACH 守衛
做對了它該做的事**——它拒絕把那個 rc=0 讀成一個性質違反。

⟹ **這支探針沒有壞。** 壞的是它腳下的那塊地，而它的守衛正是唯一報出這件事的東西。
**⚠ 不要把 REACH 守衛拿掉，也不要 retry 掉它**——那會把一支誠實的探針換成一支空洞的綠，
並且是本專案第二次面對同一個誘惑（第一次是 `advert_persistence` 的桶溢出守衛）。

## 6. 這是誰的鍋，以及要不要裁定

**引擎的鍋，而且修補這一格不需要裁定。** 沒有任何條文規定 `new_store` 該怎麼問；
也沒有任何合理讀法會贊成「在一個空目錄裡並行跑兩個 `oo status`，其中一個死掉」。

**但要與 Q-016b 分清楚。** Q-016b（並行提交該收斂還是該合法分叉）**是未裁的語義題**。
本列**不碰語義**：兩個行程對這個 store 的宣告本來就沒有分歧，
分歧只發生在「其中一份宣告還沒落地」的那幾微秒。

### 6.1 不變式（不是機制）

**任何時刻，一個並行的觀察者對 `.oo` 的宣告只能看見兩種狀態之一：
「還沒有 store」，或「一份完整的宣告」。不得存在一個中間狀態，讓觀察者把
「正在被建立」讀成「既有，但宣告不全」。**

### 6.2 而它是 v0.49.0 那則判例的第三個實例

`REAL_03` §6.6 的 v0.49.0 新判例逐字是：`Path::exists()` 在 EACCES 回 false
⟹ **不透明**被壓成**不存在**，而且「這不是有人決定要壓平，是一個看起來無害的
前置檢查替他決定的」。

本列是同一個形狀的第三次：`!oo.join("format").exists()`
⟹ **「尚未」被壓成「沒有」**。

⟹ **附帶一個規格問句（需裁定，不擋修補）**：§6.6 今天要求「存在／不存在／不透明」
三者可分。**有並行寫入者時，「不存在」不是一個答案而是兩個**（沒有人要建 / 有人正在建）。
這要不要成為第四個必須可分的結果，是一則裁定；**本列的修補不等它**。

## 7. 建議

1. **開一張不需裁定的卡**修 §6.1 的不變式（`.oo` 宣告窗口原子化）。
   分母的參考值：修完之後，§4 那張表的六個組合都要 0/100 **在 tmpfs 上**，
   且既有的 legacy conflated store（`.oo/format` ＝ 裸數字、無 `objects.format`）
   仍須走 `ensure_format` 的舊枝——**這一格是那一行當初被加上去的理由，
   不得因為修競態而回歸。**
2. **R4 的 REACH 守衛不動。** 修完之後它自然不再開火；若日後仍開火，
   那是新的成因，應該再被聽見一次。
3. §6.2 的規格問句進 `STATUS` 的 O 帳，等排序。
