# 偵察：一個它自己還沒蓋完的 store

**日期**：2026-09-12（v0.49.0 切版之後，Ready 空）
**起因**：`an_authority_you_could_delete_probe_test::r4_two_concurrent_discharges_both_survive`
在全跑裡偶發變紅。驗收方於 v0.49.0 收弧時把它**改判為「疑似 Q-040 殘留缺陷」**。
**本次量測推翻該改判。** 見 §5。

---

## 1. 量測器與 known-answer

三支，全部在會話 scratchpad，不進倉：

* `r4probe`（`rustc -O`，只用 std）——逐字照抄探針 R4 的形狀，**但保留兩個
  `evolve` 的離開碼與 stderr**（探針把它們送進 `Stdio::null()`）。
* `race`（同上）——泛化成「在一個全新工作區裡並行跑任意兩個 `oo` 子命令」，
  按第一行輸出把非零離開分類計數。
* `r4_harness.sh`——最早的 bash 版，**已作廢**：它的 subshell fork 慢到把窗口關上
  （100/100 全過）。留在此處是因為它是本次「未重現 ≠ 不存在」的第一個實例。

**known-answer（每支都先過）**：
* `solo`：只 discharge `#io`，`commit --grant effect_override:io` → **rc=0**（5/5）。
* `seq`：循序 discharge `#io` 與 `#nondet`，同一個 grant 提交 → **rc=1**（20/20）。

⟹ 閘是活的，量測器碰得到它。

## 2. 首要發現：紅的不是 R4 的斷言，是它的 REACH 守衛

release 建置、隔離重跑 **30 次**（＝300 對並行）：**15 紅**。
**15/15 全部倒在同一行**，一次都不是那條性質斷言：

```
panicked at …an_authority_you_could_delete_probe_test.rs:234:9:
assertion `left == right` failed: round 0: REACH: both landed
  left: 1   right: 2
```

⟹ **探針從來沒走到它要測的性質。** 而 R4 把兩個 `evolve` 的輸出丟掉了，
所以「為什麼只落地一顆」這件事，在探針裡是看不見的。

## 3. 把丟掉的那一半撿回來

保留 stderr 之後，輸家每一次都逐字說了同一句話：

```
evolve[0] rc=0
evolve[1] rc=1
  Error: cannot determine this store's object encoding:
         `.oo/objects.format` is absent; refusing to open
```

**不是「共用格子掉了一個寫入者」**（那是 Q-040 的病，探針註解描述的也是那個）。
**是 `.oo` 的自動初始化不是原子的。**

### 3.1 機制（`crates/interpreter/src/storage.rs:298`–`319`）

```rust
let new_store = !oo.join("format").exists()      // ← (0) 判別
    && !oo.join("HEAD").exists()
    && !has_cas_objects(&oo.join("objects"));
if new_store {
    fs::create_dir_all(&oo)?;
    atomic_write(&oo.join("format"),         "layout=5\n")?;   // (1)
    atomic_write(&oo.join("objects.format"), "encoding=5\n")?; // (2)
} else {
    Self::ensure_format(base_dir)?;   // 讀「兩份」宣告，缺一即 bail
}
```

**每一格都是原子的（rename），兩格合起來不是。** 第二個行程在 (1) 與 (2) 之間
問 (0)：`format` 在了 ⟹ 判定「這是別人既有的 store」⟹ 走 else ⟹
`ensure_format` 讀得到 `format`、讀不到 `objects.format` ⟹ 拒絕開啟。

**一句話**：**判別「這是不是別人的 store」的那個問題，讀的是它自己等一下要寫的
第一個檔案。**

### 3.2 這是 v0.43.0 引進的，而且只有一行

〔量，真標籤二進位，`status ‖ status`，各 100 回合，皆在 tmpfs〕

| 版本 | 非零離開 | `.oo/objects.format` |
| :-- | --: | :-- |
| v0.40.0 | **0** | 有 |
| v0.41.0 | **0** | 有 |
| v0.42.0 | **0** | 有 |
| v0.43.0 | **4** | 有 |
| v0.44.0 | **8** | 有 |
| v0.46.0 | **7** | 有 |
| v0.48.0 | **3** | 有 |
| v0.49.0 | **6** | 有 |

⟹ **拆成兩份宣告本身不是成因**（v0.40–42 也有兩份而 0/300）。
〔讀，比對 v0.42.0 與 v0.43.0 的 `init` 原始碼〕**差一行**：v0.43.0 在
`new_store` 前面加上 `!oo.join("format").exists() &&`。v0.42.0 的判別式只看
`HEAD` 與 CAS 物件——**兩者在初始化窗口裡誰都沒寫**，所以兩個行程一致判定
「新 store」、各自冪等地寫下同樣的兩行，無害。

**⚠ 那一行不是寫錯的，它有正當理由**，就在它自己上面的註解：先前的引擎可能
staged 過 injections 而從未寫下 HEAD 或 CAS 物件；把那種倉當成新的，會**只因為
打開它就偷偷推進 layout**，繞過明示的遷移閘。⟹ **修法不得只是把那一行拿掉。**

## 4. 射程有多大

〔量，v0.49.0 標籤二進位，全新工作區，各 100 回合，tmpfs〕

| 並行的兩個命令 | 非零離開 |
| :-- | --: |
| `evolve ‖ evolve` | 5 |
| `evolve ‖ status` | 5 |
| `status ‖ status` | 6 |
| `log ‖ log` | 8 |
| `status ‖ log` | 11 |
| 〔對照〕先跑一次 `status` 建好 store，再 `evolve ‖ evolve` | **0** |
| 〔對照〕先建好 store，再 `status ‖ status` | **0** |

三件事：

1. **與 `evolve` 無關，與寫入無關。** 兩個**唯讀**命令並行，其中一個會 rc=1 死掉，
   而它們兩個都沒有要寫任何東西。
2. **對照組把成因釘死在初始化窗口**：store 已存在時 0/200。
3. **使用者沒有辦法先把它蓋好**——`oo` 沒有 `init` 子命令（`--help` 全列已查），
   store 一律自動建立。⟹ **這個窗口是不可迴避的。**
   ⟹ 直接抬高既有 Inbox 那一列（唯讀命令仍偷偷 init）的份量：
   它不再只是「形狀不乾淨」，它是這個競態的唯一入口。

### 4.1 為什麼一直沒被看見：檔案系統

〔量，同一支量測器、同一個二進位，只換根目錄〕

| 根目錄 | 檔案系統 | 回合 | 失敗 |
| :-- | :-- | --: | --: |
| `/tmp` | **tmpfs** | 100 | 7 |
| `/tmp` | tmpfs | 100 | 6 |
| 會話 scratchpad（`/`） | **ext4** | 200 | 0 |
| 會話 scratchpad | ext4 | 200 | 0 |
| 會話 scratchpad | ext4 | 100 | 0 |

⟹ **ext4 上 500 回合零次，tmpfs 上約 6%。** 而 `ScratchDir` 逐字用
`std::env::temp_dir()`，本機 `/tmp` 是 tmpfs ⟹ **探針剛好落在唯一看得見它的
地方**。**在 ext4 上跑 CI 的人永遠不會看到這個缺陷。**

〔算式對得上〕每對約 6% ⟹ 一次執行 10 回合至少紅一次的機率
`1 − 0.94¹⁰ ≈ 46%`；實測 15/30 ＝ 50%。**與 §2 的分母一致。**

## 5. 更正：這不是 Q-040 的殘留缺陷

驗收 v0.49.0 時，驗收方把這支 flake 改判為「疑似 Q-040 殘留缺陷（性質已裁、
只是沒有在並行下被兌現）」。**該改判是錯的。**

〔量，合計三批：ext4 200 ＋ tmpfs 100 ＋ ext4 workspace 建置 100 ＝ 400 回合〕
其中 **393 回合兩顆都落地**，這 393 回合的
`commit --grant effect_override:io` **全部 rc=1**，逐字具名拒絕。
**零個反例。** ⟹ **Q-040 的修補（意圖與值同住不可變成員、提交取聯集）
在並行下站得住。**

那 7 個 rc=0 的回合，**引擎是對的**：只有一顆 injection 落地（`#io` 那顆），
而操作者持有的 grant 正好覆蓋它 ⟹ 提交本就該成功。**探針的 REACH 守衛
做對了它該做的事**——它拒絕把那個 rc=0 讀成一個性質違反。

⟹ **這支探針沒有壞。** 壞的是它腳下的那塊地，而它的守衛正是唯一報出這件事的東西。
**⚠ 不要把 REACH 守衛拿掉，也不要 retry 掉它**——那會把一支誠實的探針換成一支空洞的綠，
並且是本專案第二次面對同一個誘惑（第一次是 `advert_persistence` 的桶溢出守衛）。

## 6. 這是誰的鍋，以及要不要裁定

**引擎的鍋，而且修補這一格不需要裁定。** 沒有任何條文規定 `new_store` 該怎麼問；
也沒有任何合理讀法會贊成「在一個空目錄裡並行跑兩個 `oo status`，其中一個死掉」。

**但要與 Q-016b 分清楚。** Q-016b（並行提交該收斂還是該合法分叉）**是未裁的語義題**。
本列**不碰語義**：兩個行程對這個 store 的宣告本來就沒有分歧，
分歧只發生在「其中一份宣告還沒落地」的那幾微秒。

### 6.1 不變式（不是機制）

**任何時刻，一個並行的觀察者對 `.oo` 的宣告只能看見兩種狀態之一：
「還沒有 store」，或「一份完整的宣告」。不得存在一個中間狀態，讓觀察者把
「正在被建立」讀成「既有，但宣告不全」。**

### 6.2 而它是 v0.49.0 那則判例的第三個實例

`REAL_03` §6.6 的 v0.49.0 新判例逐字是：`Path::exists()` 在 EACCES 回 false
⟹ **不透明**被壓成**不存在**，而且「這不是有人決定要壓平，是一個看起來無害的
前置檢查替他決定的」。

本列是同一個形狀的第三次：`!oo.join("format").exists()`
⟹ **「尚未」被壓成「沒有」**。

⟹ **附帶一個規格問句（需裁定，不擋修補）**：§6.6 今天要求「存在／不存在／不透明」
三者可分。**有並行寫入者時，「不存在」不是一個答案而是兩個**（沒有人要建 / 有人正在建）。
這要不要成為第四個必須可分的結果，是一則裁定；**本列的修補不等它**。

**⚠ 2026-09-13 就地更正：本節把兩件事寫成了同一件。** 用戶問「不透明跟不存在的
邊界在哪，不然當時為何會被壓平」，量下去發現**是兩條邊界，性質不同**——見 §9。
本節「同一個形狀的第三個實例」在「一個看起來無害的前置檢查替他決定了」那一層仍然
成立，**但可救性與修法不同類**，而 §9 據此改變了 O86 的候選排序。

## 8. 這一族有多大（2026-09-12 追加，起因：用戶問「這單是不是範圍超小」）

**問題成立。** §7 第 1 點的修補本身只有一行——若工單只寫那一行，那是**修個案**。
故先量類別：全樹（非測試）`.exists()` 共 **34 處**，分佈
`storage.rs` 11／`universe.rs` 10／`lib.rs` 3／`value.rs` 2／`savepoint.rs` 2／
`peers.rs` 2／`injections.rs` 2／`builtins/io.rs` 1／`builtins/fs_guard.rs` 1。

**判準不是「有沒有用 `.exists()`」**，是三問：
**(a) 缺席在這裡是什麼意思？(b) 它會不會只是暫時的？(c) 答錯的後果是什麼？**

已逐格量過四處，每一格都帶對照組：

| 呼叫點 | 缺席被讀成 | 結論 |
| :-- | :-- | :-- |
| `storage.rs:310` `new_store` | **「尚未」→「沒有」** | **缺陷**，§3–§4 |
| `builtins/io.rs:75` `io.exists` | **「不透明」→「不存在」** | **缺陷**，見 §8.1 |
| `storage.rs:345` `object_exists_digest`（→ `gc`） | — | **不是缺陷**，見 §8.2 |
| `storage.rs:379` `write_object` | — | **做對的**：註解逐字講明內容定址 ⟹ 兩個搶著寫的人 rename 同一份 payload，無 TOCTOU 缺口 |

⟹ **四格裡兩格有病、一格做對、一格經量測澄清。剩下 30 格沒有人問過這三問。**

### 8.1 `~%Io./exists` 把「不透明」當成一個值交給 n/ 程式

〔量 2026-09-12，v0.49.0 標籤二進位，`oo eval`，三問含完整對照組〕

| 問句 | 答 |
| :-- | :-- |
| `(~%Io./exists "open/f.txt")` 存在且可讀 | `#true  ;; %effect: #io` ✅ |
| `(~%Io./exists "open/nosuch.txt")` 真的不存在 | `#false ;; %effect: #io` ✅ |
| `(~%Io./exists "locked/f.txt")` **存在但父目錄 000** | **`#false ;; %effect: #io`** ❌ |

⟹ **後兩者在語言層完全不可分。** 而 n/ 正是為了「我說不出來」才有 `#blur` 與 ⊥。
**這是 §6.2 那個形狀最鋒利的一格**：前三格都在引擎內部，這一格**把壓平後的結果
當成一個值交出去**，程式會拿它去做決定。

**⚠ 這一格需要裁定，故不進不需裁定的那張卡**：它要回什麼？`#blur`（帶 `%cause`）／
⊥（帶 `%cause`）／第三個 tag？三者對既有程式的相容性不同。**已併入 O86 的語言面。**

### 8.2 `gc` 這一格經量測澄清，不是缺陷

先前的疑慮是：`object_exists_digest` 若回 false，可達物件會落在
`gc.rs:219`「Absent: continue without a verdict」那一枝之外而被掃掉。**量下去不成立。**

〔量，兩組，各帶對照〕**(i) 物件檔 `chmod 000`**：`.exists()` **仍為 true**
（不可讀的是檔案，不是目錄）⟹ 走到解碼 ⟹ 逐字
`integrity #object_undecodable: reachable digest 7038e250… cannot be decoded`，
**移除 0 顆，物件數 5→5**；〔對照〕不動時 `5 objects, 5 reachable, 0 collectable`。
**(ii) 物件的父目錄 `chmod 000`**（此時 `.exists()` 才為 false）：`gc` **更早就退出**，
逐字 `Error: list objects: cannot read store objects: permission denied`、
**rc=1**（**離開碼不經管線取得**——第一次取在 `| head` 之後讀到 rc=0，就地作廢重取）；
〔對照〕還原權限後同一指令 rc=0 且回報正常。

⟹ **兩條路都到不了那個塌陷**，`gc` 在兩種情形下都具名。這一格**清白，且清白是量出來的**。

### 8.3 工單該有的形狀

⟹ **不是一行，是一族**：

1. **`.oo` 宣告窗口原子化**（§6.1 的不變式）。
2. **逐格回答那三問，34 格一格不漏**，把「缺席被當成答案而缺席可能是暫時的或不透明的」
   那些修成具名。**交付要交的是那張 34 列的表**，不是只有被改動的那幾行——
   **沒有病的格子也要留下它為什麼沒病的一句話**，否則下一次還要再掃一遍。
3. **不進本卡**：`io.exists` 的回傳形（需裁定，O86 語言面）；`REAL_03` §6.6 要不要
   新增第四款（O86）。

**與 v0.49.0 的關係要寫在工單首段**：v0.49.0 修的是**一個**這樣的前置檢查
（`read_object_raw` 的 `Path::exists()`），並把它寫成 §6.6 的判例。
**本弧是去問「還有幾個」——那正是判例存在的意義。**

## 9. 兩條邊界（2026-09-13 追加，起因：用戶問「不透明跟不存在的邊界在哪？不然當時為何會被壓平？」）

### 9.1 為什麼會被壓平：壓平發生在標準函式庫

〔量 2026-09-13，`rustc -O` 直接問，七種情形〕

| 情形 | `exists()` | `try_exists()` | `metadata()` | `symlink_metadata()` |
| :-- | :-- | :-- | :-- | :-- |
| 存在且可讀 | `true` | `Ok(true)` | Ok | Ok |
| 真的不存在（ENOENT） | `false` | `Ok(false)` | Err(NotFound) | Err |
| 父目錄不可搜尋（EACCES） | `false` | **`Err(PermissionDenied)`** | Err(13) | Err |
| 父目錄本身不存在（ENOENT） | `false` | `Ok(false)` | Err(NotFound) | Err |
| 斷掉的符號連結 | `false` | `Ok(false)` | Err(NotFound) | **Ok** |
| 中間段不是目錄（ENOTDIR） | `false` | **`Err(NotADirectory)`** | Err(20) | Err |
| 符號連結成環（ELOOP） | `false` | **`Err(FilesystemLoop)`** | Err(40) | **Ok** |

⟹ **`.exists()` 對六種非平凡情形一律回 `false`。** 底下的 syscall 給的是三分
（`Ok(true)`／`Ok(false)`／`Err(kind)`），而 `Path::exists()` 的回傳型別是 `bool`
——**它丟掉 `Err` 那一臂，且丟得沒有聲音**。每一個呼叫點只是接受了那個較窄的型別。
〔量〕全樹 `try_exists` **0 次**、`symlink_metadata` 2 次、`fs::metadata` 2 次。

**用 D65 的話說**：`bool` 這個型別**只有點，沒有纖維**。它能說「哪一個點」，
說不了「我沒有走到任何點」。⟹ **壓平不是有人選錯了值，是有人選了一個裝不下纖維的型別**
——而 n/ 自己有那個字，就是 `#blur`。

### 9.2 第一條邊界（不透明 vs 不存在）：畫得出來，是我們丟掉的

它就在 `Ok` 與 `Err` 之間，**就地救得回來**（換一個保留 `Err` 的拼法，逐格決定
每個 `Err` 分支怎麼答）。

**但這條線不等於 `Ok`/`Err`**，量測給了兩個反例：

* **ENOTDIR 與 ELOOP 是 `Err`，卻不是不透明**——沒有人瞞著誰，是**問句本身壞了**
  （那條路徑上不可能有東西／問題繞回自己）。對到 n/ 這邊它們是 **⊥**（一個沒有答案
  的計算）而不是 `#blur`（一次被阻斷的觀測）。
* **斷掉的符號連結是 `Ok(false)` 而 `symlink_metadata` 是 `Ok`** ⟹ 那不是同一個
  答案的兩種，**是兩個不同的問句共用一個拼法**：「這條路徑上有東西嗎」與
  「這條路徑通到一個東西嗎」。⟹ `.exists()` 被重載的不只是答案，還有問句。

### 9.3 第二條邊界（尚未 vs 不存在）：畫不出來

**這是 §3 那個競態的真相，也是 §6.2 沒說準的地方。** 第二個行程問下去得到
**`Ok(false)`，而檔案系統沒有說謊**——在那一瞬間那個檔案真的不在。

⟹ **沒有任何錯誤處理救得回這個差別。** 「尚未」既不是點的性質、也不是通道的性質，
**它是另一個行程的意圖**，而檔案系統不知道什麼叫承諾。

⟹ **兩條邊界的修法不同類**：

| | 邊界在哪 | 救法 |
| :-- | :-- | :-- |
| 不透明 vs 不存在 | 通道上，API 畫得出來 | **就地**：換拼法 ＋ 逐格回答（型別紀律） |
| **尚未** vs 不存在 | **不在通道上** | **只能用構造消掉**：讓中間狀態不可觀測（整份宣告一次落地），使「尚未」這個答案**不存在**，而不是讓它可辨識 |

### 9.4 據此改變 O86(i) 的候選排序

把「尚未」寫成 `REAL_03` §6.6 的**第四個必須可分的結果**可能是**類別錯誤**：
前三個是通道回得出來的答案，**而「尚未」回不出來**。
⟹ **候選乙（不動 §6.6，改為呼叫方／構造的義務）現在比甲強**，
**而這個理由是量出來的，不是驗收方的推薦。** 已回寫 `STATUS` O86。

### 9.5 §8 那三問因此收緊成一問

原本的三問（缺席是什麼意思／會不會只是暫時的／答錯的後果）偏鬆。真正的判別器是：

> **一個 `.exists()` 是安全的，若且唯若它答錯時，下一步會有別的東西抓到。**

逐格對照：

* `write_object`（`storage.rs:379`）**安全**——答錯就落到 `atomic_write`，會大聲失敗。
* `new_store`（`storage.rs:310`）**不安全**——那個答案**決定走哪一枝，而那一枝不會回頭**。
* `io.exists`（`builtins/io.rs:75`）**最不安全**——**答案本身就是輸出**，交給 n/ 程式去做決定。

⟹ **34 格的掃描以這一問為準**，§8.3 第 2 點的表格每一列都要答它。
