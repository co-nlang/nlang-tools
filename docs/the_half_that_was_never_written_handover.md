## 2. O58：拆開

### 2.1 查找已經是對的形狀，只差一層

〔量〕裸名解析順序（`lib.rs:3685`）：

```
ctx.scopes → ~%Config 特例 → ctx.staged → ctx.root
                                          ↑ ~%Math 今天在這裡被找到
```

⟹ **在 `ctx.root` 之後加一層標準根。**

**優先序不必設計**：`hydrate_standard_root` 用 `entry().or_insert()`（缺席才插）
⟹ 使用者贏；而「root 先、標準根後」給的是同一件事。**不得改變這個方向。**

### 2.2 `~%Config` 不需要例外（偵察 §4，第一版寫錯已更正）

它是兩件東西：**創世旋鈕**（7 個常數）屬標準根，**隨它一起搬**；
**操作者覆寫**依 SPEC_09 §6.0.1 **本來就不進被提交的根**，活在暫存區。
〔量〕該節四條 MUST **全部已兌現**——不要動它們，也不要為 `~%Config` 造特例。

### 2.3 標準根必須成為一個真的物件

〔量〕它今天**有位址（`65f52e2d…`）卻不是物件**——`oo inspect` 回
`CAID not found in local store`，新倉只有 2 個物件。
**它是系統裡唯一一個有位址卻定址不到的東西。** → **P2**

⟹ 拆開後 sentinel 從「寫在物件裡卻不進雜湊的欄位」變成**進雜湊的內容**
（一個指名依賴的欄位，§6.8.1 已允許）。**這會讓 §6.8.1 那句被 O58 量測推翻的話
變成真的**——條文措辭由驗收方處理，交付方不動規格。

### 2.4 四個孤兒自動消失

〔量〕`/add`、`@list`、`@option`、`@result` **四個都擋人**（閉合的繭佔住使用者可見座標）。
拆開後它們都變成可遮蔽。→ **P1**

**不要用「特別處理這四個名字」來讓 P1 變綠**——那是修個案。P1 該綠是因為
根上不再有那四個座標。

## 3. O61 ＋ O62：效果搬家與正準形

### 3.1 搬家，不是新機制

〔量〕`ComboVal` 有兩個 effect 住處：`meta`（寫下的，**進雜湊**）／`effect`
（傳染的，**不進**）。把傳染值落成 `meta["%effect"]` 即可——**meta 軸本來就進雜湊**。

**這一格的證據**〔量〕：`app: { v: "written-down" }` 與
`app: { v: ~%Env./get("OO_PROBE_VAR") }`（同值）提交到**同一個位址**。
**一個從外面讀進來的值，與一個打進去的值，位址無法區分。** → **P3**

### 3.2 兩條界線（**逐字帶進實作**）

*   **判準是格的 ⊥。** 對 SPEC_08 §4.1 的五個基礎標籤而言，「非 ⊥」與「非 `#pure`」
    **是同一個判準**——`if effect != Pure` 是對的。
    **⚠ 本項第一版寫成「不是『純不純』…會把 `#cached` 一起吃掉」，那句話是錯的**
    （`#cached` 非 `#pure`，`!= Pure` 本來就含它）。**真正的風險在反面**：
    `#cached` 讀起來像「已經固化、等同沒事了」，於是被順手一起正規化掉
    （`if effect != Pure && effect != Cached`）。**它不是單位元**，
    §4.2.4 的固化語義靠它——**落成欄位，不得省略**。
*   **正規化只得在守衛之後。** §4.1 允許顯式寫入優先於引擎標籤 ⟹ 使用者寫得出一個
    **假的** `#pure`，而那正是 §4.3 靜態守護要抓的謊。
    **若正規化搶在守衛之前抹掉那個欄位，正規化器就成了共犯。**
    順序：**判定有效效果 → 守衛 → 僅當有效效果 ＝ ⊥ 時去欄位**。→ **C1** 看守

### 3.3 §6.7 的既有違反本弧順帶關掉

〔量〕`{ %effect: #pure, v: 1 }` 與 `{ v: 1 }` 的 `.%effect` **皆讀 `#pure`**，
位址卻不同。O61 已裁二者為同一個值 ⟹ **§6.7「位元組為值之函數」今天被違反著**。
→ **P4**

## 4. 舊倉：多重具備第一次真的上場

O61/O62 改變標準根的內容 ⟹ **它的 digest 移動** ⟹ **每一個既有倉指名的都是舊的那一份**。

〔量〕`shipped_standard_roots()` 今天是 `from_roots([self.root_with_system()])`
——**一列**。而 Q-025 的驗收用的是**三個真二進位**，**「同一個引擎持有兩列」這條路
從未被真的走過**。

⟹ **必須新增歷史列**，保留拆開前的標準根值（`v0_22_standard_root()` 的註解逐字
預期了這一天：「Keep this builder after a future library change so that
`shipped_standard_roots` can retain it as data」）。

**C3 看守它**：斷言 `supports_standard_root("65f52e2d…")`。
**今天綠，做完必須仍綠。忘了加歷史列，C3 就紅。**

> **⚠ 這一項最容易被漏掉，因為它不在「哪幾處程式碼要改」的清單上。**
> 前三處（`put_root` 投影／`Universe` 不內含／`EvalContext` 加一層）都是**結構**改動；
> 歷史列是一筆**資料**。少了它，程式結構完全正確，而**所有既有的倉打不開**。

⚠ **C3 不能證明舊倉真的打得開**——那要一個標準根不同的二進位，樹內造不出來。
**真證據是驗收時的跨版本矩陣**，見 §6.4。
