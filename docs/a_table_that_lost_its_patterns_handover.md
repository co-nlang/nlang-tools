## 1. 缺陷

〔量，v0.83.0；v0.78.0 起逐版相同〕寫在檔案頂層的表，提交後照常分派；**同一張表往下一層——或寫在箭頭的本體裡——提交後就不是那張表了**：

*   `k: { t: { @{ @str }: 9, @{ @int }: 1 } }` 提交後 `_.k.t "s"`、`_.k.t 5` ⟹ ⊥ `#no_matching_branch`（就地 `9`／`1`）；深度 3、私有欄位 `~k: { t: … }` 同。
*   `f: (x -> { @{ @str }: 9, @{ @int }: 1 } x)` 提交後 `_.f "s"`、`_.f 5` ⟹ `#no_matching_branch`。
*   `@{ 4 }:` 讀回成依鍵查找的 `4:`、`@{ _ }:` 讀回成預設分支 `_:`、`@{ #a }:` 讀回成裸 `#a:`——每一個都是**另一個鍵**（`{ @{ #a }: 1 } = { #a: 1 }` ⟹ `#false`，而 `t: { @{ #a }: 1, @{ #b }: 2 }` 提交後的根與 `t: { #a: 1, #b: 2 }` 同為 `1b8ee686…`）。
*   `@{ @int & 4.. }:`、`@{ 1 | 2 }:`、`@{ 1..9 }:`、`@{ { a: @int } }:`、`@{ [@int, @int] }:`：evolve 照收（rc=0），**寫下的工作集讀不回來**——`commit` rc=1「`store n/ parse`」，連 `oo status` 都印同一個剖析錯；之後的 `oo eval` 讀的是空宇宙。
*   巢狀的箭頭 `&` 表（`k: { t: (x @str -> 9) & { @{ @int }: 1 } }`）提交後 `#missing_key`，頂層同式已得 `1`／`9`（D105）。
*   **`oo fmt --write` 改壞使用者的檔**：`k: { @{ @str }: 9, @{ @int }: 1 }` 被就地改寫成 `k: { @int: 1, @str: 9 }`（rc=0），改寫後施於 `"s"`、`5` 皆 `#no_matching_branch`；`k: { @{ 1..9 }: 1 }` 被改寫成 `1..9: 1`（rc=0），之後這個檔再也剖析不了。

〔讀〕成因只有一處：`crates/parser/src/ast.rs` `FieldKey::to_string_canonical` 的 `FieldKey::Pattern(e) => e.to_nlang(0)`——印模式鍵時丟掉 `@{ … }` 包裝（創世提交即如此）。頂層的表在 evolve 時就求成值，以 `%rules`／`%pattern` 存，不經過這條路；**巢狀欄位與箭頭本體存成表達式**（thunk 的 `~%__nlang_expr`、`Code`），`store_codec.rs` 以 `expr.to_nlang(0)` 寫成 n/ 文字、讀時再剖析——`.oo/injections/<id>` 逐字是 `@str: 9`／`@int: 1`、`@int & 4..#_: "A"`。`oo fmt` 用同一個印出端（`main.rs` `program.to_nlang()`）。`main.rs` 的 `repl_unobserved` 自己包了 `@{…}`——同一個坑只在那一個呼叫端修過。

〔量〕對 `nlang-spec` 與 `nlang-tools` 全部 229 個 `.n` 檔做「剖析 → 印 → 再剖析、比 AST」：224 個往返相同、3 個本來就剖析不了、**2 個讀不回來，皆因模式鍵**（`conformance/L2/07`、`08`）；另手列字面、跳脫、插值、區間、展開、導航等 36 形，模式鍵以外無一失敗。

## 2. 裁定與依據

*   **不需新裁定**：`SYNTAX_02` §4 #12 已是 MUST——印出的源碼必須讀回**同一個值**；D96 已規定裸 `@T:` 與 `@{ @T }:` 是兩個不同的鍵；D101 已規定一張表一個正規形。這是**引擎的鍋**：任何符合規格的印出端都不會這樣印。
*   位址：thunk 與 `Code` 的位址由表達式的節點表算（`bn_serial.rs`，Q-052），**不由印出的文字算**。⟹ 修好之後，只有「讀回來就變成另一個值」的那些值位址移動——它們第一次拿到自己的位址；其餘一個位元組也不該動（D69 判例同理）。

## 3. 射程＝不變式（不是機制）

*   **I1 一張表在哪裡寫都是同一張表**：寫在頂層、欄位裡、欄位的欄位裡、私有欄位裡、箭頭的本體裡、與箭頭相交後放在欄位裡；提交後、就地、`run --observe`，對每一個輸入答案相同（r1–r4、r6、r7）。
*   **I2 每一種模式鍵都存得下、讀得回**：型別、字面、Top、標籤、聯集、區間（含開放端）、`&` 組合、Combo、清單、補集、`$` 約束——evolve 與 commit 皆 rc=0，讀回後與寫下的是同一個鍵（r4、r5、r7）。**「印出的源碼讀回同一個值」是要守的不變式，修那一行只是一種機制**——若你找到印出端還有別的構造讀不回（本卡偵察沒找到），一併在射程內，並在 8.1 列出。
*   **I3 `oo fmt` 不改變檔案的意思，且冪等**（r8）。
*   **I4 其餘不動**：不含模式鍵的值——包括巢狀的引號鍵、標籤鍵 `#a:`、`_:`、裸 `@int:`、開放區間值、沒有表的箭頭——位址不動（g1）；非模式鍵在 `fmt` 下照舊裸印（g2）。
*   **I5 不改磁碟格式**：不推進佈局或編碼（新倉仍 `layout=9`／`encoding=5`）。

## 6. 明文不在射程內

*   **位址不含欄位的軸**（`{ int: 1 }` 與 `{ @int: 1 }`、`{ h: 3 }` 與 `{ ~h: 3 }` 同址；`REAL_03` §6.3 與 §6.7 自相矛盾，修法是紀元）：本卡偵察旁量，**另列 Inbox**（`interrupt-candidate`，須裁）。你會看到 `~k: { … }` 與 `k: { … }` 提交出同一個根——那是這一列，不是本卡。
*   **補集模式鍵在表裡不匹配**（`{ @{ !(..0) }: "pos", _: "no" } 12` ⟹ `"no"`；同一約束寫成箭頭 `(x @{ $ & !(..0) } -> 1) 12` ⟹ `1`）：就地即如此，與巢狀無關，另列 Inbox。r5 刻意不用補集鍵。
*   巢狀欄位的**書寫順序**進入 thunk 的位址（`k: { t: { a: 1, b: 2 } }` 與 `{ b: 2, a: 1 }` 兩根、`=` 判 `#true`）：Inbox 既有列「`=` 對 Thunk 外延，而它的位址是內涵的」（O90）的實例；`oo fmt` 重排欄位因此會移動巢狀值的根。不在本卡。
*   標籤鍵 `#a:` 與 `@{ @tag }` 並列時的分派（`{ #a: 1, @{ @tag }: 2 } #a` ⟹ `2`）：Inbox 既有列「標籤鍵 `#a:` 與引號鍵 `"#a":` 是同一個座標」的家族。
*   `x @{ 4.. } -> …` 剖析成施用：Inbox 既有列。
*   規格文字與 `CHANGELOG`：驗收方收尾。
