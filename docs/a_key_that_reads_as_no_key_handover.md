# 工單：一把讀不到的金鑰被讀成沒有金鑰（Q-054）

> 佇列 `nlang-spec/meta/WORK_QUEUE.md` Q-054／裁定 `meta/oo/STATUS.md` **O91**
> 探針（已預先提交並校準）`crates/interpreter/tests/a_key_that_reads_as_no_key_probe_test.rs`
> 基線：dev `cbfd95d`／`oo v0.56.0` ⟹ **5 綠 4 紅**，三輪一致、零空洞讀數。

## 1. 缺陷

`node_id_if_present()`（`lib.rs:1103`）與 `Ouroboros::init` 裡的兩個讀取（`lib.rs:948`／`957`）
都用 `Identity::load(..).ok()`。**三個狀態塌成兩個**：

```
不存在                → None
存在但讀不到          → None      ← 缺陷
存在且讀得到          → Some(id)
```

而下游 `peers::load` 把 `None` 讀成「還沒有節點金鑰」，並且
`restore_asserted = this_node_id.map(|id| id == owner).unwrap_or(false)`（`peers.rs:319`）
⟹ **一把讀不到的金鑰不只是換個順序，它把每一筆記錄的觀測半邊整個丟掉**：
`addr` 清空、`provenance` → Unknown、**`admission_seq` → 0**，且路由表未播種、為空。

## 2. 為什麼這比「順序不同」嚴重

`local_seat_rank` 用**讀者自己的** node id 加鹽。它的理由逐字記在
`crates/oo/tests/seat_order_probe_test.rs` 表頭：一個與受害者無關的繫結破法，
讓攻擊者 grind 一把金鑰（SPEC_15 §7.1 量到 3,500 keys/s）就能
「在每一個曾在同一秒聽見你的節點上都佔一個席位」。

**讀者的 id 缺席時，那個雜湊只剩 `sha256("oodp-seat-order:v1:" + "|" + peer_id)`
——只由同儕自己的身分決定。**

那就是 `seat_order` 那一弧的 **C′**，它被立為 MUST NOT 而**刻意沒有探針**，
理由是「一旦到達順序是全序，它就不可達」。**它可達**：
一把讀不到的金鑰把每一筆的 `admission_seq` 歸零，
⟹ **它自己製造出那個繫結，然後用只由同儕身分決定的方式去破它**，
而且**在任何目錄上都成立，不限 legacy**。

## 3. 已量（驗收方，2026-09-22，`oo v0.56.0`）

*   **寫入視窗是真的且還開著**：200 次真實鑄造，0 位元組可見視窗 **120／200**，
    部分寫入 **0／200**（永遠不會讀到半把金鑰，只會讀到空的）。
*   **`oo status` 對金鑰的四種狀態完全無差別**（完好／0 B／20 B 垃圾／不存在）：
    同 rc、同輸出；而**同一把垃圾金鑰 `oo node id` 拒絕 rc=1**「not a valid PKCS#8」。
    ⟹ **拒絕已經存在，准入那條路沒去問。**
*   **一個讀者會等，三個不會**：`load_after_race` 只被 `load_or_mint` 用（`value.rs:2653/2658`），
    而 `948`／`957`／`1117` 是裸 `Identity::load`；**且 948／957 對同一把金鑰載入兩次**。
*   `Ouroboros::init` 耗時 **14–18 ms**，而金鑰讀取在它尾端（這是探針 `WINDOW=60ms` 的依據）。

## 4. 射程＝不變式（不是機制）

*   **I1（丁）** 任何一般讀取路徑，**不得**在磁碟上存在一把完整身分、且在 **Q-051 已裁的
    有界窗口內**完成時，斷定本工作區沒有節點身分。
    ⚠ **那個不變式在 Q-051 就已經以強形式被接受**——「等過**任何**暫時不完整的身分檔」
    ——而它今天只落在**四個讀取點的一個**。本項是補完，不是新裁定。
*   **I2（甲）** 當身分檔存在、且**等過之後仍讀不到**時，其結果**不得與「根本沒有身分」
    在觀測上相同**。⚠ **本工單不指定形式**：具名拒絕、回報降級、三態型別皆可，
    **探針 R3 對機制無知**。你選，並在報告裡寫為什麼。
*   **I3** 一把**永久**無效的金鑰**必須**仍然是錯誤，且其位元組**逐字未變**（Q-051 G2／D2）。
    **等待不得變成接受。**
*   **I4** 任何讀取路徑**不得**鑄造。

## 5. 紅線（探針已釘，今天綠，修復不得拿它們換 I1／I2）

*   **C1／C2** 控制組：可讀身分下全部 6 筆載入、路由表播種 6、`admission_seq` 1..6 存活，
    且全序決定順序（繫結根本沒發生）。
*   **G1** 永久無效金鑰仍是錯誤、訊息含 `not a valid PKCS#8`、位元組未變。
*   **G2** 開啟工作區不鑄造。
*   **G3** 兩個**可讀**身分在真正的繫結上必須破得不一樣
    ——那證明 C′ 買到的性質**存在**，故 R4 讀作「失去它」而不是「它從來沒有」。
*   **身分紅線**：本弧**不得**碰 `bn_serial`／任何位址。全樹 ×3 不得有任何 digest 移動。

## 7. 明文不在射程內（沉默不得被當成覆蓋）

*   **戊／乙（把寫入原子化：獨佔暫存名＋`link`）不在本弧**。它在 **Q-051 工單 §4 就被提過並否決**，

    而身分檔也可能由安裝程式、同步工具、使用者複製產生 ⟹ **讀者無論如何都得等**。
    〔交付當時已量〕若日後要做，**必須用 `link` 不能用 `rename`**（`rename` 會覆寫，違反 D2），

    那是為什麼本弧的探針在庫層而不是 CLI 層。**要不要給它一個出口是另一張卡**，已入 Inbox。
*   **I1 的代價沒有量**（三個點、每點最多 100 ms）⟹ 這是 Q1 指名要你量的。

## 8. 探針完整性

*   紅探針（r1／r2／r3／r4）**基線必須是紅的**，理由逐支寫在各自的 doc comment。
    **你可以讓它們變綠，不得改寫它們的宣稱。** 若你認為某個 pin 是錯的，**在報告裡說，不要改它**。
*   **r1／r2 是時序探針，而它們會宣告自己作廢**：`observed_mid_write` 在讀者跑得比視窗還久時
    **panic 並印出 `VOID READING`**，而不是回一個沒有意義的綠。
    〔量〕`WINDOW=60ms` 對 `init` 的 14–18 ms 有 3–4 倍餘裕，且仍在 100 ms 預算內。
    **若你在你的機器上看到 `VOID READING`，那不是失敗也不是通過——回報它。**
*   `rustfmt` **不得**掃這個檔案。
