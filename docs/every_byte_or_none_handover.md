## 1. 一句主張

> **同一個 CAID 的 CAS 物件,磁碟位元組必須相同。**

這是 O48「每一位元組要嘛進雜湊,要嘛不該在磁碟上」的可測形。引擎今天已經有**一個方向**
——位元組決定位址,合法的語義竄改被 `#caid_mismatch` 擋下。缺的是**另一個方向**:
**位址不決定位元組。**

## 2. 地上有什麼〔量 2026-08-13,引擎 v0.19.0〕

### A 鍵序不決定

三次獨立執行、**逐位元組相同的源碼**:

| | 位址 | 檔案 sha256 | 大小 |
| :-- | :--- | :--- | ---: |
| run 1 | `ba56831a…` | `84db4cfb…` | 252,435 B |
| run 2 | `ba56831a…` | `b23f5929…` | 252,435 B |
| run 3 | `ba56831a…` | `b9200dc9…` | 252,435 B |

大小相同,且**排序後的行多重集相同** ⟹ **純粹是重排**。`system` 頂層鍵序逐行程不同:
run 1 `[String, Effect, Config, …]`／run 2 `[Process, Csv, Cond, …]`。

**雜湊路徑本身是決定性的**(位址三次都沒動),不決定的是**序列化路徑**。

### B `span` 存進去、不進雜湊

| 源碼 | 存下的 span | 位址 |
| :--- | :--- | :--- |
| `app: { k1: 1 }` | `{11,12}` | `16ba5683…` |
| `app: {   k1: 1 }` | `{13,14}` | **`16ba5683…`** |

磁碟上竄改 span 的數字:**不被偵測**,`oo inspect` 照常回 `k1: 1`。竄改整數(合法編碼
`[1,[1]]`→`[1,[2]]`):**被偵測**。⟹ 檢查存在,**覆蓋面是位元組的真子集**。

### C pretty 空白

物件以 pretty JSON 寫出:磁碟 **252,435 B**,緊湊 **67,971 B** ⟹ **約 184 KB 的縮排,
沒有任何雜湊覆蓋它**。〔量〕根物件 **9,501 個換行**。

## 3. 可滿足性檢查(工單自身)

A ＋ B **完全解釋**全部位元組分歧,沒有第三個原因:把兩份「只差空白」的物件各自
**排序後**再比對,差異剩 **14 行,其中非 `start`／`end` 的行數 ＝ 0**(不截斷,全文列出)。

⟹ 修掉 A 與 B,R2／R3 即可滿足。**這一步是在寫閘之前做的**,不是事後解釋。

## 4. 射程

**做**:

1. **序列化採正準序**——與雜湊路徑同一個順序。
2. **`span` 不寫進 CAS 物件**。
3. **不寫 pretty 空白**。
4. **`STORE_FORMAT_VERSION` 1 → 2**(2026-08-13 追加,理由見 §4.1)。

**不做(明確)**:

| 不做 | 為什麼 |
| :--- | :--- |
| **強制求值** | Q-010b。本弧結束後 CAS 物件裡**仍有 Thunk**(R1 的存在半驗這件事) |
| **拔閉包** | 〔量〕閉包**進雜湊**(清空或加鍵皆得 `#caid_mismatch`)⟹ 拔它移動 CAID。放進本弧會逼出**第二個紀元** |
| **改 `system` 為 digest** | O50,隨 Q-010b 同一紀元 |
| **換編碼形(JSON → n/)** | O31／W8′-c |
| **動 `.oo/staged`** | O35／O48／O49 治的是 **CAS 物件**;`staged` 今天已是耐久檔但**沒有位址**,依 O51 **保留 Thunk**。**強制發生在 commit,不在 evolve**(P2 守這條) |

**⟹ 本弧不移動任何身分。** P1 釘住 `app: { k1: 1 }` 的根 CAID `16ba5683…`;若它變紅,
交付動到了雜湊投影,本弧就不再是非破壞性的,**不能與 Q-010b 分開出貨**。

### 4.1 工單更正:兩個破壞軸,我原本把它們併成一個(2026-08-13)

**模型 #4 找到一組不可同時滿足的驗收對,指控成立**:R1 要求新物件沒有 `"span"`,而
本檔 §6.5 原本要求 v0.19.0 讀得開新物件。

〔量 2026-08-13〕`crates/parser/src/ast.rs` **四處** `pub span: Span`,**零個 serde 屬性**
⟹ 缺欄位直接反序列化失敗。**「JSON 仍是 JSON」不足以保證舊引擎讀得開**,而舊二進位
無法從一個不存在的欄位推回 span——**這不是新實作補一層相容層能解決的**。

根因是我把**兩個不同的破壞軸併成一句**:

| 軸 | Q-010a | Q-010b |
| :--- | :--- | :--- |
| **身分**(CAID 動不動) | **不動**(P1) | **全面移動 ⟹ 紀元** |
| **讀相容**(舊引擎開不開得了) | **開不了** | 開不了 |

「本弧不移動任何身分」是真的;我接著把它當成蘊涵讀相容,那一步是假的。

**裁定:方向 3(升格式版本,舊引擎明確拒開)**,理由:

1. **機制已經存在,不必新造。**〔量〕`storage.rs:119 ensure_format` 已在強制;實測把
   `.oo/format` 改成 `2` 得到 `store format version 2 is not supported by this engine
   (understands format 1); refusing to open`——**乾淨的拒絕,而且說得出版本號**。
2. **方向 1 嚴格較差。** 同樣讀不到,但舊引擎撞到的是「缺少一個它沒聽過的欄位」的
   serde 錯誤,而不是一句說得出版本的拒絕。同一個結果,較差的診斷。
3. **方向 2 廢掉本弧的主張。** 保留 span,O48 在本弧不成立。
4. **不牽動 O36。** O36 問的是「**缺檔**時 `.oo/format` 代表宣稱還是裁決」;格式**真的
   變了**就把數字加一,在兩種讀法下都成立。**Q-011 不因此提前。**

**考慮過但否決的第四條**:保留 `span` 欄位但恆寫 `{0,0}`。它能同時滿足 R2／R3 與舊引擎
讀取,但那是**把 §7 警告的捏造讀數從讀取端搬到寫入端**——磁碟上一個不進雜湊、且內容是
謊的欄位。O48 的字面與精神都不允許。

5. **跨版本**(**2026-08-13 更正,原文不可滿足,見 §4.1**):
   - **舊倉 → 新引擎**:v0.19.0 寫的 format-1 倉,新引擎**必須讀得開**。
     ⟹ 讀取端要能吃「有 span 的舊物件」與「沒有 span 的新物件」兩種。
   - **新倉 → 舊引擎**:v0.19.0 **必須拒開,並說出版本號**——不是 serde 錯誤。
     **這一項要用真的 v0.19.0 二進位實測**(git worktree ＋獨立 target,同 M2 跨版本
     表的作法),**不要推論**。
6. **加性關鍵量測**:新的根物件大小。預期由 252,435 B 降到 67,971 B 上下(−73%),
   **且 P1 的 CAID 不動**。

## 7. 交付方要注意的一個陷阱

`span` 的移除若用 `#[serde(skip)]`,讀回時會由 `Default` 填一個 `{0,0}`。那是一個
**被捏造的讀數**,而它會出現在載入後的錯誤訊息裡,指向源碼第 0 個位元組。

本弧不裁「span 該不該有一個『未知』的表示」——但**交付不得讓捏造值看起來像真的**。
若做不到,選擇讓載入後的值**沒有** span,而不是有一個假的。
