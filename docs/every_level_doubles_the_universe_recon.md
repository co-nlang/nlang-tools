## 1. 形狀鑑別

| 形狀 | 時間 |
| :-- | :-- |
| `oo fmt` 深度 16(只解析+印) | **0.01 s** |
| eval 深度 16 單鏈 | >15 s |
| eval **一層 200 個欄位** | **0.33 s** |
| eval 深度 8 單鏈 | 0.08 s |
| eval **深度 8,每層兩個子樹** | **>15 s** |

* 解析**沒問題**——`fmt` 走完整個解析與列印。
* **與節點數無關**:201 個節點的寬結構 0.33 s;約 511 個節點的深度 8 二分叉樹跑不完。
* 成本 ≈ **2^深度**(單鏈)、**4^深度**(二分叉)⟹ 每個節點對每個子節點做兩份工。

## 3. 機制(讀碼,已在型別層確認)

`crates/interpreter/src/value.rs:554`:

```rust
pub fn seal_defining_scope(c: &mut ComboVal) {
    let frame = c.clone();                          // 深複製整棵子樹
    fn inject(v: &mut Value, frame: &ComboVal) {
        match v {
            Value::Thunk { closure, .. } => closure.push(frame.clone()),   // 每個 thunk 再一份
            Value::Combo(inner) => { /* 走訪全部欄位族 */ }
```

而 `Value::Thunk.closure` 的型別是 **`Vec<ComboVal>`——傳值,不是 `Arc<ComboVal>`**。

於是第 n 層封存時,`frame` **本身已經含有第 n−1 層塞進去的 frame 副本**:

```
size(n) = size(n−1)          [combo 本體]
        + size(n−1)          [被 push 進 thunk closure 的那份]
        = 2 · size(n−1)
```

單鏈 2^n、二分叉 4^n,與 §1、§2 的量測一致。
唯一呼叫點:`eval.rs:1196`(combo 建構),每建一個 combo 就走一次。

## 4. 沒有任何視界攔得住它

| 閘 | 預設 | 結果 |
| :-- | :-- | :-- |
| `fuel` | 10000 | **完全沒被計**——實測 `~%Config.fuel: 50` 於 16 層仍逾時 |
| `max_unification_depth` | 256 | 不相干(16 ≪ 256) |
| `max_branches` / `max_pattern_nodes` | — | 不在這條路上 |
| **`timeout`** | **`#_`(無限)** | **唯一擋得住的**:`timeout: 2000` 於 16 層 **2.93 s 退出 0** |

兩件要記:

1. **`timeout` 的預設是本 session 的 O41 裁定改成 `#_` 的。** 在此之前它是 `1000`
   但從未被接線(W4″/O38 才接上)。所以牆一直不存在,只是現在**是明文政策造成的**。
   〔這不表示 O41 錯;預設無限是對的裁定,而 `timeout` 只是碰巧遮住過這個缺陷。〕
2. **`fuel` 沒攔住,使一條規範性定義為假。** SPEC_08 §3.2 寫 `%fuel` 是
   「限制單次收斂觀測涉及的**節點展開與遞迴總量**(MBU)」。
   2¹⁶ 次展開燒不掉 10000 燃料 ⟹ **fuel 計的不是展開。**

## 5. 看起來像兩件事(留給裁定階段)

* **D1 機制**:作用域 frame 以值複製,且被複製進每一個 thunk 的閉包鏈。
  自然的方向是 `Arc<ComboVal>` 共享,但**未驗證**——`inject` 之後是否有人改寫 frame、
  以及 `PartialEq`/雜湊是否依賴 frame 的獨立身分,都還沒查。
* **D2 計量**:`fuel` 沒有在數它宣稱在數的東西。**即使 D1 被修好,D2 仍然成立**
  ——修好之後這條路只是變便宜,不是變有界。

兩者是否同一弧,取決於「修好 D1 之後 D2 還會不會咬人」。**本稿不裁。**
