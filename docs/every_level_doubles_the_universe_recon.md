## 1. 形狀鑑別

| 形狀 | 時間 |
| :-- | :-- |
| `oo fmt` 深度 16(只解析+印) | **0.01 s** |
| eval 深度 16 單鏈 | >15 s |
| eval **一層 200 個欄位** | **0.33 s** |
| eval 深度 8 單鏈 | 0.08 s |
| eval **深度 8,每層兩個子樹** | **>15 s** |

* 解析**沒問題**——`fmt` 走完整個解析與列印。
* **與節點數無關**:201 個節點的寬結構 0.33 s;約 511 個節點的深度 8 二分叉樹跑不完。
* 成本 ≈ **2^深度**(單鏈)、**4^深度**(二分叉)⟹ 每個節點對每個子節點做兩份工。

## 3. 機制(讀碼,已在型別層確認)

`crates/interpreter/src/value.rs:554`:

```rust
pub fn seal_defining_scope(c: &mut ComboVal) {
    let frame = c.clone();                          // 深複製整棵子樹
    fn inject(v: &mut Value, frame: &ComboVal) {
        match v {
            Value::Thunk { closure, .. } => closure.push(frame.clone()),   // 每個 thunk 再一份
            Value::Combo(inner) => { /* 走訪全部欄位族 */ }
```

而 `Value::Thunk.closure` 的型別是 **`Vec<ComboVal>`——傳值,不是 `Arc<ComboVal>`**。

於是第 n 層封存時,`frame` **本身已經含有第 n−1 層塞進去的 frame 副本**:

```
size(n) = size(n−1)          [combo 本體]
        + size(n−1)          [被 push 進 thunk closure 的那份]
        = 2 · size(n−1)
```

單鏈 2^n、二分叉 4^n,與 §1、§2 的量測一致。
唯一呼叫點:`eval.rs:1196`(combo 建構),每建一個 combo 就走一次。

## 7. 續查(2026-08-10):診斷已由執行期證實,不再只是讀碼

### 7.1 A/B spike:指數 100% 在 `seal_defining_scope` 裡

在拋棄式 worktree 把該函數以環境變數閘掉(**純診斷,不是提案的修法**),同一支二進位:

| | seal 開 | seal 關 |
| :-- | :-- | :-- |
| nest=12 | 1.09 s | **0.06 s** |
| nest=14 | 5.01 s | **0.06 s** |
| nest=16 | 逾時(20 s) | **0.06 s** |
| nest=20 | 逾時 | **0.07 s** |
| nest=40 | 逾時 | **0.12 s** |

指數整條消失,且 12→40 層幾乎不長。**§3 的讀碼推論由此升為執行期證據。**

### 7.2 封存是承重的,所以「拿掉」不是選項

同一個 spike 跑測試:**8 支失敗**(cargo 在第一個失敗的測試二進位後停下,
故 147 這個總數是**不完整的**,不可當成「只有 8 支依賴它」)。
封存實作的是 SPEC_04 §2.1／§3.1 的詞法作用域,本來就不能移除。
這一項的用途只是**界定語義面**:修法必須保住封存的效果,只改它的代價。

### 7.3 `Arc` 方向:三個可能擋路的都清掉了

| 疑慮 | 查證 | 結果 |
| :-- | :-- | :-- |
| frame 被推入後是否遭就地改寫 | grep `scopes`/`closure` 的 `iter_mut`/`get_mut`/索引指派 | **零命中,只讀** ⟹ 不需要 CoW |
| 相等性是否依賴 frame 的獨立身分 | `value.rs:413` Thunk 的 `PartialEq` 比 `cl1 == cl2` | **結構相等**,`Arc` 解參考後不變 |
| 序列化 | `Thunk.closure` 無 `#[serde(skip)]`,但耐久形已量為線性 ⟹ 帶大 closure 的 thunk 不會落地 | 需要 `serde` 開 **`rc`** feature;`Arc<T>` 序列化為 `T`,磁碟格式不變 |

**爆炸半徑**:型別宣告 2 處(`lib.rs:82` `pub scopes: Vec<ComboVal>`、
`value.rs:237` `closure: Vec<ComboVal>`),使用點約 **67** 個。機械性改動,編譯器會逐點指出。

### 7.4 一個要在裁定裡講清楚的上界

`Arc` 之後 `closure.push(frame.clone())` 變成 O(1);但
`let frame = c.clone()` **仍會深複製該層的 `ComboVal` 結構**(只有內層 closure 變成
共享指標)。所以代價由 **2^n 降為約 n²**,不是 n。

40 層的 n² 微不足道,**但這是上界不是消滅**。若要到線性,得再把
`Value::Combo` 也改成 `Arc<ComboVal>`——那是另一個量級的改動。
**建議在裁定裡明說止於 n²**,免得日後有人以為這條路已經線性。

### 7.5 D2 未被本次續查觸及

`fuel` 沒有在數展開,這件事**與 D1 無關且不會被 D1 的修法帶到**。
仍為獨立的一件。

## 8. 裁定書草案(2026-08-10,待批)

### 8.0 補量:`fuel` 不是「太鬆」,是**沒有錶**

`check_resources` 全樹只有 **9 個呼叫點**,而計的是
**已求值的 AST 節點數,加上該節點在原始碼中自身的字面元數**:

| 位置 | 何時扣 | 成本 |
| :-- | :-- | :-- |
| `eval.rs:914` `eval_internal` | 每求值一個 AST 節點 | 1 |
| `eval.rs:938` `ExprKind::Combo` | combo 字面 | 10 + **欄位數**×2 |
| `eval.rs:1610` `ExprKind::Tuple` | tuple 字面 | 10 + 元素數×2 |
| `eval.rs:1633` `ExprKind::Poset` | poset 字面 | 10 + 關係數×2 |
| `eval.rs:1260` `ExprKind::Apply` | 態射套用 | 5 |
| `lib.rs:3145` | `<<path>>` 解析 | 1 + 段數(空路徑 32) |
| `lib.rs:3625` | 路徑導航 | 每段 2 |
| `unify.rs:92` `unify` | 每次合併 | 10 |
| **`lib.rs:3171` `force_recursive`** | 固化遞迴 | **0** |

「欄位數」數的是**你在原始碼那個位置寫了幾個欄位**,不是執行期展開出幾個節點;
總帳因此 ≈ **O(走過的 AST 大小)**。

**最後一列最刺眼**:`force_recursive` **有**呼叫 `check_resources`,金額寫死 **0**
——它只借那個函數做深度與逾時檢查,而遞迴固化正是走整棵子樹的地方。
所以不是「沒人想到要在那裡計費」,是**計費點已經接好,金額是零**;
其註解自陳該呼叫是 Stage 3 為了讓深度守衛攔住 `v: <<_.>>` 而加,
關心的是堆疊不要死,不是計量。

`seal_defining_scope` 與 `ComboVal::clone` 則完全不在這九個點裡。實測:

| | |
| :-- | :-- |
| nest=6,`fuel: 5` | **跑完** |
| nest=14,`fuel: 20` | **跑完,4.93 s**(約 2¹⁴ 單位的工作,預算 20) |

十六層巢狀的帳:AST 16 個節點、每個 1 欄位 ⟹ 約 16×12 = **192 燃料**;實際工作 **2¹⁶**。

⟹ 這不是常數校準問題。**指數爆炸那條路上沒有計費點。**

### 8.1 拆弧(問題 a):**拆,D1 先**

正當理由是「**這是兩件不同的事**」,不是「這樣不破壞相容」:

* **D1** 是**代價**缺陷——同一件事做得太貴。
* **D2** 是**計量**缺陷——貴不貴沒有人在數。

互不蘊含:修好 D1,錶仍然不存在(只是這條路變便宜了);
修好 D2 而不修 D1,十四層巢狀會變成 `#fuel_exhausted` ——**從掛住變成合法地失敗**,
有界了,但普通程式碼開始壞掉。

⟹ **順序是 D1 先、D2 後**,而這是排序理由,不是合併理由。

### 8.2 D1 的修法(問題 b):採 `Arc<ComboVal>`,**明說止於 n²**

**R-1** `EvalContext.scopes` 與 `Value::Thunk.closure` 的元素改為 `Arc<ComboVal>`。
三個可能擋路的已於 §7.3 逐一查證清空(不被就地改寫／相等性為結構相等／磁碟格式不變)。

**R-2 上界寫進工單與 CHANGELOG:代價由 2^n 降為約 n²,不是 n。**
`let frame = c.clone()` 仍深複製該層的 `ComboVal` 結構。
要到線性須把 `Value::Combo` 也 `Arc` 化,**不在本弧**。
不寫下來,下一個人會以為這條路已經線性。

**R-3 封存的效果不得改變。** 本弧只改代價。SPEC_04 §2.1／§3.1 的詞法作用域行為
是承重的(§7.2 的 spike 只用於界定語義面,**不是提案的修法**)。

### 8.3 D2 的修法(問題 c):錶要裝在工作上,不是裝在語法上

**不採**「改寫 SPEC_08 §3.2 去對齊引擎實際在數的東西」。理由:
§3.2 現行定義(「限制單次收斂觀測涉及的**節點展開與遞迴總量**」)正是使 `%fuel`
成為一條**安全性質**的那個定義;改成「已求值 AST 大小」會讓一支小程式可以做無界的工作,
而 `%fuel` 就不再是任何東西的上界。REAL_01 §10 的 MBU 計費表是**跨引擎規範性**的,
它指的必須是同一件事。

**R-4 判準,不是清單**:

> **凡其代價不由「已求值的 AST 大小」決定的操作,必須計費。**

寫成判準而非清單,因為清單會過期而判準不會——**而且這條判準本來就會抓到 D1**:
一個十六層的字面值,已求值的 AST 是線性的,工作是 2¹⁶。

判準要抓的第一個對象已經指認出來:**`force_recursive` 的金額 0**。
它連介面都接好了,缺的只是金額——這是判準落地成本最低的一格,
也說明了為什麼要立判準而不是列清單:**清單會漏掉「已經在那裡但寫著 0」的那一種**。

**R-5 本弧只立判準與最小落地,不做全面計費普查。**
普查(把判準套到每一個熱迴圈)另計,否則本弧沒有邊界。

### 8.4 射程

**進**:`lib.rs:82`(`scopes` 型別)、`value.rs:237`(`closure` 型別)及其約 67 個使用點、
`Cargo.toml`(`serde` 的 `rc` feature)。
**不進**:`Value::Combo` 的 `Arc` 化(R-2)、全面計費普查(R-5)、
`seal_defining_scope` 的**語義**(R-3)、D2 的實作(§8.1,另弧)。

**(c) 錶裝在工作上,並以判準立法**。批准後我出工單與探針。

### 9.5 探針

| | 斷言 | 基線 |
| :-- | :-- | :-- |
| **C0** | **詞法作用域穿過 1／3／6 層封存仍解析為 `6`** | 綠 |
| C1 | 一層 200 欄位仍在預算內完成且 `z.f199 = 199` | 綠 |

**C0 是整條弧掛著的那支控制。** 三支紅都是「這件事會完成」,而讓巢狀 combo 完成
最便宜的辦法就是不要封存它——那正是診斷 spike 做的事。C0 綠著,那條路就被封死。

RSS 已在偵察期直接量過(§2)。

**預算 15 秒是刻意寬鬆的**:今天這些案例根本不會結束,修好之後約 0.1 秒,
中間地帶不是本弧要裁的邊界,寬預算讓探針不會因機器負載而誤紅。
