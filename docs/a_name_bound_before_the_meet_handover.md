## 0. 判準（規格原文）

*   **D118（本卡是後一半）**：一個名字解析到寫下它的那個節點——**交會之後的那個節點**。同一組寫入不論分組一個答案（與 D101、D117 同）。前一半「在哪裡被強制都一樣」已由 Q-102 落地。
*   **D118 Q2**：私有欄位只對寫在宣告它的字面裡的名字可見；兩邊都宣告了同一個私有鍵時，兩邊都讀到交會後的值（`SPEC_04` §3.1）。
*   **`SPEC_05` §5.1**：泛型的具現化是對參數維度的交會——`@IntBox: @Box & { ~@T: @int }`，`{ value: "hi" } & @IntBox` 擋下（D117 之後是 `{ value: ⊥ }`）。
*   **D117**：交會留下的欄位衝突不帶訊息（訊息隨先後而變）。
*   **D110**：根上的名字讀根；宇宙自己的合併（工作集、根上的寫入）在根上交會。
*   **`SPEC_07` §1.1.2 Q-098 判例**：同一組寫入不論分成幾次演化、寫在一檔或分檔，提交後的根相同。

## 1. 缺陷

〔量，`v0.103.0` 標籤建置，空目錄 `oo eval`〕

*   **交會在綁定之前**：`({ p: @int, s: p } & { p: 5 }).s` ⟹ `@int`（兩向同；寫成一個字面 `{ p: @int, s: p, p: 5 }.s` ⟹ `5`）；`({ s: p } & { p: 5 }).s` ⟹ `_`；巢狀、算術、閉包、經路徑、三方、交會後再交會同。
*   **兩邊都有的欄位當場交會，名字還沒落到節點**——兩個字面交會與**同一字面重複的鍵**皆然：`({ p: @int, s: p + 1 } & { p: 5, s: @int }).s` ⟹ ⊥；`{ p: @int, s: p + 1, p: 5, s: @int }.s` ⟹ `@int`（應 `6`）；`{ s: p, p: 1, s: 2 }.s` ⟹ `2`（應 ⊥）。
*   **泛型不具現化**：`SPEC_05` §5.1 的 `{ value: "hi" } & @IntBox` ⟹ `{ value: "hi" }`。
*   **私有鍵**：兩邊都宣告了 `~s`，`{ p: { ~s: 1, a: 2 }, q: p & { ~s: _, peek: ~s }, r: q.peek }.r` ⟹ `_`（應 `1`）。
*   **提交後**：`r: { z: y } & { y: 5 }` 就地、`r: { z: y }` 與 `r: { y: 5 }` 一檔、兩次演化、兩次提交——`_.r.z` 皆 `_`（應 `5`）。
*   〔讀〕`unify.rs` `merge_axis`：兩邊都有的鍵一律當場 `unify_internal`，兩個 thunk 就地求值，此時交會後的節點還不存在；單邊的欄位 thunk 留在原字面的框裡，交會後沒有人把它的框換成交會後的節點。

## 2. 依據；位址

*   **D118**（裁定已下）。〔驗收方在 Q-102 量過的兩個限制〕(1) **不得在交會時改寫存著的閉包**——thunk 的身分編碼（`bn_serial`）把閉包框整個內嵌序列化，換成交會後的大框會讓兩個 n 欄記錄交會的成本約 n³、而且根移動；(2) **兩邊都有的欄位要延後交會**，連同一字面重複的鍵。
*   **位址**：不讀名字的值根不動（g2，含 `c: { b: 2 }`、`r: c`、`r: c` 與 Q-102 的根）。一檔、兩次演化、兩次提交三者同根（r5，與 v0.103.0 同）。會移動的：交會出、而欄位讀到交會後節點名字的值（例 `r: { z: y } & { y: 5 }` 就地提交 `1f01ed3d…` → `64fe56dc…`）。

## 3. 射程＝不變式（不是機制）

*   **M1 交會的欄位讀交會後的節點**：一向、另一向、只有另一邊有的名字、巢狀、算術、閉包、經路徑、被一個也有同名的讀者讀、三方、交會後再交會、展開（r1）。

**射程**：**同一組寫入，任何分組、一個字面，讀到同一個答案**——延後的交會再交會也是。合成框不是任何人寫的節點，在它上面找到的值不換框。
