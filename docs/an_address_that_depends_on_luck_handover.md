## 2. 缺陷 A

〔量〕隔離乾淨——**成因是「引用根」，與 blur 無關、與 fuel 無關**：

| 源碼 | commit | status |
| :--- | :--- | :--- |
| `v: <<_.>>` ＋ fuel 受限 | ✅ | ❌ `#object_undecodable` |
| `v: <<_.>>` **無 fuel 限制** | ✅ | ❌ |
| `v: <<f>>`（非自我引用）→ **C2 看守** | ✅ | ✅ |
| blur 但無自我引用 → **C3 看守** | ✅ | ✅ |
| 普通提交 → **C1 看守** | ✅ | ✅ |

錯誤訊息為 `recursion limit exceeded at line 1 column 8481` ⟹ 序列化產物是**自我巢狀**的。

**⚠ 不得用「提高遞迴上限」處理。** 那只會把毀倉的門檻往後推。
**寫入時就該知道自己寫了一個讀不回來的東西**——與 REAL_03 §6.6 的重算義務同族：
**任何以 CAID 取得內容的路徑必須於解碼後重算並比對**。
若寫入端不做同樣的往返檢查，「成功」這兩個字沒有依據。

**射程須含**：`<<_.>>` 之外的其他自我引用形（`<<^.>>`、深層自我引用），逐一回報。

〔量〕

| 條件 | 結果 |

〔讀〕**crate 內無平行**（無 rayon／crossbeam／dashmap）⟹ 不是執行緒。

**候選源（偵察未定位到行，這是你的工作）**：Rust 的 `HashMap`／`HashSet`
**預設 hasher 逐行程隨機播種**。求值路徑上至少有
`EvalContext::dep_collector: Option<HashSet<String>>`（`lib.rs:148`，`:3381` 被迭代）、
`force_memo`／`force_memo_rev`／`unify_memo`（`lib.rs:745–748`）、
`compute_ranks` 內的 `HashSet<String>`（`eval.rs:879`）。

> **REAL_03 §6.7 第三條 MUST 已為序列化鍵序禁止此來源**：「不得取自**行程內的雜湊表
> 迭代序**、插入序或任何與該值無關的來源」。**本項是求值順序，同族不同地點。**

**⚠ fuel 是放大鏡不是成因**（〔量〕一個欄位時即使 fuel 受限也穩定）。
**不要去修 fuel 的計量**——要修的是順序。
