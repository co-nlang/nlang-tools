## 1. 缺陷

### 1.1 五個旋鈕不做事(兩點法,2026-08-09)

每個旋鈕都用**同一份輸入、兩個旗鼓相當的值**量,看門檻是否移動。
**只設一個值而「沒事發生」不算量測**——那分不出「旋鈕無效」與「輸入沒碰到那道閘」。

| 旋鈕 | 暫存後讀得回 | 生效 | 證據 |
| :-- | :-- | :-- | :-- |
| `fuel` | ✓ | **✓** | `5` → `#fuel_exhausted`;`100000` → `_` |
| `strategy` | ✓ | **✓** | 同輸入:`#strict` → `_\|_`;`#blur` → `#blur` |
| **`timeout`** | ✓ | **✗** | `timeout: 1`(毫秒)之下,一個 **2286 ms** 的運算**正常跑完** |
| **`max_branches`** | ✓ | **✗** | 上限 `2`,分支算術 **11 支全部存活**(這就是 `eval.rs:2043` 那道閘) |
| **`max_unification_depth`** | ✓ | **✗** | 二分臨界**恆為 256**(＝預設值);旋鈕設 8／64／256／4000 **皆不動** |
| `max_lifting_depth` | ✓ | **✗** | **全樹從未被讀**——**O39 已裁:不在本弧**(§3) |
| `max_pattern_nodes` | ✓ | **✗** | 同上 |

### 1.2 七個旋鈕一個都提交不了

```
~%Config.fuel: 7            → evolve ok,commit: Error: Commit failed
~%Config.strategy: #strict  → evolve ok,commit: Error: Commit failed
~%Config.max_branches: 8    → evolve ok,commit: Error: Commit failed
x: 1                        → commit 成功              ← 控制
```

**視界參數只能活在暫存區,活不過一次提交。**

## 2. 裁定(用戶已批 2026-08-09)

### O37｜視界參數**不進歷史**

理由(用戶):**要保存視界參數的唯一條件是 CAID 一致性,而那已經記在 CAID 裡**
——SPEC_08 §3.2.1 明文要求 `#blur` 的 CAID **必須**包含視界參數。
使用者若真要提交,**自己觀測出來再存到別的欄位**。

**落地形式取 (b) 而非 (a)**(驗收方判斷,用戶已批):

* (a) 有 `~%Config` 就整次 commit 失敗
* **(b) commit 照常進行,`~%Config` 留在暫存區不進去,並明說它沒被提交** ← **採此**

理由:一份檔案裡同時有 `~%Config.fuel: 7` 與 `x: 1` 時,(a) 會讓一個普通寫入
**因為跟旋鈕同檔而被連坐**。「不進歷史」說的是它**不是歷史**,不是它**會毀掉歷史**。

**「明說」不可省**——靜默丟棄踩到 D36 那條線的反面:
**沒有義務可以靜默,有東西被丟掉不行。**

### O38｜直接修,不設過渡

用戶已批。**五個旋鈕從未生效過,不可能有人依賴它們的失效。**

### O39｜`max_lifting_depth`／`max_pattern_nodes` 不廢止,掛帳之後實作

用戶理由:廢止前要先論證「當初的設計沒有必要」,而那個論證沒有做;
引擎本來就還有許多未實作項。**⟹ 不在本弧射程。** 已記入 ENGINE_SYNC。

## 4. 一個我沒有定位到的點,寫成待測項而不是假說

`check_resources`(`lib.rs:198`)讀 `self.max_unification_depth`。全樹只有**一個** 256
(`lib.rs:158` 的預設值),所以那道閘讀到的就是**預設值**,不是設定值。

三個 `EvalContext::new` 建構點:

| 位置 | 是否套用 `~%Config` |
| :-- | :-- |
| `universe.rs:281`(**evolve**) | **否**——只設 `staged`／`horizon_salt`／`privilege`／`in_evolve` |
| `universe.rs:840`(**observe**) | 是,七個旋鈕全套 |
| `lib.rs:2511`(`eval_context()`) | 是,自引擎自身的 `sys_root` |

evolve 那個不對稱是真的。**但我測過了,它不是完整解釋**:
把運算式**直接寫在被觀測欄**(走 observe 路徑)`~%Config.max_unification_depth`
**一樣不生效**——depth=8 與 depth=4000 在 300 項時**同樣** blur。

⟹ **值到不了那道閘,而我沒有定位到它在哪裡漏掉。**
`sub_context` 是 `ctx.clone()`,不會重設。**這一節是給交付方的待測項,不是結論。**

〔本輪已有一次讀碼假說被自己的量測推翻(evolve/observe 那個),故此處明寫界線。〕

### 5.1 校準(2026-08-09,基線 `dev 9cff223`)

**兩支控制、三支釘綠;五支紅各自紅在自己的理由上:**

| # | 基線訊息(摘) |
| :-- | :-- |
| R1 | `a 2.3-second computation completed under timeout: 1 — the timeout knob does nothing: 19999900000` |
| R2 | `a cap of 2 left as many branches as a cap of 64 — max_branches does nothing.` |
| R3 | `the depth threshold did not move with the knob (16 → 256, 300 → 256)` |
| R4 | `a commit failed because a horizon knob shared the file: Error: Commit failed` |

**R5 目前紅在 R4 的缺陷上,不是紅在自己的主張上。** 它的 LIVENESS 守衛先擋下來

一個獨立的檢查**,而在那之前它是一個**相依的紅**。這一點寫出來,免得交付方
以為讓 R4 綠就自動有了 R5。

**P2 今天是空過的,而且是刻意的**:`~%Config` 那側根本提交不了,`head_root`
回 `None`,比較被跳過。**R4 綠掉的那一刻 P2 才開始真的比對**——它從那時起
就是「旋鈕是工作階段狀態」與「旋鈕進了你的歷史」之間唯一的東西。
〔空過的釘通常是缺陷(見 W8′-a 的 P3);**此處空過是被 R4 擋住的,而 R4 是本弧的紅**,
故不是同一回事——但仍寫明,不讓它看起來像一支已經在保護什麼的釘。〕
