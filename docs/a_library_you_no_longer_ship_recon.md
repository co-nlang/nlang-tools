# A library you no longer ship — 偵察

> Queue ID **Q-025**。基線：引擎 `v0.22.0`／規格 `v0.22.0-draft.1`。
> 設計依賴：`STATUS` **O50**（根以摘要指名標準根）、**O54**（只 hydrate 帶 sentinel 的根）、
> **O55**（引擎得持有一張歷史標準根表，已裁 2026-08-14）。
> 規格面：`REAL_03` §6.8（三條 MUST ＋自陳缺口）。
>
> **本檔是偵察，不是工單。** 它量到的東西改變了 O55 當初被裁時所記的代價，
> 因此在開工單之前需要一次補裁。**明確不做**：不動標準根的內容
> （`/add` 孤兒、SPEC_09 兩張型別表都不在本弧射程內——它們是本弧的下游）。

## 1. 為什麼現在問這個

`REAL_03` §6.8 立了一條 MUST：**引擎讀到自己不具備的標準根摘要時，必須拒絕開啟該根**，
且不得以自身的標準根代入後繼續。那一條是安全條款，擋掉「兩個宇宙、同一個位址」。

它的副作用是一堵牆：**引擎今天只持有一份標準根**，所以「改一個內建」等於
「所有既有的倉都被指名拒絕」。O55 就是那堵牆上的門。

而 §6.8 自己記了一則自陳缺口：核心規格**尚未**給出標準根的完整清單，
已知兩處不一致（`/add` 孤兒、SPEC_09 §2.1 與 §2.5 兩表互不相同）。
**要修那兩處，就必須動標準根；要動標準根，就必須先有門。**

## 2. M1 — 至今只存在過一份標準根

〔量 2026-08-15〕`root_with_system()` 與 `builtins/` 在 `v0.20.0 → v0.21.0 → v0.22.0`
之間**逐位元組未動**（`git diff --stat` 空）。

| 引擎 | 它建出的標準根摘要 |
| :--- | :--- |
| v0.20.0 | 〔無 sentinel——該版把整張表逐位元組寫進每一個根〕 |
| v0.21.0／v0.22.0 | `65f52e2d…b2bcbe72` |
| v0.22.0＋一筆（本次為量測而建） | `c8b0d4b8…71021413` |

⟹ **今天要建的那張「歷史表」只有一列。** 這不是把 O55 降級的理由，是相反的理由：
**現在是這張表最便宜的時刻**，門在只有一列時裝，比在有五列時裝便宜。

## 3. M2 — 牆是真的，而且對稱

〔量 2026-08-15，三個引擎、兩種倉齡，每格皆實跑 `oo log`〕

**v0.20.0 寫的倉**（根自足，無 sentinel）：

| 讀者 | 結果 |
| :--- | :--- |
| v0.22.0（控制組） | `commit hash:sha256:v1:cc322dab…` |
| v0.22.0＋一筆 | `commit hash:sha256:v1:cc322dab…` — **逐字元相同** |

⟹ **O54 成立且已交付**：舊倉不被碰，M4 的假 corrupt 指控消失。
兩個標準根不同的引擎得到**同一個** commit 位址，這是 hydration 確實沒有跑的強控制。

**v0.22.0 寫的倉**（根以摘要指名）：

| 讀者 | 結果 |
| :--- | :--- |
| v0.22.0（控制組） | `commit hash:sha256:v1:022cc3c4…` |
| v0.22.0＋一筆 | `Error: refusing root: standard root digest 65f52e2d… is unavailable` |

**反向亦然**：v0.22.0＋一筆寫的倉，被沒有那一筆的 v0.22.0 讀 ⟹
`refusing root: standard root digest c8b0d4b8… is unavailable`。

⟹ 牆**對稱**：不是「新引擎讀不了舊倉」，是**任兩個標準根不同的引擎互相讀不了**。
拒絕本身照 §6.8 是**對的**，指名也**確實指出所缺者為何**。要修的不是拒絕，是可得性。

## 4. M3 — 今天寫下來的程序，正好與 O55 相反

`crates/interpreter/src/genesis.rs` 第 1–4 行：

```
// Genesis seed CAIDs — computed once at genesis freeze using content_hash_v1().
// DO NOT modify. If root_with_system() changes, update these by running:
//   cargo test seed_caids_are_stable -- --nocapture
// and copy the printed "UPDATE:" lines into the constants below.
```

〔量〕該檔釘了 **26 個** `SEED_*` 常數。

⟹ **引擎裡唯一寫下來的「標準根改了怎麼辦」程序是：把釘改掉。**
而「把釘改掉」正是「舊的那一份不再存在」。O55 要的是相反的事，
所以本弧必然要動這個檔的語義——**它現在是一組釘，之後要變成一張表的第一列。**

## 6. M5 — 三個家，而分辨它們的軸不是大小

那張歷史表可以住在三個地方：

| | 家 | 舊表怎麼取得 |
| :-- | :--- | :--- |
| **A** | 引擎程式碼保留歷代 `root_with_system_vN()` | 重新建構 |
| **B** | 引擎內嵌歷代標準根的正準位元組 | 直接載入 |
| **C** | **標準根本身是倉裡的一個 CAS 物件** | 從倉裡讀，位址自證 |

**大小軸**〔量 20 次提交的 `.oo/objects` 總位元組〕：

| | 20 次提交 | 1 次提交 |
| :--- | ---: | ---: |
| v0.20.0（表逐份內嵌進每個根） | 1,432,894 B | 68,544 B |
| v0.22.0（表由引擎持有） | 30,240 B | 957 B |
| v0.22.0 ＋ C（表在倉裡存一份） | ≈ 97,600 B | ≈ 68,300 B |

⟹ **C 在任何歷史長度上都不比 O50 之前更差**（連只有一次提交時也是 68,286 < 68,544），
而在 20 次提交時仍比 O50 之前好 **14.7×**。**C 沒有把 O50 賺到的東西還回去**——
O50 省的是「**每個根**一份」，C 付的是「**每個倉**一份」。

**真正分辨它們的軸是：那份標準根由誰提供。**

*   A／B：由**引擎**提供。對等點取走一個根，若它的引擎建置不同，
    那個摘要**永遠**解不開——`peer fetch` ＝ `get_value`（O35），
    所以這在線上就是「歷史可以傳過去，但傳過去的一半打不開」。
*   C：由**倉**提供，並由它自己的位址自證。倉重新變成自足的，
    對等點連表一起取走。**但那份標準根從此是對方供給的資料。**

⟹ **C 的代價不是大小，是它把標準根搬上了 `%builtin` 那條信任路徑。**
標準根裡是 26 個以名字指名的內建（`math.add`…），而〔既有掛帳，Inbox〕
**使用者資料中的 `%builtin` 今天未被拒絕，名字是唯一憑證**——
一份敵意的標準根可以指名 `process.exit`。在 A／B 下那個洞碰不到標準根；
在 C 下它就在承重路徑上。

**這一項在 O55 被裁時不在桌上。**

## 8. 明確不做

*   不動標準根的**內容**。`/add` 孤兒與 SPEC_09 兩張型別表是本弧的**下游**，
    不是本弧的一部分——它們正是「門裝好之後第一批要走的人」。
*   不動 §6.8 的三條 MUST 之中的前兩條（不得內嵌、以單一摘要指名）。
    本弧只可能動第三條（無法解析時指名拒絕）的**適用條件**。
*   不碰 `.oo/format`／`.oo/objects.format`。C 若中選，標準根是 `objects/` 底下的
    一個普通 CAS 物件，**佈局不變**——`layout` 不需要再撥一次。
