## 1. 缺陷

〔量，標籤建置；腳本 `nlang-baselines/acc/q95/m.py`、`m2.py`、`m3.py`、`m4.py`〕

*   **形**：先提交 `d: { b: 3 }`、`b: d.b`；之後一次提交寫 `c: { b: 2 }`、`...c`。v0.96.0：**evolve 退出碼 0，提交印 `#conflict at b` 後成功，`_.b` 是 ⊥ `#conflict`**，`_.c.b` 是 `2`。v0.93.0 在 evolve 以 `#conflict at b` 拒絕。
*   **同族**（v0.96.0 皆收下、⊥ 進根）：鍵上存別名 `b: n`、施用 `b: n + 0`、記錄裡的讀法 `b: { k: d.b }`；`c` 先提交、之後只寫 `...c`；兩次演化先 `c` 後 `...c`；來源本身是讀法（`c: { b: e.b }`，`e.b` 是 2）。
*   **同一個相撞，今天會拒的**（v0.96.0）：同一檔寫、兩次演化（鍵在暫存裡）、欄位寫入 `b: 2`、點號寫入、座標層 `r: { ...c }`、巢狀 `s: { r: { ...c } }`、重攤（`...c` 先、`c` 後）、鍵上存答案 `b: 3`。
*   〔讀〕`evolve_spread` 第一次落地時對根的單調檢查（G2-S）以 `engine.unify(root_val, v)` 判：一份新的引擎層上下文，看不到根與暫存；鍵上的配方 `d.b` 在那裡讀成 `_`，與什麼都不衝突。欄位寫入那條路有「以兩邊的答案判」（`evolve_field` 的 `kept` 與其後的檢查），重攤那條路有 Q-093 R-2 的一致檢查（演化上下文），所以會拒。
*   v0.94.0 起的回歸（v0.93.0 那一格拒）。
