# 偵察：一個取決於印表機的位址

> 起因：v0.54.0 把 `Code` 的身分從 Rust `Debug` 換成規範性的 Expr 節點表之後，
> `Thunk`（`0x17`）是「第二個實作算不出位址」那一族**唯一剩下的一格**。
> 量測用 `v0.55.0` 標籤建置。known-answer `add (1,2)`→`3`／對照 `(1,3)`→`4`。

---

## 1. 一句主張

〔讀 `bn_serial.rs:152`〕`Thunk` 酬載第一項是 `encode_string(&expr.to_nlang(0), buf)`
——**位址對一個 pretty-printer 的輸出算雜湊**。

〔讀 `SYNTAX_02` §4.12〕該款逐字只要求：輸出**必須可被文法讀回**、且**必須讀回同一個值**。
〔查〕**規格全文沒有任何一條規定那串字的逐字形**（空白、括號皆無規範）
⟹ **一個印成 `1+1` 而非 `1 + 1` 的實作完全合規，而它算出不同的位址。**

## 2. 而這件事是可以正面示範的，不只是「規格沒寫」

〔量〕`v: 1 + 1` 會在倉裡留下一個 Thunk，其位元組逐字是

```
{ v: { ~%__nlang_thunk: #true  ~%__nlang_expr: 1 + 1  ~%__nlang_closure: [] } … }
```

| 源碼 | 根位址 | 存下來的 expr |
| :-- | :-- | :-- |
| `v: 1 + 1` | `5ab20106…` | `1 + 1` |
| `v: 1+1` | **`5ab20106…`** | `1 + 1` |
| `v: (1 + 1)` | **`5ab20106…`** | `1 + 1` |
| `v: 1 + 1 + 1` | `20d63171…` | `1 + 1 + 1` |

⟹ **位址不取決於你怎麼寫，取決於 `to_nlang` 選了哪些空白與括號。**
**印表機是承重的，而規格沒有承重它。**

## 3. 與 `Code` 那一格的差別（重要，因為它改變了修法的理由）

`Code` 修補前的病是**兩種呈現**：耐久位元組存 `to_nlang`、位址用 Rust `Debug` 算
⟹ 第二個實作**連起點都對不上**。

**`Thunk` 不是那樣**〔讀 `store_codec.rs:571` `write_thunk`〕耐久形的 `EXPR` 欄位**也是** `expr.to_nlang(0)`
⟹ **耐久與身分用同一個呈現，兩者一致。** 病只剩一個：**那個呈現沒有被規範。**

## 4. `to_nlang` 對結合性是忠實的 ⟹ 本弧沒有碰撞可修

〔量〕`v: (1 + 1) + 1` → `20d63171…`（存 `1 + 1 + 1`）；`v: 1 + (1 + 1)` → `2424e668…`（存 `1 + (1 + 1)`）
⟹ **右結合的括號被保留，兩棵不同的樹沒有被印成同一串字。**
**⟹ 修法不是在修一個碰撞，是在移除一個依賴。** 這一點要寫進工單，否則交付會去找一個不存在的紅。

## 5. ⚠ 本卡沒有紅探針，與 Q-050 同一個理由

缺陷是**跨實作的可重算性**，**一個二進位無法表現它**——本實作的印表機當然自我一致。
⟹ **基線會是全綠，而「全綠不構成修好了任何東西的證據」。**
補償要求與 Q-050 同形：交付須報**修前後位址**（值要變、等價類不變）＋**紀元範圍**。
**⟹ 但本弧比 Q-050 便宜得多**：規範表已經存在（v0.54.0 的 Expr 節點表，36 列），
修法是把 `encode_string(&expr.to_nlang(0), …)` 換成 `encode_expr(expr, …)`。

## 6. 修法：甲，而乙要被明文否決

*   **甲　身分改用 Expr 節點表**（v0.54.0 已規範）⟹ 印表機的逐字形不再承重。
*   **乙　把 `to_nlang` 的逐字輸出規範下來**（空白、括號、欄序逐一釘死）。
    **否決，理由是結構性的不是偏好**：那會讓**每一個排版決定都永久成為 Layer 1 破壞性變更**
    ——換一個空白就是換所有 Thunk 的位址。**一個語言不該把排版鎖進身分。**

## 7. 兩件相鄰的發現，**都不在本弧**，各自入 Inbox

**(a) `=` 對 Thunk 強制求值（外延），而位址是內涵的。**
〔量〕`((1 + 1) = 2)` → `#true`、`((1 + 1) = ~%Math./add (1,1))` → `#true`
（對照 `((1 + 1) = 3)` → `#false`）⟹ `=` 會 force。
而 `v: (1 + 1) + 1` 與 `v: 1 + (1 + 1)` 的**根不同**（`20d63171…`／`2424e668…`）
⟹ **`=` 判為相等的兩個東西，位址不同。**
**⚠ 這不違反任何已寫下的條款**（§6.7 第二條治「分得開 ⟹ 位址須相異」，沒有治反向；
§6.9 治「同位址 ⟹ 同結果」，也不是反向）⟹ **與 α-等價那一列同族**，一併待裁。

**(b) 兩個同樣純、算出同一個值的式子，一個被留成 Thunk、一個被換成結果。**
〔量〕`v: 1 + 1` → **留 Thunk**（根 `5ab20106…`）；
`v: ~%Math./add (1,1)` → **沒有 Thunk**，根 `b8f0fe91…`，
**而那正是 `v: 2` 的根**（`b8f0fe91…`，逐字相同）。
〔讀 `universe.rs:235`〕該處只在 expr 不屬一串被排除的種類時才包成 Thunk。
⟹ **D46 ① 裁「`#pure` 的 thunk 留在根裡」，而今天只有一部分的純式子留得住**
——**是刻意的窄，還是半落地，未知。** 與 **O79／D46** 同族，入 Inbox。
