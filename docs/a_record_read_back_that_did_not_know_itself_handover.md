## 1. 缺陷

〔量，`v0.105.0` 標籤建置；eval 在空目錄，提交在新宇宙〕

*   **之後的寫入到不了讀回來的記錄**：`h: { k: @int, r: k }` 再提交 `h: { k: 5 }` ⟹ `_.h.r` 是 `@int`；同兩行寫成一檔 ⟹ `5`。兩次演化、一次提交也是 `@int`（不是提交的事：工作集成員也是讀回來的）。一檔根 `f24b7d05…`，兩次演化與兩次提交 `2b25181b…`。點號寫 `h.k: 5`、清單 `[k]`、巢狀 `{ t: { u: k } }`、`^.k`、私有鍵 `~k`、聯集 `k | "s"`、鏈 `z: r`、路徑 `a.k`、`{ z: k }.z` 皆然。

## 2. 依據；位址

*   **不須新裁定**：D118 與 Q-103 的不變式直接回答；一檔已得 `5`。
*   **位址**：節點身分是求值的機制——**不進身分、不進相等、不存**。r1：三種寫法同根（探針逐格寫明）；g2 單次寫入的根逐位元組不動；Q-104 r4 的根 `006795a8…` 不動。
*   **就地交會的根會移動**（驗收方的參考如此；破壞性，收尾時記 `CHANGELOG`）：Q-103 寫下的交會後節點的視圖，是那個節點的複本，它讀名字的欄位仍帶著被它取代的舊框；身分編碼內嵌框 ⟹ 一個讀自己名字的 N 欄記錄就地交會，寫成 N 份 N 欄、每欄再帶 N 欄（〔量，v0.105.0〕400 欄一檔 >300 s、15 GB，逾時）。兩次提交以前快，是因為讀錯（舊框沒被換掉）；本卡讓兩次提交等於一檔，就會走進這個洞——所以它在射程內（r4）。參考的做法：視圖裡讀這個節點名字的欄位，不帶這個節點的各個版本（名字在視圖上找到時本來就在視圖裡讀）；同一個節點的視圖各欄共用。讀數不變，根移動；v0.105.0 寫的倉照讀、照寫（驗收方量過）。
*   **不同分組之間同根不在射程**（v0.105.0 已然，Inbox「位址是內涵的」一族）——但**同一種分組每次都同根**（r3：每種分組跑四次一個根；工作集成員的檔名是隨機的）。

### 8.4 工單指名要你回答的問題

前是本工單所在提交建出來的 `oo`（v0.105.0），後是這一版。

**Q1** 讀回來的記錄怎麼知道自己是哪個節點。

判準比六個軸：鍵相同，寫下的值也相同。thunk 比式子原文，其餘比印出來的值。對得上的框 `node_id` 是 0 時，蓋上這筆記錄的 `node_id`（還沒有就新取一個）。展開來源的 `k` 是 `1`、容器的 `k` 是 `2`，值不同，來源不會被當成容器。`_.h.q` 前後都是 `1`，根是 `2e6e0abd…`。

兩框位元組相同時，判準答它就是這筆記錄。存進去的沒有另一個節點身分；鍵與寫下的值都相同，就是封框前的那一框。

`encoding<8` 的文件每份 thunk 各寫一份框，解出來是不同的 `Arc`。判準看鍵和寫下的值。每一份對得上的框蓋上同一個 `node_id`。這些文件仍走 `decode_value`，認框發生在 `combo_expr_to_value` 收尾。寫回的現行倉是 `encoding=10`。

**Q2** 宇宙自己的合併（`unify_universe`、`unify_unmetered`，`UNMETERED_MERGE`）裡，兩邊都有的欄位若是同一個寫下的欄位——式子原文相同，閉包等長，框或是同一個、或是正在交會的節點、或內容相同——留左那一份。視圖已經拿掉被它取代的舊版本，兩份編出來的位元組相同，所以根不隨寫入次序、也不隨工作集成員的檔名次序變。計費的交會（eval 裡的 `&`）仍把讀節點名字的欄位延後成待交會，不走這一判。一檔與兩次演化都是這次不計費的合併，所以同根。`h: { k: @int, r: k }`／`h: { k: 5 }` 三條路的後根都是 `2fc429bb…`，`_.h.r` 是 `5`。r3 每種分組四次一個根。

*   **攤平**：`& { r: 5 }` 再 `r: 6` 三條路拒；區間收窄 `1..` 再 `..9`；聯集；兩邊讀不同名字；四組三寫入（`r: 1..`／`r: ..9`、`r: j`、`r: @int`／`r: k`）五種分組各一根（R-2 有分根、v0.105.0 有讀錯）。
*   **視圖建原子**：中間那筆寫字串與標籤、巢狀記錄、多行字串、`v: 1 + 1`——五種分組各一根。
*   **最外框**：展開兩次、容器與展開同名、巢狀展開、展開後交會再寫——讀來源、同根。
*   v0.105.0 寫的倉由交付引擎照讀（讀數與 v0.105.0 同）、照寫（之後的寫入照新規則交會或拒）。

不一致而不是本卡的三格：`h: { k: @int, f: (x -> x + k) }` 再寫 `k: 5` 兩次提交 ⊥、`h: { k: @int, r: k + 0 }` 再寫 `h: { k: 5, r: 5 }` 兩次提交拒——第一層的值在第一次提交被強制（§6，R-2 同）；`k: 5`、`h: { r: <<_.k>> }` 再寫 `h: { r: 6 }` 一檔與兩次演化收下 ⊥、兩次提交拒——`_.` 在演化時只解到已提交的根（v0.105.0 同，Inbox「根上的 `..._.c`」那列）。
