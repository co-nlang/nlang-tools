## 0. 判準（規格原文）

*   **D118**：一個名字解析到寫下它的那個節點——交會之後的那個節點；在哪裡被強制都一樣。`SPEC_04` §2.1「$H$ 是交會之後的那個節點」（Q-103）：延後的交會也是交會做出的；任何分組一個答案。

## 1. 缺陷

〔量，`v0.105.0` 標籤建置；eval 在空目錄，提交在新宇宙〕

*   **之後的寫入到不了讀回來的記錄**：`h: { k: @int, r: k }` 再提交 `h: { k: 5 }` ⟹ `_.h.r` 是 `@int`；同兩行寫成一檔 ⟹ `5`。兩次演化、一次提交也是 `@int`（不是提交的事：工作集成員也是讀回來的）。一檔根 `f24b7d05…`，兩次演化與兩次提交 `2b25181b…`。點號寫 `h.k: 5`、清單 `[k]`、巢狀 `{ t: { u: k } }`、`^.k`、私有鍵 `~k`、聯集 `k | "s"`、鏈 `z: r`、路徑 `a.k`、`{ z: k }.z` 皆然。
*   **eval 裡交會一個已提交的記錄**：`(_.h & { k: 5 }).r` ⟹ `@int`；`r: { z: y }` 提交後 `(_.r & { y: 6 }).z` ⟹ `_`；`h: { r: <<k>> }` 提交後 `(_.h & { k: 7 }).r` ⟹ `_`。
*   對照：深一層 `h: { s: { k: @int, r: k } }` 再提交 `h: { s: { k: 5 } }` ⟹ `5`（`s` 存的是語法，讀時重新封框）；名字第一次不在字面裡的 `h: { r: k }` 兩形皆 `5`、同根；根上 `k: @int`、`r: k` 再提交 `k: 5` ⟹ `5`。
*   〔讀＋插桩〕`ComboVal::node_id`／`merged_from` 是 `serde(skip)`：從倉或工作集解碼出的記錄 `node_id` 是 0，它欄位閉包裡那一框（`seal_defining_scope` 封進去的、記錄自己的影子）也是 0。第二次寫入的記錄有 `node_id`，`unify_combo` 交會出的節點 `merged_from` 只有新那一邊 ⟹ `rebind_to_met` 認不出舊框，`r` 仍在舊框裡讀 `k: @int`。

## 2. 依據；位址

*   **不須新裁定**：D118 與 Q-103 的不變式直接回答；一檔已得 `5`。
*   **位址**：節點身分是求值的機制——**不進身分、不進相等、不存**。r1：三種寫法同根（探針逐格寫明）；g2 單次寫入的根逐位元組不動；Q-104 r4 的根 `006795a8…` 不動。
*   **就地交會的根會移動**（驗收方的參考如此；破壞性，收尾時記 `CHANGELOG`）：Q-103 寫下的交會後節點的視圖，是那個節點的複本，它讀名字的欄位仍帶著被它取代的舊框；身分編碼內嵌框 ⟹ 一個讀自己名字的 N 欄記錄就地交會，寫成 N 份 N 欄、每欄再帶 N 欄（〔量，v0.105.0〕400 欄一檔 >300 s、15 GB，逾時）。兩次提交以前快，是因為讀錯（舊框沒被換掉）；本卡讓兩次提交等於一檔，就會走進這個洞——所以它在射程內（r4）。參考的做法：視圖裡讀這個節點名字的欄位，不帶這個節點的各個版本（名字在視圖上找到時本來就在視圖裡讀）；同一個節點的視圖各欄共用。讀數不變，根移動；v0.105.0 寫的倉照讀、照寫（驗收方量過）。
*   **不同分組之間同根不在射程**（v0.105.0 已然，Inbox「位址是內涵的」一族）——但**同一種分組每次都同根**（r3：每種分組跑四次一個根；工作集成員的檔名是隨機的）。

## 3. 射程＝不變式（不是機制）

*   **M1 之後的寫入是讀回來的那個節點上的交會**：九個形，一檔、兩次演化、兩次提交同讀數、同根（r1）。
*   **M2 eval 裡的交會也是**：自己字面有的名字、沒有的名字、巢狀、引用、`^`（r2）。
*   **M3 三個寫入、任何分組都讀到交會後的節點**；同一種分組決定（r3）。
*   **M4 規模**：400 欄讀自己名字的記錄，一檔、兩次提交，60 秒內讀對（r4）。
*   **另一半——到不了的照舊**：不碰那個名字的寫入（`h: { j: 1 }` 之後仍 `@int`）；巢狀字面有自己的同名鍵（`s: { k: 7, r: k }` 仍 `7`）；**展開來源的名字讀來源，不是容器**（`{ k: 2, ...{ k: 1, q: k } }.q` 是 `1`，交會之後也是）；根上的名字；名字第一次不在字面裡（g1）。根不動（g2）。
*   若你找到另一處讀回來的值認不出自己的節點（例如另一種解碼路徑、`refine`、`squash`），一併在射程內，在 8.1 列出。

## 5. 必答（請在交付報告裡回答，逐題）

*   **Q1 讀回來的記錄怎麼知道自己是哪個節點**：判準是什麼、為什麼不會把展開來源（或任何鍵集合相同的別的框）當成容器；兩者位元組相同時你的判準怎麼答。舊編碼（框不共用、`encoding<8`）的倉怎麼辦。
