## 0. 判準

*   **提交投影每格算一次**（`SPEC_10` §2.3.1 D132 款）：提交逐欄決定存配方還是存答案（D46；預測為純、強制時做了效應的定義存答案，Q-126、D131）。為了問「它做不做效應」，它碰到的每一格只算一次；同一個記錄從第二條路再到，不再算一遍。
*   **投影時一個座標是一個值**（Q-134 的規則，`SPEC_10` §2.3.1 Q-120 款）：一個座標被好幾個讀者讀，只算一次。
*   **存下的根、讀數、效應次數不變**：與 v0.137.0 相同。

## 1. 缺陷

〔量，`acc/q138/m1.sh`、`ph.sh`；插樁 `dbg1.py`–`dbg11.py`（worktree `q138-dbg`）；v0.134.0、v0.137.0 標籤建置；每程 3 GB〕

**一、記錄從第二條路再到，就再算一遍（2^L）**：每筆都有兩條路通到下一筆的環（`n_i: { v: i, w0: n_{i+1}, w1: n_{i+1} }`），提交秒數：

| :-- | :-- | :-- |
| 8 | 0.13 | 0.08 |
| 12 | 1.67 | 0.09 |
| 16 | 37.85 | 0.10 |
| 64 | 中止（2.8 GB，49 秒） | 0.37 |

經呼叫（`c_j: id n_{i+1}`）、經清單（`l_j: [n_{i+1}]`）同；同一個環的演化 0.15 秒（Q-135）。

*   插樁〔`dbg1.py`〕：時間全在 `project_for_commit`（L=14：投影 7.24 秒，其餘階段合計 0.1 秒）。
*   成因（讀碼並反事實確認）：預測為純的 thunk，投影用 `force_each_cell` 把它強制到底，看它做不做效應、讀成不讀成 ⊥；做了就存那個值，沒做就丟掉、存配方。強制到底時一個記錄從第二條路再到，不在路徑上（`FORCING`）就再展開一次。這些值在純的環裡全部丟掉。
*   反事實〔`dbg2.py`，`Q138_ONE`：改成只強制一層〕：L=64 0.14 秒；兩張格子裡純的格逐格相同，**帶效應的格 56 格變**（存答案的格改存配方，D131 被破壞）——所以不能只強制一層，強制到底是為了看效應。

**二、一個座標被每個讀者各算一遍（N²），每次呼叫造的記錄都留著（N³ 記憶體）**：`id: (x -> { v: x })`、`k_i: id k_{i+1}`、`k_N: 7`，提交：

| N | v0.137.0 | 參考 |
| :-- | :-- | :-- |
| 50 | 1.47 秒，356 MB | 0.35 秒，85 MB |
| 100 | rc 1，2476 MB（「refusing to store a root this engine cannot read back」） | 1.43 秒，246 MB |
| 250 | 中止（2.8 GB） | 3.48 秒，554 MB |

同一條鏈的演化 1.0 秒、100 MB（Q-134：演化時一個座標只算一次）。

*   插樁〔`dbg4.py`–`dbg7.py`〕：投影逐欄，`k_i` 的秒數與 N − i 成正比；投影後常駐記憶體 N=50 338 MB、N=75 1046 MB。Q-126 的 `OBSERVED` 在投影後有 N(N−1)／2 筆（N=25 300、N=50 1225）：每次呼叫造的記錄都留著，每筆是那一段的整條鏈。
*   成因：Q-134 的座標快取只在演化時開（`ctx.staged.is_some() && ctx.memo_enabled`）；提交的上下文兩者皆否，於是 `k_0` 的強制把 `k_1…k_N` 全算一遍、`k_1` 再算一遍……
*   反事實〔`dbg9.py`，`Q138_COORD`：投影時開座標快取〕：N=100 1.40 秒、271 MB；兩張格子逐格相同。只開快取不碰一：環仍是 2^L。

**三、範圍外，但量到的**：
*   讀已提交的環（`a: { e: x, x: a }` 之後 `oo eval _.a`；或環裡的清單 `_.n0.l1`）展開到深度上限，2.8 GB 中止（v0.120.0 起；v0.137.0 同）。列印，不是提交：Inbox 新列。

*   呼叫造記錄的鏈，提交後 `OBSERVED` 仍持有 N 份巢狀副本（N=100 246 MB）：同上。

## 3. 射程＝不變式（不是機制）

*   **M1 問效應時每格一次**（r1）：每筆兩條路的環 L=64，直接讀、經呼叫、經清單三種，提交各在 3 秒內（v0.137.0 都不返回）。
*   **M2 投影時一個座標一個值**（r2）：呼叫造記錄的鏈 N=100，提交 5 秒內、3 GB 內（v0.137.0 rc 1）。
*   **另一半 g1**：九形的根、讀數、效應位元組數與 v0.137.0 相同：
    *   三種環各帶一個效應（`g: ~%Env.get`）——存答案的格存的答案不變；
    *   節點先在「它的效應在路徑上」的地方碰到，再經呼叫碰到——後者照樣存答案（「碰過」不跨欄位）；
    *   效應經環與呼叫只做一次（1 個位元組）；
    *   純的環、呼叫造記錄的鏈——根不變；
    *   **兩個環分兩半提交**（先寫一半、提交、再寫另一半）——這裡「每個節點只走一次」問出來的值與完整強制的值不同，存的是後者。
*   **這個機制的每個入口**（Q-136 的教訓）：`project_for_commit` 的兩個呼叫者——提交（`universe.rs` `commit`）與 pin 的合併（`pin_commit_merge`）；投影裡強制到底的兩個分支——預測為純的 thunk（本卡改的）、預測不純的 thunk（存它強制的值；本卡不改，§6）。
*   **探針外（驗收時量）**：兩張格子（`acc/q137/grid137.py` 832 格、`acc/q135/acc/grid.py` 800 格）；成本 `acc/q138/m1.sh`、`acc/q137/cost.sh`、`acc/q136/cost.sh` 對 v0.137.0、v0.134.0。
