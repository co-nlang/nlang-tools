## Q5 — ○ 鏈往回走

〔量〕○2 body ＝ `{ a: 1 b: 2 }`，○3 body ＝ `{ a: 1 }`。後一個比前一個小。Q4 的 Config 再暫存更極端：commit 之後立刻多一顆只有 Config 的 ○。

**讀法。**

今天的 body 是 `encode_savepoint(&self.staged)`（`record` 的第二個參數，`universe.rs:894`）。`staged` 在 commit 時被清空（或收成 Config）。所以 body **是工作集的快照**。它不是「宇宙被看到多深」的讀數：已提交的根不在裡面，觀測化約的值也不在裡面。

§3.1 標題：「Savepoint 記錄的是『看了多深』，Commit 記錄的是『它是什麼』。」
若「深度」是單調的，往回走是矛盾。
若深度可以在提交邊界歸零，那「深度」在這一節用的是工作集的基數，不是觀測深度——**用詞與實作對得上的是後者，與標題對得上的是前者。**

「看了多深」在提交之後歸零：

* 對「工作集快照」這條讀法：**是對的**。工作集確實歸零（D48：commit 清空注入目錄）。
* 對「觀測深度」這條讀法：**是錯的**。已提交的宇宙還在，深度不該跟著工作集一起沒。

兩者都要？那是 Q4 形 3：body 分開記。只要給讀法，不選。

**§8 開弧 4**：不適用。

## Q6 — 判準 (b) 與 `_|_`；不做 Q-018 的前提下

§1.7／§1.8 要分清的兩件事，**都在，而且不是同一件事。**

### (1) 沒有寫者 — 全域

`savepoint::record` 在該檔之外**只有一個呼叫者**：`universe.rs:894`，在 `save_staged` 裡。`save_staged` 的產品呼叫者是 `run_evolve`（`main.rs:463`）與 commit 的 Config 再暫存（`universe.rs:1101`）。

### (2) 觀測路徑沒有倉庫可寫 — 只綁在 `run`／`eval`／`test`


## Q7 — 體積與 GC

每一次位置移動存一份**整個工作集**的快照。〔量，標籤二進位，逐欄位 `oo evolve`，N 個相異欄位 `f{i}: {i}`〕

| N | ○ body 數 | `savepoints/` 檔位元組合計（`du -sb`＝逐檔加總） | 其中 LOG | 最後一顆 body | 逐次 `oo evolve` 牆鐘 |
| --: | --: | --: | --: | --: | --: |
| 1 | 1 | **49** | 17 | 32（`#nlang/store savepoint\n{ f0: 0 }`） | 0.016 s |
| 10 | 10 | **760** | 170 | 86 | 0.247 s |
| 100 | 100 | **42 790** | 1 700 | 806 | 9.95 s |
| 1000 | 1000 | **4 837 990** | 17 000 | 9 806 | 1 980.6 s |

趨勢是 **O(N²)**：第 k 顆 ○ 的 body 長度 ≈ O(k)，N 顆加起來 ≈ O(N²)；LOG 是 17N 位元組（每個 id 16 hex ＋ 換行），可忽略。牆鐘主要不是寫 ○（N＝1000 的目錄只有 4.8 MB），是每一次 evolve 都要 fold 已經累積的注入——那是 Q-014 工作集的成本，本卡改鑄名不會把它削掉。N＝1 的 body hex 以 `23 6e 6c 61 6e 67`（`#nlang`）開頭。

### `oo gc` 不走 `savepoints/`

〔讀〕`gc.rs:282`：「Sweep unreachable objects under `.oo/objects/` only。」`mark` 從 `HEAD` 走 CAS 引用。目錄名 `savepoints` 在 `gc.rs` 零命中。

〔量〕兩個 ○ 存在時 `oo gc --grant gc`：報告 `3 objects, 3 reachable, 0 collectable`（那 3 是 CAS），`savepoints/` 檔數與位元組不變。再種一個 `.oo/savepoints/deadbeef`，再 gc：**`deadbeef` 還在。**

### 有沒有任何路徑會刪 ○？

〔讀〕`savepoint.rs` 沒有 `remove_file`。`universe.rs` 的 `remove_file` 只打 `staged`／`pin_pending`／`effect_pending`／`abandoned`。`injections::clear` 只清 `injections/`。`migrate_layout` 只寫 `format`／`objects.format`。

〔量〕`rollback`：`savepoints/` 檔名與 LOG 位元組不變（abandoned 寫的是 commit CAID，不是 ○）。`squash`：同上。`migrate --grant migrate`：同上（連種進去的 `deadbeef` 都還在）。

**沒有。這是一個永遠成長的目錄。** 本卡若只修鑄名與序，成長曲線不變。GC ○ 或「只留最後一顆」是另一張卡，而且會碰到 D43「每一個 ○ 產生時即為持久」。

**§8 開弧 4**：不適用。

## Q11 — tip 集合能不能由不可變的 ○ 集合純導出？

能。判準成立，演算法是有限 DAG 的出度為零。

**位元組。** 目錄 `.oo/savepoints/`，跳過 `LOG`、跳過 `.partial-*`（與 `injections.rs:45` 同一條規則；`atomic_write` 的 temp 住在同一層）。每個剩下的檔名是一個 id。每個檔的**框**（combo 之外，Q15）有一行 `parents:`。讀這些行，不必解 combo、不必進 CAS。

```
ids       ← { 檔名 | 檔是普通檔、名字不以 `.` 開頭、不是 LOG }
mentioned ← ∪ { p | 某顆 ○ 的 parents 含 p }
tips      ← ids ∖ mentioned
```

空倉：`ids = ∅` ⇒ `tips = ∅`。第一顆 ○ 的 `parents` 是空集合（Q15 (i)）。

**並行。** 兩個行程同時導出同一組 tip T，各自鑄一顆、`parents = T`：磁碟上出現兩個孩子，T 不再是 tip。這是 D50 要的**分叉**（覆蓋關係分叉，偏序仍可判定：兩個孩子都嚴格後於 T，彼此不可比）。不是遺漏，不是覆寫（覆寫是身分撞檔名，那是 `mint_id` 的病，不是導出的病）。

晚到的行程若已經看見其中一個孩子，導出的 tip 含那個孩子、不含 T，寫出的是線性延伸。兩種結果都是合法 DAG，差在 `readdir` 見到誰——POSIX `readdir` 本來就不是快照，與「兩個 evolve 誰先 `rename`」是同一扇窗。D48 的注入層接受這扇窗（相異欄位的 fold 可交換）；○ 層在 D50 之下用分叉把它記錄下來。

**沒有第三種壞法，在「檔不可變、鑄名不撞」的前提下。** 導出是目錄內容的純函數。沒有一個共享格子被讀-改-寫，所以沒有 D48 那種「最後寫入者贏、值消失」。

**哪一步看起來像不可行，其實可行：** 不必原子地「拿到現在的 tip 集合」。你拿到的是**某一瞬間 `readdir` 加上當時能讀到的框**。過期是分叉，不是錯誤。不可行的是另一件事：用一個可變的 `tips` 檔當**真相**——那一步才把 Q-014 請回來。Q11 不走那一步。

不可讀的檔（半截、不是框）：與 `gc` 的 incomplete walk 同類。跳過它，等於 `readdir` 沒看見——分叉。拒絕整次 `record` 也可以，那是產品選擇，不是導出做不到。

**§8 開弧 4**：不適用。

## Q12 — 代價實測

純導出尚未進引擎。量的是**重構**：對今天已經存在的 N 個 ○ 檔做 Q11 的「開每一個、讀框」（今天沒有 `parents:` 行，所以全檔／前 256 B 都讀得到；開檔次數相同）。並排第一輪 Q7，以及**今天**在已有 N 顆 ○ 時再 `oo evolve` 一次的牆鐘與 `openat`。

標籤二進位。N＝1000 不跑。

| N | Q7 累積牆鐘（N 次 evolve） | Q7 `savepoints/` 總位元組 | 今天再一次 evolve（無 strace，中位數） | 今天 `savepoints` `openat` | Q11 開檔次數 | Q11 全檔掃描 | Q11 前 256 B |
| --: | --: | --: | --: | --: | --: | --: | --: |
| 1 | 0.016 s | 49 | **0.021 s** | **4** | 2（含本次之後） | 0.032 ms | 0.021 ms |
| 10 | 0.247 s | 760 | **0.033 s** | **4** | 11 | 0.173 ms | 0.114 ms |
| 100 | 9.95 s | 42 790 | **0.196 s** | **4** | 101 | **1.65 ms** | 1.05 ms |

今天那 4 次 `savepoints` `openat`（N＝100 逐條）：讀 `LOG`、讀上一顆 body（去重）、兩個 `.partial-*`（body 與 LOG 各一次 `atomic_write`）。**與 N 無關。** 同一次 evolve 的注入層 `openat` 是 **N＋1**（N＝100 時 102）——那才是 0.196 s 裡的東西。

純導出之下，一次 `record` 還要開 **現有的每一顆 ○**（N＝100 → 101 次）。這是 Q7 空間曲線的時間投影：第 N 次 evolve 讀走前 N 顆快照的位元組，那些快照合計 O(N²)。

**會不會把 O(N²) 的空間問題變成 O(N²) 的時間問題？**

* **漸近**：會。每次 evolve 開 N 個檔；N 次 evolve 合計開 1＋…＋N ＝ O(N²) 次。若讀全檔，第 N 次讀 O(N²) 位元組。
* **今天這組數字：不會成為瓶頸。** N＝100 時全檔掃描 1.65 ms，同一次 evolve 已經 196 ms（注入 fold）。掃描是 evolve 的 ~1/120。Q7 的 9.95 s 是 **100 次進程啟動 ＋ 逐漸變長的注入 fold**，不是 ○。把 Q11 接進去，牆鐘表上看不出差別，直到 ○ 的體積自己先成為問題（第一輪 N＝1000 已是 4.8 MB 的目錄；那一檔 33 分鐘幾乎全是注入）。

若框把 `parents:` 放在 combo 之前（Q15），常見讀取是「每檔一行」，位元組從 O(N²) 降到 O(N)。N＝100 上 header 與全檔已經同量級（1.05 vs 1.65 ms），因為最後一顆也只有 806 B。

**§8 開弧 4**：不適用。

## Q13 — 中間路線：純快取的 `tips`

第一輪 Q3 對 `LOG` 的那句話可以直接搬過來：**可以留一個 `tips` 檔，但它必須是可重建的衍生物，不能再當鑄名來源，也不能當 tip 集合的真相。**

這條路**成立**。它是 D50 與 D48 不撞車的形——不是因為有一個檔叫 `tips`，是因為**寫者不以它為輸入**。

**寫路徑（不讀-改-寫那個格子）：**

1. `readdir` 得到檔名集合（N 個名字，不開 body）。
2. 若快取存在、能解、且 **快取裡的 id 集合 ＝ 目錄檔名集合**，用快取裡的 `id → parents` 算 tip（零次讀 body）。
3. 若目錄多出一個名字（剛剛別人鑄的，或自己上次沒寫進快取），**只開那一個新檔**補進記憶體；多出很多就走 Q11 全掃。
4. 鑄新 ○（不可變、隨機 id，`atomic_write`）。
5. **可以**再 `atomic_write` 一份新的快取。這次寫失敗、被並行覆寫、或崩潰留在兩次寫之間：下次第 2 步核對失敗，重建。**覆寫快取不會覆寫 ○，也不會丟注入。**

第 5 步是衍生物快照，與上一弧偵察標過價、本弧不做的那一格同類。它可以不做。不做就每次走 Q12。做了，常見的「目錄剛剛多一顆」是 O(1) 開檔。

**什麼時候必須重建**

| 偵測 | 怎麼發現 | 代價 |
| :-- | :-- | :-- |
| 快取不存在／不能解 | `exists`／decode 失敗 | Q12 全掃 |
| 目錄有快取沒有的 id | `readdir` 名字 ⊄ 快取鍵 | 只讀新檔，或全掃 |
| 快取有目錄沒有的 id | 同上，反向（今天沒有刪 ○ 的路徑，見 Q7；若出現，這條會響） | 全掃 |
| 核對通過 | 名字集合相等 | **0** 次讀 body |

**不必每次啟動都全掃。** 啟動時做一次名字核對；相等就信快取。不一致才 Q12。沒有「魔術標記」比名字集合更便宜、也更不容易錯——計數、mtime、LOG 行數都是第一輪已經說明會穩定綠的那種。

**若有人把第 1–4 步改成「讀 `tips` → 鑄 ○ → 寫 `tips`」且第 1 步不再 `readdir`：** 那就是 brief §5.2 的病，D48 請回來。Q13 的形與那個形的差別只有一句：**核對永遠以目錄為準。**

不必回頭請裁。純導出可行（Q11），快取可選（本節）。沒有「非有共享格子不可」。

**§8 開弧 4**：不適用。

## Q15 — `parents` 的編碼

必須在 combo **之外**。今天 `encode_savepoint` 是

```
#nlang/store savepoint\n{ …combo… }
```

（`store_codec.rs:165`–`:167`）。加一行框，不要加欄位進 `ComboVal`。

建議形（不是唯一拼寫，是三個約束都滿足的一種）：

```
#nlang/store savepoint
parents: 0000000000000001 0000000000000002
{ a: 1 b: 2 }
```

id 空白分隔、**已排序**。解碼讀框、跳過這一行，combo 仍走 `write_combo`／`decode_staged`。

### (i) 空集合（第一顆 ○）

**永遠寫出 `parents:` 這一行，後面沒有 id。** 不要省略（省略與「舊檔沒有這個欄位」分不開；Q-013 已落地的 ○ 沒有這一行）。不要寫 `parent: _`——那是今天 **Commit** 單數欄位的根寫法（`store_codec.rs:490`），`_` 在 n/ 是單位元，不是空陣列。

空倉導出 tip ＝ ∅，第一顆的框就是 `parents:` 加一個換行。

### (ii) 多元素要不要正規化順序

**要。必須。** `parents` 是集合。寫出的位元組順序若跟著 `readdir`／`HashSet` 迭代走，同一組父會有 N! 種位元組。排序鍵：id 的字典序（今天是 hex，大小寫也要釘死；鑄名已是小寫）。

decode：**未排序視為編碼錯誤**（大聲拒絕）或接受後重排再比；前者比較便宜，後者比較寬。不要「讀到什麼就存什麼」。

### (iii) 陷阱：去重比的是 body 位元組

今天 `record`（`savepoint.rs:55`–`:63`）是 `prev == body`，`body = encode_savepoint(combo)`。`parents` 一旦進框，這次比較就包含它們。

若寫出前**不**排序：兩個行程導出同一組 `{A,B}`，一個寫 `A B`、一個寫 `B A`，位元組不同，去重認不出來，鑄兩顆拓樸相同的 ○。並行下看起來像間歇性——誰的 `Vec` 先插入誰贏。**這一題答成「不必排序」會在 40 並行下變成不穩的 ○ 數。**

正規化之後，同一組父 ＋ 同一份 combo ＝ 同一份位元組，去重穩定。不同父、同一份 combo 是 Q16 的另一面。

**§8 開弧 4**：不適用。
