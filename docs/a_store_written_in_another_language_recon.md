## 0. 七句承重的話

1. **`.oo/` 的 CAS 裡有兩種東西，而 Q-012 的卡片只講了一種。** 根與標準根是
   `Value` 的 serde JSON；**commit 物件根本不是 `Value`**——它是 Rust struct，
   帶 base64 的 `lattice_sketch` 與 32 個十進位整數的 digest（§1.2）。
   **「容器改用 n/ 值形」對 commit 物件不是同一個問題**，這是第一個要裁的分界。
2. **標準根在磁碟上是它自己 JSON 的 2.00×**——`"standard-root:<hex>"`，
   JSON 塞進 hex 再塞進 JSON 字串。68,126 → **136,268 B**（§1.3）。
   **這一半的浪費與 n/ 無關，今天就可以拿掉。**
3. **印表機已經幾乎是編碼器了，缺的東西可以逐一指名。** 把標準根印成 n/（21,722 B）
   再讀回來，逐行 diff 只有 **28 個 hunk**：26 個是 `%effect` 被印成註解、
   2 個是 `%val` 投影（§2.3）。**其餘 21,722 B 逐字元回得來。**
4. **語言缺兩個字面，而 `system` 軸是其中之一。** 印表機寫 `~%Cond:`，而剖析器對它回
   **⊥ `#system_reserved`**——25 個模組全部（§2.2）。這是**故意的**（Q-035 的線）。
   另一個是 **`%effect`**——v0.26.0 起它進耐久形，而印表機只能把它寫成註解，
   因為**表層語言沒有它的字面**（§2.3，此結論經判別後推翻了我的第一個讀數）。
   ⟹ **耐久形必須能表達表層語言寫不下來的東西**，這是第二個要裁的分界。
5. **編碼與身分正交，在 v0.35.0 重驗成立** ⟹ **Q-012 不是紀元弧**（§3）。
   〔量〕把根物件的位元組從 428 B 重排成 762 B（同值不同位元組），
   CAID **不變**、`inspect` 照常、`oo status` 照常。
6. **代價的方向和直覺相反：貴的不是剖析。** 〔量，20 次平均〕解析 21.7 KB 的 n/
   ≈ **7 ms**（`oo fmt` 9 ms 減去 1 行對照 2 ms），而今日讀 136 KB 標準根的
   `oo inspect` 全程 **15 ms**——**同一個數量級**，且**行程啟動支配這兩個數字**（§4）。
   `oo eval` 那 180 ms 是**求值**不是剖析，而 O35 已裁「讀取是解碼不是求值」。
7. **讀相容的破壞已經是響亮的，不是無聲的。** 〔讀〕`ensure_supported_encoding`
   只接受 1–4，其餘**拒絕開啟**（§6）。⟹ Q-012 只需要 `encoding=5`，
   而舊引擎會**明說它讀不懂**，不會誤讀。

## 1. 現況全帳（`v0.35.0` 全新倉）

〔量〕`app: { k1: 1 }`（**15 B** 源碼）→ `oo init` → `evolve` → `commit -m t`。

### 1.1 倉裡有什麼

| 檔案 | 位元組 | 是什麼 |
| :--- | ---: | :--- |
| `.oo/format` | 9 | `layout=2` |
| `.oo/objects.format` | 11 | `encoding=4` |
| `.oo/HEAD` | 79 | `hash:sha256:v1:e2facfdf…` |
| `objects/…/7038e250…` | **136,268** | **標準根**（`"standard-root:<hex>"`） |
| `objects/…/e2facfdf…` | 390 | **commit**（不是 `Value`） |
| `objects/…/932a9f9d…` | 428 | **根**（是 `Value`） |
| **合計** | **137,185** | 源碼 15 B ⟹ **9,146×** |

**標準根佔 99.33%**，而它自己有一半是 hex 的膨脹（§1.3）。

### 1.2 兩種物件，兩種拼法的 digest

根物件（428 B，全文）：

```json
{"Combo":{"closed":false,"data":{"app":{"Combo":{…"data":{"k1":{"Atom":[{"Int":[1,[1]]},0,null]}}…}}},
 …,"system":{"__nlang_system_digest":{"Atom":[{"Str":"7038e2504b…f37911"},0,null]}},"types":{}}}
```

commit 物件（390 B，全文）：

```json
{"kind":"Standard","meta":{"author":"oo-cli","message":"t","timestamp":1787672079097},
 "parent":null,
 "root":{"algorithm":"Sha256","digest":[147,42,159,157,214,34,151,167,…],
         "lattice_sketch":"/5/5p9rC1d8MAP+fu4Lu9/3UgAEAgMC0qsi607SNAQ…","masa_ref":"Top","version":"V2"}}
```

三件事逐字可見：

*   根是 **Rust `Value` enum 的外標籤 serde**（`{"Combo":…}`、`{"Atom":[…,0,null]}`），
    **不是一份 n/ 文件**。`Atom` 那個三元組的 `0` 是效果標籤、`null` 是 span。
*   commit **完全不是 `Value`**：`kind`／`meta`／`parent`／`root`，加 base64 的
    `lattice_sketch`。它是**協定結構**，不是使用者的值。
*   **同一個倉裡 digest 有兩種拼法**：根裡是 64 字元 hex 字串，
    commit 裡是 **32 個十進位整數的陣列**。〔對照〕使用者的規矩是
    「一個概念一種正準拼法」，**儲存層今天不守這條**。

### 1.3 標準根：JSON 進 hex 進 JSON

〔量〕檔案內容是 `"standard-root:7b22636c6f736564…"` ——一個 JSON 字串，
內容是 **hex 編碼的 JSON**。解出來 **68,126 B**，緊湊重印仍是 68,126 B。

```
外層檔案 136,268 B ÷ 內層 JSON 68,126 B = 2.00×
```

⟹ **標準根的一半是 hex 的膨脹，與「用不用 n/」完全無關。**
內層有 25 個 `system` 模組（`Bytes`／`Complex`／`Cond`／`Config`／`Csv`／`Diff`／
`Discovery`／`Effect`／…）。

## 2. 印表機離編碼器有多遠

### 2.1 n/ 印出形的大小

`oo inspect` 的輸出（扣掉 103 B 的 `CAID:`／`MASA:` 表頭）：

| | 磁碟現況 | n/ 印出形 | 比 |
| :--- | ---: | ---: | ---: |
| 根 | 428 B | **117 B** | **3.7×** |
| 標準根 | 136,268 B | **21,722 B** | **6.3×** |

〔重現〕W8′ 在 v0.19.0 量到 n/ 形 **21,837 B**，今天 **21,722 B**——
**七個 minor 之間幾乎未動**，而 JSON 側在同一段時間長大了。

### 2.2 唯一的語言缺口：`system` 軸

〔量〕把根的印出形原封不動餵回剖析器：

```
輸入：  ~%__nlang_system_digest: "7038e250…f37911"
輸出：  ~%__nlang_system_digest: _|_ (%cause: #system_reserved)
```

整份標準根同樣：21,825 B 的印出形讀回來剩 2,588 B，**25 個 ⊥**，
逐一對應 25 個 `system` 模組。

**這是故意的，不是缺陷。** `system` 軸不可由表層程式寫入，是 Q-035
（「名字不再是憑證」）那條線。⟹ **結論不是「印表機壞了」，是**：

> **耐久形必須能表達表層語言禁止的東西。**
> 印表機的輸出被剖析器讀回來，語義上**不等於**它印的那個值。

〔對照，量〕`%builtin` **不在這個缺口裡**：使用者手寫
`{{ %builtin: "list.map", %morphism: #true }}` **是活的**——
以 `(x -> 9)` 施用得 `[9, 9, 9]`，與 `~%List./map` 逐字相同；
而 `"list.nope"` 得 ⊥ `#unprojected_builtin`。
⟹ **憑證是標準根的投影，不是那個名字**，Q-035 的裁定在這裡看得見。

### 2.3 把 `system` 軸的拼法問題挪開之後，還剩什麼

〔量〕把印出形裡的 `~%` 全部改名為 `SYS_`（純粹繞開保留字），再讀回、印出、改名回來，
與原印出形逐行 diff：

```
21,726 B  →  21,190 B ，0 個 ⊥ ，28 個 diff hunk
```

28 個 hunk 全部歸兩類：

| 類 | 次數 | 現象 |
| :--- | ---: | :--- |
| **`%effect` 印成註解** | **26** | 印出 `}}  ;; %effect: #cached`，`;;` 是註解 ⟹ 讀回來就沒了 |
| **`%val` 投影** | 2 | `%some: { %val: _ }` 讀回來成 `%some: _` |

**其餘 21,190 B 逐字元回得來。**

**兩類的性質不同，不可混為一談**：

*   **`%effect`**：**語言有一個宣告，但沒有一個標籤。**〔本項改過兩次，過程照記〕
    第一讀：`({ %effect: #io, a: 1 }).%effect` → `#io` 而 `({ a: 1 }).%effect` → `#pure`
    ⟹「語言有拼法」。第二讀（**錯的那次**）：`({ %effect: #io, a: 1 }.a).%effect` → `#pure`
    ⟹「那只是個普通欄位」。**第三讀，才是對的**〔量〕：
    `{ %effect: #pure, v: (~%Time.now _) }` → **⊥ `#effect_violation`
    `;; declared #pure but observes #io`**，而 `{ %effect: #io, v: 1 }` **被接受**
    （宣告 ⊒ 實際，過度近似是健全的）。
    ⟹ **`%effect:` 是真的宣告，而且 Q-034 的宣告守護正在讀它。**
    **但它是包裝，不是標籤**：〔量〕真正帶效果的值印出來是**後設資料**
    （`{ t: 1787672618661  ;; %effect: #io }  ;; %effect: #io`），
    宣告形印出來是**多一個欄位**（`{ %effect: #cached, v: 1 }`），
    而〔量〕**任何住在值裡的欄位都進身分**：`{ a: 1 }` → `fd335de1…`，
    `{ %effect: #io, a: 1 }` → `2996d9ae…`。
    ⟹ **拿宣告形去寫那 26 處會移動 CAID**，而身分是本弧紅線。
    **缺的是一個「標它但不加欄位」的拼法。**
    ⟹ **這是語言的缺口，不是印表機的缺口**，而且**與問題一的 `system` 軸同型**：
    耐久形有一部分（v0.26.0 起 `%effect` 進耐久形）**在表層語言裡寫不下來**。
    〔對照〕**這是 `commit.md` §1.9 弧 D 承重句的第三個病灶**——
    位址、`system` 軸、`%effect`，**三個都是「語言缺一個字面」**。
    〔判別實驗，弧內做〕`.%effect` 讀得到那個假欄位 ⟹ **凡以 `.%effect` 判斷的守衛
    都可能被一個普通欄位騙過**，O74 的宣告守護是不是其中之一？
    若是，它是 Q-034 剛關的門上的一個洞，**須另立一件，不得併進 Q-012**。
*   **`%val`**：〔量〕`{ %val: X }` **投影為 X** 是既有語義（`{ %val: 1 }` → `1`）。
    但〔量〕**`{ %val: _, z: 1 }` → `_`，`z: 1` 靜默消失**。
    ⟹ 任何帶 `%val` 又帶別的欄位的 combo，印出再讀回會**掉欄位**。
    **這是旁量發現，入 Inbox（§9），不屬本弧射程。**

## 4. 代價

### 4.1 體積

以本節的真倉為例，若三個物件都改成 n/ 印出形（且 `system` 軸的拼法問題已解）：

```
今天    137,185 B
n/ 形   ≈ 21,839 B（21,722 + 117）＋ commit
節省    ≈ 6.3×
```

其中**有一半（標準根的 hex 膨脹，68,142 B）與 n/ 無關**——
**那一半可以在不動編碼形的情況下先拿掉**。〔這是弧的可拆點，見 §7 問題三〕

### 4.2 時間

〔量，20 次取平均，同一台機器，同一個二進位〕

| 動作 | ms/run |
| :--- | ---: |
| `oo fmt` 解析 21.7 KB 的 n/ | **9** |
| `oo fmt` 解析 1 行（行程啟動對照） | **2** |
| `oo inspect` 讀＋解碼 136 KB 標準根 | **15** |
| `oo eval 1`（載入標準根宇宙的對照） | **17** |

⟹ **解析 21.7 KB 的 n/ ≈ 7 ms**，與今日讀標準根**同一個數量級**。

**誠實邊界（三條，不得省略）**：

1. **行程啟動支配這四個數字**（1 行也要 2 ms）。要分辨真正的解碼成本，
   需要 in-process benchmark——**這是弧內的判別實驗，不是今天可決的**。
2. `oo fmt` 與 `oo inspect` **不是同一條路**（一個解析文字，一個解碼 JSON 再印）。
   兩者只能當**量級比較**，不能當單位成本。
3. **`oo eval` 的 180 ms 不是剖析。** 我第一次量到 180 ms 時差點寫成「n/ 解析慢 17 倍」——
   〔量〕改用真的只解析的路徑後是 9 ms。**那 180 ms 是求值 25 個模組**，
   而 **O35 已裁「讀取是解碼不是求值」** ⟹ 解碼器不會付這筆。

> **本偵察被 `WORK_QUEUE` §8 新增的第 4 條救了三次**：
> (i) `oo fmt f.n` 回 0.00 s，查 exit code 才發現**它根本沒解析成功**
> （`.n` 程式檔不能是裸 combo，要 `root: { … }`）；
> (ii) 上面那個 180 ms 的錯誤歸因；
> (iii) §2.3 的 `%effect` 字面——**這一格我讀錯了兩次才對**：先以為「語言有拼法」，
> 再以為「那只是普通欄位」，直到拿 Q-034 的守護去問（宣告 `#pure` 在不純值上）
> 才看出**它是真宣告、但是包裝不是標籤**。
> **三次都是「讀數看起來很合理」，而第三次連我的更正也是錯的。**

## 5. GC 走訪：今天不是走訪，是掃字串

〔讀〕`crates/interpreter/src/gc.rs:48/72/85` ——引用是這樣找出來的：

*   任何 **64 字元的 hex 字串** ⟹ 當成引用
*   任何**整數陣列**，逐位元組 hex 後長度 64 ⟹ 當成引用
*   任何以 `hash:sha256:` 開頭的字串 ⟹ 取最後一段

⟹ **GC 對 CAS 的理解是語法的，不是語義的。** 兩個後果：

1. **完成條件「GC 走訪逐項一致」有現成的迴歸閘**（W8′ 當年說的就是這個）：
   換編碼前後，同一個倉的 reachable 集合必須**逐項相同**。
2. **今天的掃法在建構上是過度包含的**：使用者寫得下 64 個 hex 字元的字串，
   而 GC 會把它當成引用。〔判別實驗，弧內〕過度包含只是留下垃圾（安全）；
   **真正要驗的是反方向**——有沒有哪一種引用**掃不到**（那是資料遺失）。
   位址錨 `_{sha256:…}.` 是**路徑**、且 commit 時已強制求值（Q-010b），
   **初判不留懸空引用，但這需要一個實驗證實，不能靠推理**。

〔讀〕`verify_reachable_object`（`gc.rs:118`）三段式：先試 store 的單一 value decoder，
再試裸 `Value`，再試 `Commit`，三者皆敗才判 `Undecodable`。
**換編碼時這三段各要一份對應**，而註解裡已記著 v0.2.52 踩過的坑
（「真的 Commit 被誤報為 undecodable」）。

## 6. 遷移與跨版本

## 7. 要用戶裁的三個問題（O31）

O31 的裁定依 `STATUS.md:145` 須含**編碼形／`format` 版本遷移／代價**。
偵察把它收斂成三個彼此獨立的問題：

### 問題一：編碼形——耐久形要怎麼表達表層禁止的東西？

**兩個缺口，同一個形狀。** §2.2：印表機寫 `~%Cond:`，剖析器回 ⊥ `#system_reserved`
（25 個模組，標準根的全部）。§2.3：`%effect` 自 v0.26.0 起是耐久形的一部分，
而印表機只能把它寫成 `;; %effect: #cached` 註解，因為**表層沒有它的字面**。
⟹ 加上 v0.29.0 已經解掉的位址，**這是「語言少一個字面」的第二、第三個病灶**。三條路：

*   **(a) 特權解碼器**：解碼走一條繞過表層守衛的路。
    代價：**「耐久形＝你看得到的那份文字」不再成立**，
    同一份位元組由不同入口讀有不同結果——這正是 O35 費力關掉的門。
*   **(b) 耐久形明示自己是文件不是程式**（一個框，或一個 `%kind: #store_document`）。
    代價：多一個概念；好處：**守衛可以照常，而且它自己說得出自己是誰**。
*   **(c) 補字面**——給 `system` 軸與 `%effect` 各一個字面，
    正如 v0.29.0 給位址一個字面（`_{sha256:…}.`）。
    〔對照〕**這與 `commit.md` §1.9 弧 D 的承重句逐字同型**——
    「標準根龐大是因為語言沒有位址字面」。**那句話今天量到了它的第二、第三個實例。**
    代價：兩個新字面都進身分（位址錨的先例，`SPEC_00` v0.29.0 那列），
    ⟹ **一旦定版就是相容性承諾**，而 v0.29.0 已示範這種弧可以是非破壞性的
    （只讓從前不合法的源碼變合法）。

> **✅ O31 編碼形已裁 2026-08-26（用戶）：(b)+(c) 合成一件。**
>
> **開單前先更正我自己的分法**：把 (b)／(c) 列成三選一是錯的——
> **(c) 是「寫什麼」，(b) 是「在哪裡合法」**，它們是一句話的兩半。
> 而且量測顯示 **`system` 軸沒有「(c) 單獨」這個選項**：
> `SYNTAX_05` §3 逐字「`~%` 唯引擎鑄造」，且 conformance **有兩個向量釘著**
> （`L2-60` combo 內 `~%` 定義鍵 ⊥、`L2-61` novel `~%` 名同違法）。
> ⟹ 讓 `~%Cond:` 到處合法＝刪掉兩個向量、廢掉所有權條款。
> **框是使字面合法的那個東西**，框外照舊 ⊥，兩個向量照舊綠。
>
> **框住哪裡——三個候選，兩個被量測否決**：
>
> | 位子 | 判定 |
> | :--- | :--- |
> | `%kind: #store_document`（值的欄位） | **否決**〔量〕`{ a: 1 }` → `fd335de1…`；`{ %kind: #store_document, a: 1 }` → `1882fd8d…`。**任何住在值裡的欄位都進身分** ⟹ 移動現存每一個根位址 ⟹ 紀元弧 |
> | `%val`（值的欄位） | **否決，且更糟**〔量〕`{ %val: X, …任何其他欄位 }` **一律投影為 X** ⟹ **框會把自己吃掉** |
> | **值的外面** | **✅ 採用**——框住在**編碼**裡，不住在**值**裡；§3 已量到編碼 ⟂ 身分（428 B → 762 B，CAID 不變）⟹ **(b) 對根位址的成本是零** |
>
> **值的外面有兩個位子，兩個都要，分工不同（用戶裁定）**：
>
> 1. **`.oo/objects.format` 的 `encoding=5` ＝ 倉級的閘。**
>    `ensure_supported_encoding` 已在讀它，範圍外拒絕開啟（§6）⟹ 破壞是響亮的。
> 2. **檔案開頭的 token ＝ 物件級的自報。** 先例現成：今天標準根的檔案內容就是
>    `"standard-root:<hex>"`，那個前綴**不是值的欄位**，是檔案在自報自己是什麼。
>    **理由是 O35 已裁的一句話**：「**線上就是 store**——OODP 送同一種物件、
>    `peer fetch` ＝ `get_value`」⟹ **單一物件會離開它的倉去旅行**。
>    若宣告只住在 `objects.format`，收到的一方拿到一個**沒有自報身分的物件**，
>    分不出它可不可以讀 `~%`——而那正是框存在的全部理由。
>
> **(a) 特權解碼器已否決**：它把 O35 的「讀取是解碼不是求值」換成「讀取有兩種解碼」，
> 同一份位元組由不同入口讀有不同結果。
>
> **弧內還要定的兩個拼法**（工單的事，不是裁定的事）：
> **(c-1)** `system` 軸在框內的字面；**(c-2)** 標籤字面——
> **必須標它而不加欄位**，否則 26 處全部移動 CAID。

### 問題二：射程的兩條邊界 —— **✅ 已裁 2026-08-26（用戶）：兩者都納入**

> **裁定**：commit 物件與 `.oo/staged` **都在射程內**。
> **用戶給的理由**：「可能之後拆 savepoint 會比較順」——即 **Q-014（單一可替換
> savepoint 物件）**。⟹ 這條裁定不是為了本弧的整齊，是為了**下一弧的可開工性**：
> 若本弧留下「倉裡同時有兩種編碼」，Q-014 要動的那個原子單位就跨在兩種編碼上。
>
> **後果，須寫進工單**：(i) `lattice_sketch`（base64）與 32-int digest 都要有 n/ 形，
> 而 §1.2 量到的「同一個倉裡 digest 兩種拼法」**由本弧一併收掉**，
> Inbox 那一列隨之吸收；(ii) `.oo/staged` 是**無位址**的耐久檔（O51 保留 Thunk），
> ⟹ 本弧要定的編碼形**必須能表達未強制的形**，這是問題一的一個額外輸入。

1. **commit 物件在不在內？** 它不是 `Value`（§1.2）。若在內，
   `lattice_sketch`／32-int digest 都要有 n/ 形；若不在內，
   倉裡會**同時有兩種編碼**，而那正是今天的狀況。
2. **`.oo/staged` 在不在內？** 它是無位址的耐久檔（§6），依 O51 保留 Thunk。

### 問題三：這一弧要不要拆 —— **✅ 已裁 2026-08-26（用戶）：不拆，一弧做完**

> **裁定**：補字面、換編碼、拿掉 hex、遷移與跨版本矩陣、GC 走訪一致，**全部同批**。
> ⟹ §1.3 的 hex 膨脹**不另立一件**。與拆弧規則一致：**拆弧的正當理由只有
> 「這是兩件不同的事」**，而用戶判定它們是同一件事的幾個面。

§1.3 量到的 hex 膨脹（68,142 B，標準根的一半）**與編碼形無關**，今天就可以拿掉。
（§2.3 的 `%effect` **不在**這個子集裡——它已被判別為**語言缺一個字面**，
