# a store you did not write — 偵察

**Queue ID**:`WORK_QUEUE` Q-011（O36）＋ 2026-08-14 新掛帳（hydration 假裁決）
**基線**:引擎 `v0.21.0` / 規格 `v0.21.0-draft.1`
**問題**:引擎打開一個**不是自己寫的**倉時,能知道什麼、能主張什麼、能寫什麼。

## 1. M1 — 從「一個檔案不見了」到「歷史被刪掉」

六步,**每一步的元件都照設計運作**,沒有任何一步報錯。

〔量 2026-08-14,引擎 v0.21.0 與真 v0.20.0 二進位〕

| # | 動作 | 觀測 |
| :-- | :--- | :--- |
| 1 | 一個 **format 3** 的倉,`.oo/format` 不存在 | — |
| 2 | 跑**唯讀**的 `oo log` | 成功列出 commit,**並在磁碟上寫下 `1`** |
| 3 | 用 v0.20.0 打開 | **打得開**（`1 ≤ 2`,閘被繞過）；誠實標籤 `3` 時它正確拒絕 |
| 4 | v0.20.0 讀那個根 | `#caid_mismatch: object at digest path is corrupt (integrity failure)` |
| 5 | v0.20.0 `evolve` + `commit` | **成功**。HEAD 移動,標籤由 `1` 變 `2` |
| 6 | v0.21.0 `oo gc --grant gc` | `removed 2 objects` —— **原根與原 commit 消失** |

第 6 步之後 `oo inspect <原 commit>` 回 `CAID not found in local store`。

**三則假話,兩個方向**:

* 第 2 步,引擎**對倉說謊**——它在同一次執行裡宣稱該倉是 format 1,又成功讀出了
  format-3 的物件。它知道得更清楚。
* 第 4 步,引擎**對人說謊**——那個物件沒有損壞,只是這個引擎不認得它的形。
  這是 REAL_03 §6.6「裁決必須為真」之族的**第三次**（前兩次:`oo gc` 在健康倉上
  指控自己〔Q-010b D3,已修〕；本節第 4 步；下節 M4）。
* 第 3 步不是說謊,是**閘失效**。REAL_03 §6.8 第四條 MUST（格式須先宣告）存在的
  理由正是防止第 3 步,而第 2 步把它拆了。

**須明說的界線**:第 6 步的 `gc` 是**特權且非自動**的（local_gc 弧裁定）。
引擎沒有自己刪掉歷史；它造出了一個狀態,使一次**合法的**回收刪掉歷史。
分野重要——要修的是前五步,不是第六步。

## 2. M2 — 標籤的兩個寫入點,一個在唯讀路徑上

`crates/interpreter/src/storage.rs`

| 行 | 函式 | 何時 | 正當性 |
| :-- | :--- | :--- | :--- |
| 150 | `ensure_format` | **每一次開啟**,含唯讀 | ✗ 讀取路徑上寫別人的倉,且寫的是猜的值 |
| 386 | `upgrade_format_for_cas_write` | 第一次 CAS 寫入之前 | ✓ 寫入路徑上宣告自己即將產生的形 |

`ensure_format` 的文件字串寫著「Absent → write `1`」,而其註解（M9 記載）寫著
"Every existing store is version 1; announce rather than refuse"。**那個假設在
它被寫下時是真的,今天是假的**——`.oo/format` 出現於 v0.2.53,而此後格式走過
1→2→3。缺席不再蘊涵 1。

## 3. M3 — 標籤的取值矩陣

〔量,唯讀命令,倉的物件實際上是 format 3〕

| 標籤 | 行為 | 標籤事後 |
| :--- | :--- | :--- |
| 缺席 | **開啟** | **被寫成 `1`** |
| `0` | 拒絕（指名版本） | 不動 |
| `1` | **開啟** | 不動 |
| `2` | **開啟** | 不動 |
| `3` | 開啟 | 不動 |
| `4` / `999` | 拒絕（指名版本） | 不動 |
| 空 / `abc` | 拒絕 | 不動 |
| `03` | **開啟**（前導零被接受） | 不動 |
| `3 `（尾隨空白） | 開啟（trim） | 不動 |

**要害不是拒絕的那幾格,是開啟的那幾格**:`1` 與 `2` 都讓一個裝著 format-3
物件的倉被開啟,而**沒有任何東西拿標籤與物件對照**。標籤是被絕對信任的。

## 4. M4 — 改動標準根會讓 format-2 倉得到一則假裁決

三個引擎,除了標準根多一筆之外完全相同:

| 倉 | 讀者 | 結果 |
| :--- | :--- | :--- |
| v0.20.0 寫（format 2） | v0.20.0**＋一筆** | **讀得開** —— 舊行為是安全的 |
| v0.21.0 寫（format 3） | v0.21.0**＋一筆** | `refusing root: standard root digest … is unavailable` ✓ 照 §6.8 |
| v0.20.0 寫（format 2） | v0.21.0**＋一筆** | **`#caid_mismatch: … is corrupt (integrity failure)`** ✗ |
| v0.20.0 寫（format 2） | v0.21.0（未改） | 讀得開（控制組） |

**機制**:`get_root` 無條件呼叫 `hydrate_standard_root`,它對六軸做
`entry().or_insert()`。format-2 的根**本來就自足地含著整份舊標準庫**,新引擎多
一筆就被插進去,重算位址不合 ⟹ 指控損壞。**物件是好的。**

今天看不見,因為還沒有人動過標準根。

## 5. M5 — 一個引擎只能持有一個標準根

`storage.rs:482` 把倉裡的摘要與 `standard_table_digest(standard)` 比對,而
`standard` 只有一個來源（`root_with_system()`,全樹唯一）。**沒有歷史標準根的表。**

⟹ 改動標準根 = 所有 format-3 倉被指名拒絕（正確但無出路）＋ 所有 format-2 倉被
指控損壞（M4,錯誤）。**標準根在有遷移故事之前不可演化**,而 `/add` 孤兒與
SPEC_09 型別表兩則掛帳做的正是動它。

## 6. 順帶更正一則已定版的規格推論

REAL_03 §6.8 的理由段原寫「新增一個內建就**移動所有歷史根的身分**」。
**量測推翻**（M4 第一列）:已在磁碟上的根位元組與位址都不動、也照樣讀得回。
移動的是**可重現性**——同一份 `app: { k1: 1 }` 由兩個標準根不同的引擎提交得到
`16ba5683…` 與 `0cc1eab9…`。已更正（`nlang-spec 62ca04c`）；**四條 MUST 不變**,
它們由第三項後果（同一位址在兩個引擎上解析成兩個宇宙）單獨支撐。

## 6.5 M6 — `.oo/format` 在量什麼:一個計數器,兩條軸

**先於 A–D 的一題,而它是 STATUS 的 O23（已記、未裁）。**

`.oo/format` **2026-07-28 引入於 local GC 弧**（`374bd47`, v0.2.53）。提交訊息:

> Declare `.oo/format` so an engine that does not understand a **layout** can
> refuse rather than proceed.

規格側同義（REAL_02 §5.1.1）:「物件是自描述的——CAID 字串自帶 `v1`/`v2`。
**沒有版本的是佈局**:`HEAD`、`staged`、`abandoned` 這些檔案的存在與意義。」

⟹ **三條軸,其中一條沒有號碼**:

| 軸 | 由誰宣告 | 現況 |
| :--- | :--- | :--- |
| 值的身分／位址格式 | 物件自描述（CAID 字串內的 `v1`/`v2`） | `v2`,自 v0.2.0 凍結 |
| `.oo/` 佈局 | `.oo/format` | 引入時的原意 |
| **物件編碼／內容** | **無** | JSON;將來換 n/（O31／W8′-c／Q-012） |

**而 1→2→3 實際改的是第三條軸:**

| 版本 | 日期 | 弧 | 內容 | 軸 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | 2026-07-28 (v0.2.53) | local GC | 宣告佈局本身存在 | 佈局 ✓ |
| 2 | 2026-08-14 (v0.20.0) | Q-010a | CAS 物件不帶 span、緊湊、正準序 | **物件編碼** |
| 3 | 2026-08-14 (v0.21.0) | Q-010b | 根以摘要指名標準根 | **物件內容** |

〔量〕format 2 與 format 3 的 `.oo/` 佈局**逐檔相同**（`HEAD`／`format`／
`objects/sha256/…`,正規化 CAS 路徑後 `diff` 為空）。**佈局仍然是版本 1。**

`storage.rs:109–116` 的文件註解自己記著這個分裂——第二行寫「this is the
**layout** marker」,第四行起把 2 與 3 定義成 CAS 投影。**五行之內自相矛盾。**

### 6.5.1 這解釋了 M1 為什麼可能

`ensure_format` 的「缺席 → 寫 `1`」**不是草率**。在該計數器被宣告要量的那條軸
上,它是**真的**——2026-07-28 當下每一個既存的倉,佈局都是版本 1,而佈局至今
未變。

它變成假的,是因為**我們默默改變了那個計數器在量什麼**,而沒有回頭看依賴舊
語義的那個假設。同理,Q-010a／b 的「舊引擎在格式閘誠實拒絕」是真的、也有價值,
但它**是靠一個宣稱在量別的東西的標記在運作**;今天不出事,只因兩條軸恰好同步。
**它們一分岔就會出事**,而 M4（改動標準根）與 Q-012（換編碼）都會使它們分岔。

### 6.5.2 對 A–D 的影響

**A 與 B 排在本題之後。** 若物件編碼取得自己的號碼,「缺席」在兩條軸上的意義
就分開了:佈局缺席仍可合理地視為 1（該軸真的沒變過）,而物件軸缺席就是
**「不知道」**——兩者不再互相污染,而 M1 的第 2 步失去成立條件。

## 7. 待裁（裁定人＝用戶）

**A′（新首題,＝STATUS O23）:`.oo/format` 是一個號碼還是三個?** 見 §6.5。
今天它被宣告為佈局標記而實際承載物件編碼,兩次。**先答這題,A 與 B 的形狀才確定。**

**A. O36:`.oo/format` 是「這個倉宣稱什麼」還是「這個引擎驗證了什麼」?**

* **宣稱**:缺席 = 沒有宣稱 = 拒絕開啟（今天的 `0` 那一格）。引擎**永不**在讀取
  路徑上寫它。代價:v0.2.53 之前的倉、以及任何遺失該檔的倉,需要一道明確的
  `oo repair`／`--assume-format N` 才打得開。
* **驗證**:蓋章前必須先解得開一個物件。代價:開啟成本上升,且「解得開一個」
  與「解得開全部」不是同一件事——混合倉（M1 第 5 步的產物）會通過。

**B. 標籤與物件不一致時,以誰為準?** 今天標籤絕對優先且無人查證。若答案是
「物件為準」,標籤就降為快取,`ensure_format` 的整個問題消失；若是「標籤為準」,
就需要一條「不得寫下你沒有驗證過的版本」的 MUST。

**C. hydration 的適用條件**(M4)。建議:只有宣告了標準根摘要的根才該被 hydrate,
format-2 的根是自足的。**這一條看起來是純缺陷修復,但它決定 B 的答案能不能實作**
——若標籤不可信,判斷「這個根是不是 format 3」就只能看根自己有沒有那個 sentinel,
而那正是 C 的判準。

**D. 引擎能不能持有一個以上的標準根**(M5)。這是 `/add` 與型別表兩則的前置。
不裁它,那兩則就是「開弧即毀掉所有既有倉」。
