## 2. 名字解析：拆開之後 `~%Math` 從哪來

〔量〕裸名的解析順序（`lib.rs:3685` `resolve_path_internal`，`PathAnchor::Bare`）：

```
ctx.scopes（詞法，內→外）→ ~%Config 特例 → ctx.staged → ctx.root
                                                          ↑ ~%Math 在這裡被找到
```

`ctx.scopes: Vec<Arc<ComboVal>>`，建構時為**空**；`~%Math` 是在**最後一層 fallback**
從 `ctx.root` 取到的。

⟹ **拆開的最小形＝在 `ctx.root` 之後再加一層。**

```
scopes → ~%Config → staged → root → 【標準根】
```

### 2.1 分層免費地重現了今天的優先序

`hydrate_standard_root` 用的是 `entry(key).or_insert_with(...)`——**只在缺席時插入**
⟹ **使用者的欄位贏**。而分層查找是「root 先、標準根後」⟹ **同樣是使用者贏**。

**不需要為優先序做任何決定**，它已經被今天的合併方式決定了。

## 3. 拆開順帶解掉的：孤兒不只 `/add` 一個

〔量 v0.25.0〕標準根頂層**使用者寫得到的四個座標，全部擋人**：

```
/add:    { mine: 1 }   → Evolution Conflict: #missing_key at /add.mine
@list:   { mine: 1 }   → Evolution Conflict: #missing_key at @list.mine
@option: { mine: 1 }   → Evolution Conflict: #missing_key at @option.mine
@result: { mine: 1 }   → Evolution Conflict: #missing_key at @result.mine

對照（標準根頂層沒有的名字）
/sub, @zzz, @int       → 全部成功
```

**成因不是「規則軸」也不是 `/add` 本身**：標準根的那四項都是**閉合的繭**，
佔住了使用者可見的座標，而閉合的繭拒絕未知鍵。

> **⚠ 這修正了 Inbox 那一列的措辭。** 該列標題為「創世根的 `rules` 軸只有一個 `/add`，
> 且它擋住使用者」——**擋人的是四個，不是一個**；`/add` 只是最早被注意到的那一個。
> 早先「`@list: { %kind: #type }` 成功」的觀察不構成反例：那是**純精煉**（不新增鍵），
> 一加新鍵就撞。

⟹ **拆開之後這四個都變成可遮蔽**（使用者的 `/add` 是一個新座標，沒有東西要精煉）。
**`WORK_QUEUE` §9.1 的第 2 項（`/add` 孤兒）因此是本弧的後果，不是後續弧。**

## 4. 破壞面：小，而且集中在一個模組

〔量〕全樹**直接對根取 `~%` 欄位**者共 **13 處，其中 10 處是 `~%Config`**
（`universe.rs` 9 ／ `lib.rs` 1）。`root_with_system()` 在非測試碼共 **8 處**。

> **⚠ 本節第一版的結論是錯的，由用戶指出（2026-08-16）。** 原文寫
> 「`~%Config` 是唯一需要單獨處置的模組……它本來就該留在根上」——**那把兩個
> 不同的 `~%Config` 併成了一個**。

〔量 v0.25.0〕**`~%Config` 不需要任何例外**，因為它是兩件東西：

| | 是什麼 | 拆開後 |
| :--- | :--- | :--- |
| **創世旋鈕**（7 個常數） | 標準根的一部分，版本綁定 | **隨標準根一起搬**，無特例 |
| **操作者覆寫** | SPEC_09 §6.0.1 **MUST NOT 進入被提交的根**；活在暫存區 | **本來就不在根的身分裡**，拆開碰不到它 |

那 10 處直接讀取走的是 `universe::effective_config(&ctx.root, ctx.staged)`
＝**創世 ∧ 覆寫**；拆開後創世那半改由標準根那一層供給，是機械改動，不是例外。

### 4.1 §6.0.1 四條 MUST 全部已兌現（量 v0.25.0）

```
加不加 ~%Config 覆寫，根 CAID 相同         6e5ad5e3… / 6e5ad5e3…   ✓
根物件裡 ~%Config 出現次數                 0                        ✓
相鄰的普通欄位照常提交                     app 正常進根              ✓
未被提交必須說出來                         note: ~%Config was not
                                           committed (horizon
                                           parameters stay staged…)  ✓
覆寫續存於暫存區                           status 仍列出它           ✓
```

### 4.2 唯一還在的路：根自己是 `#blur`

§6.0.1 的**理由**逐字：「要保存視界參數的**唯一**條件是 CAID 一致性——而那已經記在
CAID 裡：**SPEC_08 §3.2.1** 要求 `#blur` 的 CAID **必須**包含序列化後的視界參數。」

⟹ **視界參數進入身分的唯一合法途徑是 `#blur` 的 CAID**（用戶指出）。若根裡含一個
blur，該 blur 的身分就帶著產生它的視界——**那是對的，不是違反**。

**未量**：本次未能構造出 blur（兩個 fuel 值皆收斂），故
**「`#blur` 的 CAID 是否真的含視界參數」在本版屬 §2.4 類——規格寫了 MUST，引擎未經查證**。
**不擋 O58 的射程**（`~%Config` 兩邊都不需要例外），但工單須要求量它；
若不成立，視界參數在身分裡**沒有任何家**，而 §6.0.1 的理由就落空了。

## 5. O61 的射程

〔量〕`%effect` 兩個家：`ComboVal.meta`（寫下的，**進雜湊**）／`ComboVal.effect`
（傳染的，**不進**）。O61 已裁：後者也算，修法是**搬家**不是新機制。

標準根裡受影響者：**256 條態射引用中 26 條非 `#pure`**（IO 20／`#nondet` 1／`#state` 5）。
⟹ 搬完標準根 digest 移動——**與 §1 的拆開移動的是同一個東西**。

### 5.1 正準形：欄位缺席 ＝ `#pure`（**已裁 O62**）

只有**非單位元**的效果落成欄位；寫入時**正規化掉**顯式的 `%effect: #pure`。

**起因是一個既有違反**〔量 v0.25.0〕：`{ %effect: #pure, v: 1 }` 與 `{ v: 1 }` 的
`.%effect` **皆讀出 `#pure`**，而根位址分別為 `d48f4deb…` 與 `b25bfaf…`——**兩個位址**。
REAL_03 §6.7 要求「位元組為值之函數」，而 O61 已裁二者為同一個值
⟹ **§6.7 今天被違反著，此前無人記帳。本弧順帶關掉它。**

**兩條界線（工單必須逐字帶）**：

*   **「非單位元」不等於「非純」**——`#cached` **必須**落成欄位（它不是格的 ⊥，
    §4.2.4 的固化語義靠它）。判準是 **⊥**，不是「純不純」。
*   **正規化只得在守衛之後、且只在有效效果確為 `#pure` 時發生。** §4.1 允許顯式寫入
    優先於引擎標籤 ⟹ 使用者寫得出一個**假的** `#pure`，而那正是 §4.3 靜態守護要抓的謊。
    **若正規化搶在守衛之前抹掉那個欄位，正規化器就成了共犯**——謊被消滅而非被抓到。
    順序：**判定有效效果 → 守衛 → 僅當有效效果 ＝ ⊥ 時去欄位**。

## 6. 尚未量（擋開單，不擋設計）

1.  **拆開後的根物件長什麼樣**：sentinel 變成**進雜湊的內容**（一個指名依賴的欄位），
    §6.8.1 已允許「物件得指名其依賴」——但那一節同時斷言該摘要「是位址的函數」，
    而 O58 記載該斷言**被量測推翻**。**拆開會讓那句話變成真的**，須確認條文措辭。
2.  **多重具備第一次上場**：`shipped_standard_roots()` 今天是
    `from_roots([self.root_with_system()])` **一列**。舊倉要活著就必須有第二列，
    而**那條路徑從未被真的走過**（Q-025 的驗收用的是三個真二進位，不是同一個引擎的兩列）。
3.  **`#cached` 與 §4.2.4**：O61 落定義側、固化在觀測側，規格已分開；但引擎今天
    在哪一側做固化，**未量**。
4.  **工作區有多少測試假設 `~%Math` 是根的欄位**：`root_with_system()` 在測試碼的
    用量遠大於 8 處，須逐一分類。

## 7. 這一弧的形狀（初判，待工單收斂）

*   **不是**「把標準根從根裡刪掉」。是**把一個合併關係換成一個指名關係加一層查找**。
*   優先序不必重新設計（§2.1）。
*   **`~%Config` 不需要例外**（§4）——創世旋鈕隨標準根走，操作者覆寫本來就不在根裡。
*   `/add` 與另外三個孤兒**自動消失**（§3）。
*   O61 同弧（§5），因為身分只該搬一次。
*   **舊倉靠多重具備活著，而那條路徑要第一次真的被走**（§6.2）。
