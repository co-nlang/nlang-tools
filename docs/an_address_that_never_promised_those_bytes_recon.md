> 目的：把「`message` 進不進 CAID」展開成可裁的候選。
> 這是 2026-09-09 盤點排序的第 2 項（用戶已裁 1 → 2 → 3；第 1 項 ＝ D64／Q-042，已出貨 v0.47.0）。

## 0. 先說結論的形狀：卡片的前提要反過來

卡面寫的是「**`message` 的位元組不在自己的位址承諾裡**」，並把待裁問題寫成
「`message` 進 CAID（可能是紀元）／不進 CAID（則須回答一個內容定址物件裡容許多少自由文字）」。

〔量 ＋ 讀〕**那個二選一的第二支已經被答過了，而且答案是零。**

| 卡片假設 | 量到的 |
| :-- | :-- |
| 位址忘記了 `message`，是位址的缺陷 | **位址是對的**——`SPEC_04` §162 逐字裁過 `_|_` **不**可內容定址（§2） |
| 「容許多少未經認證的自由文字」待裁 | **`REAL_03` §6.7 已經寫死：一個都不行**，且**判例是 `span`，而 `span` 早已修掉**（§3） |
| 只有 `message` 不進位址 | **`%cause` 也不進**——`#conflict` 與 `#divergent` 共用同一個根（§1） |
| 這一項很可能是紀元，宜與弧 D 的身分搬遷一起做 | **紀元成本比預期小**：〔量〕標準根含 **0** 個 ⊥，本專案所有紅線根皆不含 ⊥（§5.3） |

⟹ **這不是「兩個設計選一個」，是「一條已經在出貨的 MUST NOT，底下壓著一個真的設計題」。**
形狀與 Q-002 同——**卡片描述的缺陷不是真正的缺陷，而真正的那個更上游。**

## 1. 量到的：一個位址，兩份位元組

〔量 2026-09-12，`v0.47.0` 標籤建置。**對照組先行**：`oo eval '1 + 1'` → `2` rc=0。〕

三個來源，各自 `evolve` ＋ `commit`，逐個列出 `.oo/objects` 裡的根物件：

```
bad: 1 & 2                → cbb7ef81…  { bad: { ~%__nlang_bottom: #conflict message: "Incompatible types: 1 vs 2" } … }
bad: 1 & 3                → cbb7ef81…  { bad: { ~%__nlang_bottom: #conflict message: "Incompatible types: 1 vs 3" } … }
bad: bad + 1              → cbb7ef81…  { bad: { ~%__nlang_bottom: #divergent } … }
bad: ~%Math./add (1,"x")  → cbb7ef81…  { bad: { ~%__nlang_bottom: #conflict } … }
```

**四個不同的宇宙，四份不同的位元組，一個位址。**

### 1.1 對照組（證明量測碰得到目標）

| 控制 | 結果 |
| :-- | :-- |
| 同一個來源跑兩次 | 根相同、**檔案逐位元組相同**（`cmp` 靜默）✅ |
| 換欄位名 `other: 1 & 2` | 根 **17ffc21a…**，不同 ✅ |
| 兩個 ⊥ `a: 1 & 2` ＋ `b: 3 & 4` | 根 **e7f81c9a…**，不同 ✅ |
| `x: 0` | 根 **31745ef0…** ＝ 本專案每一弧的紅線值 ✅ |
| `x: 1` ／ `y: 0` | **ca0986d5…**／**5ff8e84a…**，各不相同 ✅ |

⟹ **位址對「值」是敏感的；它只對「⊥ 是哪一種 ⊥」不敏感。**

### 1.2 而那不只是理論上的碰撞——儲存會端出另一份

把 `bad: 1 & 3` 的根物件檔案**原封不動**複製到 `bad: 1 & 2` 那個倉的**同一個路徑**
（位址一字未改），然後問同一個位址：

```
竄改前： oo inspect hash:sha256:v1:cbb7ef81…  rc=0   bad: _|_ (%cause: #conflict)  ;; Incompatible types: 1 vs 2
竄改後： oo inspect hash:sha256:v1:cbb7ef81…  rc=0   bad: _|_ (%cause: #conflict)  ;; Incompatible types: 1 vs 3
之後：   oo status rc=0（宣告標準根 available）   oo log rc=0
```

〔對照組〕不存在的位址 → `rc=1`、`CAID not found in local store`。

⟹ **一次經位址驗證的讀取，回傳了那個位址並未承諾的位元組，而引擎全程沒有話說。**
**注意這連偽造都不算**——被放進去的是**另一個宇宙合法產出的物件**。

## 2. 位址是對的，而且是被裁過的

`SPEC_04` §162（2026-08-09 更正）逐字：

> `#blur` **可內容定址**且其 CAID **必須**含視界參數，**`_|_` 不是**。

⟹ **「所有 ⊥ 在同一個座標上共用一個位址」正是規格要求的行為。**
格論上也自洽：`_|_` ＝ `@{}` ＝ 空集合（`SYNTAX_02` §53／§92），
**空集合只有一個**；`%cause` 是關於「怎麼變成空的」的話，不是那個集合的成員。

**⟹ 不要去修位址。** 修位址等於推翻 §162，而那需要先回答 §4 那一題。

## 3. 規則已經寫好了，而且違反的是一條有判例的 MUST NOT

`REAL_03` §6.7 兩條，逐字：

*   **位元組為值之函數（MUST）**：對任一 CAID，其在 CAS 中的位元組**必須**僅為所指之值的函數。
    兩次寫入同一個值——同一行程、不同行程、不同機器——**必須**產生逐位元組相同的物件。
*   **不得存在未進入雜湊的欄位（MUST NOT）**：物件**不得**攜帶不參與該物件位址計算的資料。
    **原始碼座標（`span`）為其判例**：它隨輸入的排版變動而不進入 digest，
    故**同一個 CAID 之下可存在多份相異位元組**。
    **選擇為序列化便利而加入的欄位⋯除錯輔助欄⋯皆屬同族。**

〔量〕**兩條同時被違反，而且第二條的判準逐字命中**：
`message` 與 `#conflict`／`#divergent` 這個標籤都寫在物件裡、都不進位址，
`1 & 2` 與 `bad + 1` 是「同一個值」（同一座標上的 ⊥）而位元組不同。

〔量〕**判例本身已經修掉了**：全部測試倉的儲存物件中 `span` **0 命中**
（W8′-a，v0.13.0）。
⟹ **`message` 是同一條 MUST NOT 的第二個實例，而第一個實例在 34 個 minor 版之前就被判為必修。**

> **⟹ 卡片問「容許多少未經認證的自由文字」——`REAL_03` §6.7 早就答了：零。**
> 缺的不是那個答案，是有人把它讀到 ⊥ 這一格上。

## 4. 底下真正的那一題，而它就是 O85

上面兩節合起來把問題逼到一個點：

> **`%cause` 是不是那個值的一部分？**

兩個答案各自自洽，而且**各自決定其餘三件事**：

| | `%cause` **不是**值的一部分 | `%cause` **是**值的一部分 |
| :-- | :-- | :-- |
| 位址 | 不動（§162 照舊） | **必須含 cause**（推翻 §162），`#conflict` ≠ `#divergent` |
| 儲存 | **cause 與 message 都不得寫入物件**；它們只活在診斷訊息 | 兩者都進物件**且都進位址** |
| `_|_` 的正準列印形（**O85**） | **裸 `_|_`**——與 `SYNTAX_02` §17 的文法一致，**且它本身就是合法 n/** | 必須**補文法**（帶因 bottom 字面量）或改用既有記錄形 |
| `REAL_01` §1.3 第三條（印出來的讀得回去） | **同時解掉**——裸 `_|_` 回讀無礙 | 補完文法之後才解掉 |

⟹ **O85 與排序第 2 項不是兩題。它們是同一個問題的列印面與儲存面。**
2026-09-09 盤點寫「兩者是同一條免費文字通道的兩面」——**那句話是對的，而且比當時說的更強：
連通道的存在與否都由同一個答案決定。**

## 5. 候選與代價

### 5.1 甲 — `%cause` 不是值的一部分（成因是診斷，不是內容）

*   ⊥ 存入 CAS 時只存「這裡是 ⊥」，**cause 與 message 都不寫進物件**。
*   `_|_` 的正準列印形為**裸原子**；成因改由診斷訊息（stderr／退出碼那一側）攜帶。
*   **一則裁定關掉四件事**：`REAL_03` §6.7 的違反、O85、`REAL_01` §1.3 第三條、
    以及「一個內容定址物件裡容許多少自由文字」這個問句本身。
*   **不是紀元**〔量〕：`cbb7ef81…` 是今天就已經在用的位址，甲不移動任何位址；
    它只是**不再寫下那些不被覆蓋的位元組**。
*   ⚠ **代價要說清楚**：`TAG_REGISTRY` §0.2 把 ⊥ 列為**值的載體**
    （消費者看到的形 ＝ 值本身，rc=0）。甲之下，**操作者在值層看不到成因**，
    只能從診斷訊息取得 ⟹ **`oo status` 顯示一顆歷史裡的 ⊥ 時，成因從哪裡來？**
    這是甲必須回答的問題，本文不預判。
*   ⚠ **合規語料有 11 個向量帶 `%cause` 行**〔量〕。但〔讀 `run-conformance.py`〕
    該行是**可選**的，比對時被切下來單獨檢查，**未印出只產生 note 不算失敗**
    （逐字「L1/L2 為 SHOULD」）⟹ **甲不會弄紅任何向量**；今日 note **0 條**。

### 5.2 乙 — `%cause` 是值的一部分（成因進位址）

*   位址覆蓋 cause（是否覆蓋 message 另議——若 message 是**關於補救的自由文字**
    而非值，則它仍不得入物件，乙 並不自動救它）。
*   **必須推翻 `SPEC_04` §162**，並補文法（見 O85 的候選乙／丙）。
*   **是紀元，但比預期便宜**，見 §5.3。

### 5.3 〔量〕乙 的紀元成本

| 量測 | 結果 |
| :-- | :-- |
| 標準根 `7038e250…` 含幾個 ⊥ | **0** ⟹ **標準根 digest 不動** |
| 本專案每一弧的紅線根 `x: 0` → `31745ef0…` | 不含 ⊥ ⟹ **不動** |
| 合規語料 162 個 `.expect` | **不含任何 CAID** ⟹ 不受影響 |
| 會移動的 | **只有含 ⊥ 的使用者根** |

⟹ **這修正了 2026-09-09 盤點的排序理由**。當時寫「第 2 則⋯很可能是紀元，
**紀元宜排在弧 D 的身分搬遷附近一次做**」。
〔量〕**乙 不動標準根、不動紅線根** ⟹ **它不需要跟弧 D 的身分搬遷綁在一起。**
排序 1 → 2 → 3 本身不變（第 2 項本來就在第 1 項之後），但**「必須與弧 D 併做」這個理由不成立**。

### 5.4 丙 — 明文允許未覆蓋的位元組

**不推薦，且成本已知**：它要求就地改寫 `REAL_03` §6.7 的 MUST NOT，
而那一條的判例（`span`）是本專案花了一整弧修掉的。
**開一個例外等於把那一弧的結論改成「看情況」。**

## 6. ⚠ 順帶量到：`_|_` 今天有三種拼法

| 出處 | 形 |
| :-- | :-- |
| 規格散文（數十處） | `_|_ (%cause: #conflict)` |
| 參考實作 `oo eval` | `_|_ (%cause: #conflict)  ;; Incompatible types: 1 vs 2` |
| **合規語料的 `.expect`（11 個）** | `_|_` **換行** `%cause: #conflict` |
| **文法（`SYNTAX_02` §17）** | `bottom = @{ "_|_" }` —— **只有裸原子** |

**四個地方，三種拼法，而唯一有文法的那個只寫了一種。**
這一格本身就是「一個概念一種正準拼法」在 ⊥ 上的未兌現，
與 D64 治的病同族——**只是這次不在 CLI，在值語言自己身上。**

〔另記，非本題〕`run-conformance.py` 對 ⊥ 向量的判準是
`got.startswith('_|_') or 'Conflict' in err or 'Error' in err`
——**後半段等於「只要失敗就算對」**。〔量〕今日 **21／21 全部由 stdout 的 `_|_` 判定，
0 個靠那個逃生門** ⟹ **是潛在弱點不是現行缺陷**，記此以免日後有人靠它變綠。

## 8. ⚠ 補量與自我更正（2026-09-12，用戶指出兩處舊紀錄後）

用戶回憶起兩件舊事，兩件都找到了，**而其中一件推翻本文 §2 的論證強度、
另一件給出一個本文沒有用到的判準，且那個判準指向相反的方向。**

### 8.1 `;;` 的來歷：順序與印象相反，而紀錄說得很清楚

〔查 `nlang-spec/meta/ENGINE_SYNC.md` §207，2026-07-11〕逐字：

> **⊥ 印出 `%cause` 標籤**（nit）：**現以人話註解印因果**（如 free-$ P3 註解），
> conformance runner 的 cause 比對因此暫為 SHOULD。
> **統一印 `%cause: #tag` 後可升 MUST（L3 前必須）。**

〔查同檔 §219，2026-07-12 結案〕逐字：「⊥ 顯示 `_|_ (%cause: #<tag>)`
（`to_nlang` ＋ `to_string_plain` 對齊 `#tag`）」。

⟹ **`;;` 是起點不是修法。** 當時的問題是「成因只有人話、機器讀不到」，
修法是**加上 `(%cause: #tag)`**，讓它可被比對。
**`;;` 那一半自始就是合語法的**（它是註解）；
**不合語法的是為了讓成因可機讀而加上去的那個括號。**

⟹ 也就是說：**`;;` 確實是當時挑的「不會違反語法」的載體，而那個判斷至今為真**；
今天 `;;` 承載的是 `message`（自由文字），而括號承載的是 `%cause`（可機讀）。
**兩者是為了兩個不同的需求、在不同時間加上去的，只是長在同一行上。**

〔另記，非缺陷〕`REAL_05` §245 逐字：「`%cause` 行於 **L1/L2 為 SHOULD、L3 起 MUST**」。
**⟹ 這是按層級分的 SHOULD，不是一筆欠帳**；ENGINE_SYNC 那句「L3 前必須」與它一致。
**但它是候選甲的一個直接代價**：若成因不再住在值層，**`%cause` 行在 L3 將無法成為 MUST**。

### 8.2 那個判準找到了，而本文沒有用它

〔查 `nlang-spec/meta/oo/commit.md` §62，承重第 8 句〕逐字：

> **軸不是「在哪一層」，是「重不重算得回來」。**
> ⟹ `DERIVED` 邊根本不是物件而是一個可計算的關係，pin 日誌**不是索引**不能當快取設計，
> 而 **`%effect` 標的是「可定址但不可重現」那一格**。

〔同檔 §1.8 的表〕三列：可重算者不必存；可定址且可重現者存不存是效率問題；
**可定址但不可重現者必須被記下來**——因為沒有第二條路拿得回它。

### 8.3 把那個判準套到 `%cause` 上（〔量 2026-09-12，含對照組〕）

問題：**提交之後，成因重算得回來嗎？**

```
bad: 1 & 2   → commit → 全 .oo/ 掃 "1 & 2"        命中 0 個檔
                         根：{ bad: { ~%__nlang_bottom: #conflict message: "…" } }

對照組
ok: 1 + 2    → commit → 全 .oo/ 掃 "1 + 2"        命中 2 個檔
                         根：{ ok: { ~%__nlang_thunk: #true ~%__nlang_expr: 1 + 2 … } }
```

**引擎替可重算的值留著食譜（純 thunk 留在根裡，D46 ①），而在答案是 ⊥ 的那一格
把運算元丟掉了。** ⊥ 是在 evolve 期被合併出來的，合併消耗掉兩個運算元，
而**運算元不在任何地方**——不在根、不在注入、不在 ○。

⟹ **依承重第 8 句，`%cause` 落在「可定址但不可重現」那一格，與 `%effect` 同格。**
而 §1.8 對那一格的結論是：**必須被記下來。**

⟹ **這正面回答了用戶記得的那個提問——「帶因 `%cause` 算不算一種僥倖」：**
**今天它確實是僥倖的，而且是最壞的一種僥倖**：
**它既拿不回來（不可重現），又沒有任何東西認證它（位址不覆蓋、語料不釘）。**

### 8.4 ⟹ 對本文 §2 與 §7 的更正

*   **§2 的論證被記強了，就地降級。** `SPEC_04` §162 的那句
    「`#blur` 可內容定址且其 CAID 必須含視界參數，`_|_` 不是」，
    **上下文是 fuel 截斷，講的是「`_|_` 不是一個帶視界參數的可定址快照」**。
    ⟹ 它**支持**「⊥ 不攜帶視界參數」，
    **不支持**本文 §2 所寫的「一顆根的位址不必覆蓋其中 ⊥ 的成因」。
    **那一步是驗收方的推論，不是規格的裁定，就地作廢。**
*   **§3 不受影響**：`REAL_03` §6.7 兩條 MUST 被違反是逐字的事實，
    與成因該不該進位址無關——**今天的狀態是兩邊都不對**：
    成因既不進位址（違反「位元組為值之函數」），又寫在物件裡（違反「不得存在未進入雜湊的欄位」）。
*   **§7 的推薦改為不推薦任一方，並把天平移向乙。**
    甲原本的三個理由，第一個（位址不必動）已被 §8.4 第一點降級；
    第三個（一則裁定關四件事）仍成立；
    **而承重第 8 句是一個甲沒有回答的反對理由**：
    甲 之下，一顆歷史裡的 ⊥ **永遠不可能再說出它為什麼是 ⊥**，
    而那是「格表達不了自己的失敗，記錄才能」的**第五個證人**
    （前四：特權不留邊／撤回住審計行／軸是重不重算得回來／D40 的塌陷可分辨性）。
*   **甲仍有一條活路，但它不是原來那條**：
    若「成因」改由**歷史**攜帶（提交時把成因寫進審計行而非值裡），
    則值層乾淨、成因也拿得回來。**那是第四個候選，本文原本沒有列。**

### 8.5 更新後的候選

*   **甲** ⊥ 是裸原子，成因只活在當下的診斷訊息 ⟹ **提交之後成因永久消失**。
    〔已量〕運算元不在任何地方 ⟹ **這不是「可以再算一次」，是「沒有了」**。
*   **乙** 成因是值的一部分，進位址。`#conflict` ≠ `#divergent`。
    〔已量〕紀元成本：標準根 0 個 ⊥、紅線根不含 ⊥、語料不含 CAID
    ⟹ **只動含 ⊥ 的使用者根**。滿足承重第 8 句與 `REAL_03` §6.7 兩條。
*   **丙** 明文允許未覆蓋的位元組。**不推薦**（要改寫一條剛用一整弧修掉判例的 MUST NOT）。
*   **丁（新）** ⊥ 的值層是裸原子（甲的列印面），**而成因與訊息在提交時寫進審計行**
    （○ 的框或 ● 的 meta）。值乾淨、位址乾淨、成因可取回。
    **代價**：要回答「審計行裡的成因，其身分由什麼決定」，
    且它把一個值層的事實搬到歷史層——**與 disc 027「撤回是審計行裡的事實不是值間關係」同形**。

**⟹ 待裁：甲／乙／丙／丁。驗收方不再單推甲；量測與承重第 8 句把天平移向乙或丁。**

## 9. 用戶指出 `;;` 是為了 `%effect` ——順著它查，這一題落地了（2026-09-12）

用戶：「當時建議 `;;` 應該是因為那時候需要能同時給出 `%effect` 的資訊」。
**順著 `%effect` 查到了那則裁定，而它把本題整個收掉。**

### 9.1 `;;` 不是權宜，它是一個有條文的層

〔查 `ENGINE_SYNC` 2026-07-20「%effect 顯示疣弧開單（裁定 C）」〕逐字：

> (1) **`;; %effect:` 尾註入法 ＝ 診斷註解層首位法定成員**
> （**`SPEC_11` §3.4 新設**：引擎得以註解形式附加診斷資訊；
> parser 不可見、不參與語義／CAID／排序鍵；
> **凡語義資訊必須另有正式通道，註解永不得為唯一載體**）

〔查 `SPEC_11` §3.4 本文〕三件逐字：

*   **不可見性義務**：「診斷註解對 parser 不可見——不參與值語義、等值判定、CAID 與顯示排序鍵。
    **重新解析顯示輸出即丟棄之，而這不構成資訊損失**：凡具語義地位的資訊，
    **必須另有正式觀測通道**（元欄讀取、`~%Engine` 反映等），**診斷註解永不得是唯一載體**。」
*   **法定成員**：**只列兩個**——`;; %effect: <tag>`（正式對應 ＝ `.%effect`）
    與 `#ext:` 出處識別碼。
*   **與 §3.3 相容**：診斷註解屬顯示層附註，**不進入規範化形式，不影響無損迴路與 CAID 守恆**。

⟹ **用戶記得的那個判準，規格裡就寫著**，而且是**作為註解層可以有損的理由**：
「重新解析即丟棄，而這不構成資訊損失——因為凡有語義地位者另有正式通道。」

### 9.2 於是本題分成兩半，而兩半的答案**相反**

〔量 2026-09-12，`v0.47.0` 標籤建置，含對照組〕

```
(1 & 2).%cause    → #conflict          ← 正式通道存在且具體
(1 & 2).%nosuch   → _|_ (…)            ← 對照組：不是萬用回退
(1).%effect       → #pure              ← 對照組：既有法定成員的通道
(1 & 2).%message  → _|_ (…)            ← message 沒有通道
```

| | 正式觀測通道 | 進不進位址 | 是不是 §3.4 法定成員 | 寫不寫進 CAS 物件 | 判決 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| **`%cause`** | **有**（`.%cause`） | 不進——**而 `REAL_03` §6.9 第二款明文允許**（見 §9.3） | 不適用（它在**值本體**，不在註解層） | 是 | **合法** |
| **`message`** | **沒有** | 不進 | **不是**——法定成員只有兩個 | 是 | **違反 `REAL_03` §6.7** |

### 9.3 ⟹ 本文 §2 的結論是對的，但引錯了條文；§8.4 的更正過頭了

`REAL_03` **§6.9 第二款**逐字：

> **因果通道是唯一的例外（MAY）**：不進入位址的欄位**得**於因果／來源通道
> （`%cause` 及審計行）上可觀測——**判例：`TopCaused`**。
> 〔量，引擎 v0.32.0〕`_` 與靜態環所得之 Top **CAID 逐字元相同**，
> 而 `.%cause` 分別為 `_` 與 `#static_cycle`。
> **這是允許的，因為那個欄位不改變值是什麼，只改變審計行怎麼說。**
> **凡欄位改變的是值層結果者，不受本款保護。**

⟹ **`%cause` 不進位址是明文允許的，有條款、有判例、有量測。**
`#conflict` 與 `#divergent` 都不改變「那個值是什麼」（都是空集合）。

*   **本文 §2 的結論成立**（位址是對的），但當時引的 `SPEC_04` §162 是 fuel 截斷的上下文，
    **證據力不足；正確的條文是 `REAL_03` §6.9 第二款**。就地更正。
*   **本文 §8.4 把天平移向乙，那一步過頭了，就地作廢。**
    承重第 8 句（「重不重算得回來」）**對 `%cause` 是滿足的**——
    `.%cause` 就是那條拿得回來的路；§8.3 量到的「運算元不在任何地方」
    說的是**運算元**不可重現，而**成因**經由正式通道可得。兩者不是同一件事。
*   **§8.3 的量測本身仍然成立且仍然有用**，只是它指向的是 `message` 不是 `%cause`。

### 9.4 ⟹ 兩題的答案是相反的，本文 §4 說「兩題一個答案」是錯的

*   **排序第 2 項（`message`）** ⟹ **不進位址，也不進物件。**
    它沒有正式通道 ⟹ 依 §3.4 它**不具語義地位** ⟹ 依 §3.4 丟掉它「不構成資訊損失」
    ⟹ 依 `REAL_03` §6.7 它**不得**被寫進 CAS 物件。
    今天的狀態是：一個診斷註解層的產物**被持久化成了物件欄位**。
    **⚠ 而它甚至不是 §3.4 的法定成員**——那張名單只有 `;; %effect:` 與 `#ext:` 兩個，
    `;; Incompatible types: …` 是**第三個沒有被登記就上路的成員**
    （與 `TAG_REGISTRY` 治的病同形：未登記之物搭在已登記的通道上）。
*   **O85（`_|_` 的正準列印形）** ⟹ **成因留在值本體**（§6.9 第二款允許、`.%cause` 佐證）
    ⟹ **文法必須定義那個形** ⟹ **傾向 O85 的乙或丙，不是甲。**

⟹ **兩題不是一個答案：`message` 要拿掉，`%cause` 要補文法。**
本文 §4 把它們綁成同一個答案，**那是在找到 §6.9 第二款與 `.%cause` 之前寫的，作廢。**

### 9.5 更新後的建議

| 題 | 建議 | 依據 |
| :-- | :-- | :-- |
| **排序第 2 項** | **`message` 不得寫入 CAS 物件**；它只活在診斷註解層，於失敗當下產生。**若要保留它，必須先把它登記為 §3.4 的第三個法定成員並給它一條正式通道**——而那等於宣稱它有語義地位，需另裁。 | `REAL_03` §6.7；`SPEC_11` §3.4（不可見性義務＋法定成員名單） |
| **O85** | **補文法**，使帶因 bottom 成為合法拼法（乙），或改用既有記錄形（丙）。**不是甲**——成因有通道、有條款、不可從值層移除。 | `REAL_03` §6.9 第二款；`SYNTAX_02` §17；`REAL_01` §1.3 第三條 |

**⚠ 兩者仍應一起裁**——不是因為答案相同，而是因為**它們今天長在同一行輸出上**，
分開做會讓那一行在兩個版本之間各壞一半。
