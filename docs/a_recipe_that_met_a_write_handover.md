## 0. 判準（規格原文與裁定）

*   **D110（`nlang-spec/meta/oo/STATUS.md`；`SPEC_10` §2.3.1）**：一個 `#pure` 定義的答案若在求值時讀到了宇宙，演化與提交存的都是它的**語法**；讀它的人每次讀到當下的宇宙，與同一句話就地重讀同答。**存語法不得讓衝突晚到**：與既有定義相撞的寫入，照舊在演化時以兩邊的答案判、拒絕。
*   **`SPEC_03` §3.1**：展開是格的合併（同鍵相交），不是後寫者勝。
*   **同一個座標寫兩次是兩次寫入的交會**（`SPEC_10` 演化單調、G2-S）。其中一次是配方時，交會也讀了宇宙——D110 適用於交會本身：直接寫成一句 `r: c & { z: 9 }` 今天就存配方、讀當下的 `c`。
*   **D111**（根層展開讀當下的來源）**不在本卡**；本卡只動直接寫在座標值上的那一層展開。

## 1. 缺陷

〔量，v0.93.0 標籤建置；v0.92.0 對照〕

*   **配方遇上記錄寫入，配方那一側不見了**（v0.93.0 的回歸，靜默丟資料）：`c: { b: 2 }`、`r: c`、`r.z: 9` ⟹ `_.r` v0.93.0 `{ z: 9 }`，v0.92.0 `{ b: 2 z: 9 }`。`run --observe r`、`status`、提交後同；同檔、兩次 evolve 一次提交、兩次提交、兩次寫入對調先後，皆然。`r: (x -> x) c`、`r: c & { a: 1 }`（剩 `{ a: 1 z: 9 }`）、`w: t`（開放項，`{ b: 1 } |> _.w` 少了 `a`）、私有 `~p: c` 同；`r: <<c>>` 與記錄欄位 `r: { x: c }` 再寫 `r: { x: { z: 9 } }` 在 v0.92.0 就已丟（同一機制的舊實例）。同鍵相撞照舊拒絕（`r: c` 之後 `r: { b: 3 }` rc=1）。
*   **直接寫在座標值上的展開讀了宇宙仍存答案**：`c: { b: @int }`、`r: { a: 1, ...c }` 提交後再提交 `c: { b: 5 }` ⟹ `_.r.b` 仍 `@int`；`c` 之後新增 `d` ⟹ `_.r.d` 是 `_`；`r` 先寫、`c` 晚到（兩次提交或兩次 evolve）⟹ `_.r.b` 是 `_`，兩種 evolve 順序兩個根。巢狀 `r: { x: { a: 1, ...c } }` 這四面全對、兩種順序同根（v0.93.0 與 v0.92.0 同）。
*   **與座標層展開相撞的寫入被接受**：`c: { b: 2 }`、`r: { a: 1, ...c }`、`r: { b: 3 }` 同一檔 ⟹ evolve rc=0、提交存 `{ a: 1 b: ⊥ #conflict }`（v0.92.0 同）；跨一次提交則被拒。
*   〔讀〕(1) 宇宙自己的合併——evolve 把寫入併進暫存（`universe.rs`）、工作集成員依序相交（`injections.rs`）、提交把暫存併進根、觀測把根與暫存併成一個視圖——都呼叫 `engine.unify`，它用**看不到宇宙的引擎層上下文**強制兩側；配方在那裡讀到 `_`。`unify.rs` 的 F3 註解早寫了這個風險（「在 evolve 的引擎層上下文強制等於快照」）。Q-091 讓別名、施用等存配方之後，這條路從少數（算術配方、活引用）變成常見。(2) `unify` 有一個以兩側位址為鍵的記憶表：同一對值在別處被普通地相交過，結果會被宇宙的合併直接取用。(3) 記錄字面量的展開延到 `land_staged_spreads` 才讀來源，evolve 求值時 D110 的旗標沒被設，`recipe_instead_of_pure_answer` 把它當不讀宇宙的字面量留答案；`pending_spreads` 是 `#[serde(skip)]`，落地前不進成員。

## 3. 射程＝不變式（不是機制）

*   **M1 交會不丟任何一側**：一個座標被寫兩次以上、其中有配方時，讀它得到每一次寫入的交會——與把它們寫成一句 `&` 相同。同檔、跨 evolve、跨提交、任何先後皆然；答案與根不隨寫入的先後或怎麼分成 evolve／提交而變（r1、r2）；在一個宇宙上 `run` 一個程式，觀測到的也是這個交會（r7）。「配方」是 D110 的意思：求值時讀了宇宙；字面欄位的 thunk（`{ a: 1 }` 的 `1`）不是——兩個字面的交會照舊當場判（`a: 1 & 2` 是衝突，不是延後的語法）。
*   **M2 交會仍是讀數**：之後來源變了，那個座標跟著變，與一句 `r: c & { z: 9 }` 相同（r3、r5）。
*   **M3 座標層的展開讀了宇宙就存語法**：來源收窄、新增欄位、晚到，讀到的都是當下的來源，與巢狀那層相同；兩種 evolve 順序同根（r4）。
*   **另一半——碰撞照舊在演化時拒絕**：與配方相撞的寫入、與座標層展開相撞的寫入，都在 evolve 拒絕，同檔與跨提交皆然（g1、r6）。
*   **另一半——沒遇上配方的不動**：兩個答案的交會、同一個配方寫兩次、D110 已移的根、巢狀與閉合來源的展開，存形與根不變（g2）。
*   **另一半——寫一次已有的東西不移根**：同一個寫入在下一次提交再寫一次，根與讀數都不變（g3）。
*   若你找到另一個「宇宙自己的合併在看不到宇宙的地方強制配方」的入口（`pin` 提交、`refine`、`~%Config` 的部分合併、gc、diff、log……），一併在射程內，在 8.1 列出。
