## 1. 一條性質，六個輸入

**印出一個值，必須得到「讀回去是同一個值」的源碼。**

今天它可以得到「讀回去是**另一個**值」的源碼，而且**不報錯**：
`{ "a.b": 1 }` 是一個座標（SYNTAX_03 §106 #8），印出 `a.b: 1`，讀回去是兩個。

六支紅是同一條性質的六個輸入，**不是六個 bug**。

## 2. 三處改動

### 2.1 引號性不得在 AST→值 的邊界上被丟掉

〔讀〕`crates/interpreter/src/universe.rs:35`：

```rust
FieldKey::Quoted(name) => vec![name.trim().to_string()],
```

**好消息**：AST 上方**已經**區分 `FieldKey::Quoted` 與 `FieldKey::Named { name, prefix }`。
遺失只發生在這**一個**邊界。

〔讀〕另有 `universe.rs:182` 對引用鍵測 `starts_with("~%")`——**同族，一併處理**。

**裁定（Q1）**：**引號內的字元屬於名字，前綴不例外。**
⟹ `{ "@t": 1 }` 是資料軸上一個名叫 `@t` 的鍵，**不是**型別軸的 `t`。

### 2.2 印出端必須加引號

〔讀〕`value.rs:1064–1079` 一族 `format!("/{}", k)`：**前綴不是被儲存的鍵的一部分**，
它由「這個鍵住在哪個軸」在顯示時重建。

⟹ **一旦 §2.1 落地，顯示就不再是單射**（資料軸的 `@t` 與型別軸的 `t` 都顯示為 `@t`），
**除非印出端同時加引號**。**§2.2 不是 §2.1 的配套，是它的可行性條件。**

**裁定（Q3 正準形）**：**非純識別碼即加引號。**
——可機械檢查，且與 SYNTAX_03 §104 #6「純識別碼鍵不應多餘加引號」互為逆。

**射程須含三個輸出面**：`to_string_plain`／`to_nlang`／`inspect`。

### 2.3 `field_key` 補多行字串（跳脫）

〔讀〕SYNTAX_02 §106 #11 **逐字指名 `quoted_key`**，並為它與 `str_lit` 指定同一條
出路：「需要引號的內容用多行字串」。
〔讀〕但 SYNTAX_03 §1／SPEC_14 §102 的
`field_key = { anon_set | path | named_key | quoted_key | tag }` **沒有多行形式**，
引擎（`n.pest:38`）逐字照做。

⟹ **這是規格的內部矛盾，不是實作缺陷**：散文指定的補救路徑被同一份規格的文法擋住。
**裁定：把多行字串補進 `field_key`。** 不是新機制，是讓既有機制到達條文已指派給它的位置。

## 3. 標準根：改名三個鍵（裁定 B）

〔量〕標準根 **238** 個相異（軸,鍵），新規則下需要引號者**恰為 3 個**：

```
/~%Engine//%differential.1    …/.2    …/.3
```

它們是 rules 軸（`/`）而**名字本身**是 `%differential.1`（以 `%` 起首且含 `.`）。

**裁定 B：改名，使標準根無任何鍵需要引號。**（另一路是實作 Q2 的 `prefix ~ quoted`
只為這三個鍵引進新文法——代價不對稱。）

*   **R6 釘的是性質不是拼法**：「每一個標準根座標都寫得出而不需要引號」。
    **新名字由交付方選**，只要是純識別碼。
*   Q-033 審計 §5 已判定它們是**引擎內部 arity 多載編碼漏進使用者可見座標**
    ——本來就該改。

> ⚠ **這會移動標準根 digest**，因而移動每一個新根的位址。
> **請照舊回報新舊兩組數值**，並依 `genesis.rs` 檔頭流程重算 seed CAID。
> 切版時的軸別判定由驗收方處理，**交付方不改規格、不改 CHANGELOG**。
